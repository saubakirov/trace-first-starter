## 1. Objective

Move live task state and coordination history out of the root `README.md` Task Board and into each task's
own folder, so that two tasks advancing at the same time change different files. Ship the discovery route
that replaces the board, the participant profiles that say who acted, and an accounting migration that
leaves the existing corpus byte-identical. This is the mode-agnostic core: transport is TFW-61's.

## 2. Scope

### In Scope

- configured task container, nested by immutable creation year
- clock-derived task identifiers satisfying DoD 18
- a short bounded task state file, and a `journal/` of one immutable file per event with a measured
  entry-length ceiling
- `team/<handle>.md` participant profiles for humans and agents; private device binding off the shared tree
- deterministic index generation and its degraded-state reporting
- removal of the root Task Board and every read of it, including the documentation generator
- accounting migration of the existing corpus, with nothing renamed, moved or invented
- canonical rules, configuration, templates, adapter originals, Quick Start and docs generation
- `2.0.0` release surface: version, CHANGELOG, migration guidance, `tasks/README.md`

### Out of Scope

- any Git or file-sync transport rule, topology, landing protocol or provider matrix — **TFW-61**
- observation of a non-technical participant or a real provider client — **TFW-61** (S43)
- a state engine, mutation interface, schema files, journal segments, digest chains, device identifiers
  or a session-name gate — removed by research iteration 3
- renaming, moving or reorganizing any existing task directory
- task-local debt (**Phase B**) and knowledge staging (**Phase C**)
- byte-identical adapter copies under `.claude/`, `.agent/` and `.agents/` — excluded from budget by
  owner ruling S32, and regenerated by the project's normal adapter sync, not by this phase's accounting

## 5. Acceptance Criteria

### AC-1: Tasks live in a configured container, nested by creation year, on stable paths

A task is created at `<container>/<YYYY>/<id>__<slug>/` where the container is a configuration value and
the year is the year of creation.

- [ ] `project_config.yaml` carries the container key with a documented default and every workflow reads it
- [ ] no workflow writes a hardcoded `tasks/` path
- [ ] no lifecycle transition, and no terminal state, moves a task directory
- [ ] the year in a path is never recomputed or updated after creation
- [ ] a task created in December and closed the following year stays in the earlier year folder

Gate: create a fixture task, drive it through `active → waiting → active → done`, and diff the path set
before and after — it must be identical. Set the container key to two different values and confirm both
resolve.
Evidence: N/A — transport-independent behaviour verified by fixture; real-environment observation belongs
to TFW-61.

### AC-2: Task identifiers need no project-wide read  [depends: AC-1]

Satisfies master HL DoD 18 and amendment A1.

- [ ] the identifier is derived from the clock in the grammar `YYYYMMDD-HHMMSS`, per owner selection
- [ ] creating a task reads no other task directory and no counter
- [ ] two participants creating tasks with no knowledge of each other cannot produce the same identifier
- [ ] a same-second collision is detected and resolved by taking a new actual timestamp, never by reuse
      or overwrite
- [ ] both the new grammar and the legacy `{prefix}-{seq}` grammar are readable by every consumer

Gate: run task creation with the rest of the corpus hidden — it must succeed. Replay two creations from a
frozen clock and confirm the collision is detected, not silently merged.
Evidence: N/A — determinism is fixture-verifiable.

### AC-3: The journal is one immutable file per event, with a measured ceiling  [depends: AC-1]

- [ ] one file per event, named from the clock; the filename is the identifier
- [ ] a written event is never rewritten; a correction is a new event
- [ ] the closed vocabulary is `created`, `dispatch`, `handoff`, `transition`, `ownership_changed`,
      `amendment_escalated`, with `consolidation` reserved for later phases
- [ ] every event carries time, kind, actor, state change, at least one artifact reference, and at most
      one bounded summary
- [ ] **entry length has a finite ceiling that a person can check by eye**, and the configured value is
      justified by a recorded measurement — the iteration-1 fixture value of 240 code points has no
      privileged status (S30)
- [ ] content over the ceiling moves into an artifact and the entry keeps a reference
- [ ] no event body copies HL, RES, TS, RF, REVIEW, evidence or chat text
- [ ] two participants appending concurrently produce two files and no contended write

Gate: append from two processes at once and confirm two files and no loss. Attempt an over-ceiling entry
and confirm it is refused with the artifact route named. Show the measurement behind the configured value.
Evidence: N/A — concurrency on one machine is fixture-verifiable; cross-device behaviour is TFW-61.

### AC-4: Participants are declared in `team/`, and a session knows who is acting  [depends: AC-1]

- [ ] one file per participant with a stable handle, a display name and an explicit `human` or `agent` type
- [ ] an automated principal has its own profile and never borrows a person's identity
- [ ] a single profile is used without asking
- [ ] several profiles resolve through a binding stored **only** on the participant's own machine
- [ ] no binding, a shared device, a copied binding or a stale profile produces exactly one short question
      before the first durable write
- [ ] identity is never inferred from an OS username, hostname, folder name or account display string
- [ ] the shared tree contains no current-user file and no private preferences
- [ ] the profile is documented as declared attribution, never as authentication

Gate: run the four resolution cases — one profile, several, no binding, stale binding — and confirm the
question appears exactly where specified and nowhere else.
Evidence: N/A — a non-technical participant is TFW-61's observation (S43). **The RF must state that
readability by a non-specialist is design intent and was not observed.** NS3 forbids the untested claim.

### AC-5: The index is generated, declared derived, and never authoritative  [depends: AC-1]

- [ ] generated deterministically from task state plus the legacy snapshot; the same input yields the
      same bytes
- [ ] carries identity, short goal, short value, lifecycle, owner, terminal outcome where applicable, and
      a link to authority
- [ ] declares that it is derived, its source count and its freshness
- [ ] reports every legacy, malformed or unresolved input instead of dropping it
- [ ] sorts so that the newest year is last and the newest task is the last entry within it
- [ ] pinned to the top of the container listing
- [ ] absent, stale or malformed, it degrades discovery and changes no task state
- [ ] every workflow acting on a selected task re-reads that task's state first

Gate: generate twice and diff — byte-identical. Run the four conditions (normal, absent, stale, malformed)
and confirm task state stays authoritative in all four.
Evidence: N/A — deterministic.

### AC-6: The legacy corpus is accounted for exactly and left byte-identical  [depends: AC-1, AC-5]

- [ ] migration runs against an isolated copy or manifest before any project write
- [ ] every board row and every task directory is accounted for exactly once
- [ ] zero renames, zero moves, zero byte changes to any existing task artifact
- [ ] task state is created only for the 11 non-terminal tasks, and only from verified facts
- [ ] a missing goal, value, owner, lifecycle or terminal fact is never invented
- [ ] unresolved and malformed entries stay discoverable and non-actionable with a stable diagnostic
- [ ] the 41 terminal tasks are captured in the frozen legacy snapshot before the board is removed

Gate: run against a copy, diff the corpus — the only additions are the 11 state files. Reconcile the
accounting total against the directory count with zero unexplained entries.
Evidence: N/A — accounting is deterministic.

rows. The 8 that do not match are TD-177 schema drift and are exactly the malformed class this AC

## 6. Technical Guidance

- The container default for a new project is `tasks/`. This repository sets it to `work/` so the legacy
  corpus keeps `tasks/` untouched; `work` sorts after `tasks`, which is why the newest task is the last
  entry in the last folder rather than buried above the legacy block.
- Both grammars must be readable everywhere, so write one resolver and use it in every consumer rather
  than pattern-matching per call site.
- The state carrier should be short enough to read at a glance and closed enough to parse without
  ambiguity. Every field must have a named reader; a field no consumer reads does not belong.
- Do not reintroduce a pointer field that duplicates a journal fact. `last_event_id` and `journal_head`
  were removed precisely because they created a two-file synchronization problem that then needed an
  engine to solve (S35).
- `KNOWLEDGE.md` D24 is why references did not replace adapter copies and why they will not replace this
  either: agents stopped following indirection. Prefer an inline rule over a pointer in normative text.
- The index generator and the migration script are the only executable deliverables. Keep them out of the
  read and write path of a task: they are invoked deliberately, never as a side effect of a transition.

## 7. Definition of Failure

- ❌ A component is required for a task to be read or advanced — this is the runtime NS3 forbids
- ❌ A counter, a project-wide maximum read, or any identifier allocation that consults other tasks
- ❌ Any existing task directory renamed, moved or byte-changed; any of the 249 commit subjects orphaned
- ❌ A task directory moved by a lifecycle transition, a terminal state or a year correction
- ❌ The derived index treated as authoritative by any workflow, or a workflow acting without re-reading
  task state
- ❌ A journal entry with no ceiling, a ceiling with no recorded measurement, or an event body copying
  artifact or chat text
- ❌ A shared current-user file, private preferences on the shared tree, or identity inferred from an OS
  username or hostname
- ❌ Any board row or directory unaccounted for, or any task fact invented to fill a gap
- ❌ The RF implying that non-technical readability or any transport behaviour was verified
- ❌ The census exceeding roughly 75 files total, or a new group appearing, without returning to the
  coordinator — the owner's overrun ruling was given against the counts in §4, and delegation is never
  authority to accept a further overrun (`conventions.md` §3 rule 19)

## 8. Phase Risks

| Risk | Mitigation |
|---|---|
| The census in §4 is a grep upper bound and the real edit set differs | The RF reports corrected counts per file; a material move returns to the coordinator before work continues |
| The state carrier drifts back toward prose | Closed field set with bounds; no free-text field that invites explanation |
| The journal becomes the next README | Measured ceiling, closed vocabulary, references not prose, immutability once written |
| Two containers become unexplainable within a year | `tasks/README.md`, CHANGELOG and migration guidance ship in this phase, not later |
| A malformed legacy row is silently normalized | Exact accounting; the 8 known non-matching rows are a named input, not a surprise |
| Removing the board breaks a reader nobody remembered | `git grep` sweep over originals is part of AC-8's gate, not a post-hoc check |
| Readability by a non-specialist is assumed | Stated as intent, never as verified; observation is TFW-61's (S43) |
