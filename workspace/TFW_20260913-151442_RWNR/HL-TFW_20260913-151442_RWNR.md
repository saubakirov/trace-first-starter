## 1. Vision 🔒 FROZEN

Trace-First Workflow has one clear public entry for starting or reconsidering task planning, while lifecycle-specific commands remain responsible for research, execution, review, documentation, knowledge, and release. The separate `/tfw-resume` command no longer exists because every behavior that protected continuation has an explicit, tested survivor route rather than a second overlapping entry point. Historical traces remain truthful and readable.

**Impact:** A user returning to a task no longer has to decide between `/tfw-plan` and `/tfw-resume`; the command surface becomes smaller without sacrificing phase selection, historical read safety, recovery, role separation, or deterministic routing.

> “I normally continue work through plan. Prove that resume is unnecessary, and destroy it if it is.”

## 2. Current State (As-Is) 🟢 FREE

The public surface contains two Coordinator entry points whose user jobs overlap but whose implementations are not equivalent. `/tfw-plan` already resolves a known task and routes an approved TS to `/tfw-handoff`. `/tfw-resume` additionally owns phase selection, historical-only read protection, a status matrix, and limited closing/record-recovery behavior. Therefore “duplicate implementation” is already disproven; “unnecessary public command” remains a viable hypothesis if those protections can be preserved elsewhere.

| Measure | `/tfw-plan` | `/tfw-resume` | Interpretation |
|---|---:|---:|---|
| Canonical workflow lines | 220 | 84 | Removing resume is not safe if its 84 lines are merely pasted into plan. |
| Canonical workflow words | 1,995 | 690 | Plan already exceeds the 1,200-word design rule, so convergence must reduce or redistribute instructions. |
| Canonical workflow bytes | 14,416 | 5,093 | Net surface, not command count alone, must be measured. |
| Repository text occurrences | 583 in 242 files | 89 in 43 files | These are references, not invocation telemetry; they cannot prove real usage frequency. |

| Capability | Plan today | Resume today | Retirement obligation |
|---|---|---|---|
| Continue a known task with an approved TS | Routes to handoff | Routes by status | Keep the plan route deterministic. |
| Rework an HL or TS after a return | Owns planning revision | Points elsewhere | Keep planning authority in plan. |
| Resume a research iteration | Research workflow owns it | Reads the state | Preserve research-local continuation. |
| Select among multiple phases | No equivalent behavior found | Builds a phase matrix and asks for selection | Provide an explicit surviving route and tests. |
| Inspect a historical-only task | No equivalent guard found | Stops after read-only inspection | Preserve the no-mutation guarantee. |
| Close or repair a task record | Role Lock forbids this in plan | Has narrow Coordinator recovery behavior | Rehome the behavior without widening the wrong role. |

The repository also contains one verified stakeholder fact saying that the owner normally continues through plan and regards resume as obsolete. That is evidence of user intent, not by itself proof that all protected semantics can be deleted.

## 3. Target State (To-Be) 🔒 FROZEN

The task retires `/tfw-resume` only after an evidence-backed responsibility map names and verifies the survivor for every current behavior. The surviving system has no replacement public “resume” command, no ambiguous duplicate entry point, no orphan adapter or receiver, and no edits to historical task truth.

| As-Is | To-Be |
|---|---|

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. `/tfw-resume` is deleted because the owner rarely invokes it, without proving survivor routes for its unique protections.
- ❌ 2. Resume instructions are pasted into plan, increasing ambiguity or worsening the existing workflow-size violation.
- ❌ 3. Phase selection, historical read-only safety, closing, recovery, or a lifecycle route becomes unavailable or less constrained.
- ❌ 4. Plan gains mutation or closure authority that violates its Coordinator Role Lock.
- ❌ 5. A replacement public resume alias, wrapper, or hidden long-lived helper recreates the same surface under another name.
- ❌ 6. Canonical sources, adapters, manifests, docs, tests, clean installs, and update receivers disagree about whether the command exists.
- ❌ 7. Historical traces or changelog records are rewritten to make the deletion appear cleaner.
- ❌ 8. Repository occurrence counts are presented as usage telemetry or absence of references is presented as proof of safety.
- ❌ 9. A phase TS is drafted, implementation is dispatched, or a write is made before the owner records the G1 verdict.
- ❌ 10. Knowledge consolidation, unrelated configuration repair, or mutation of TKL enters this task without an approved amendment and its own authority.
- ❌ 11. An unaccepted or provenance-losing result is merged into `master`, or integrated verification is skipped.
- ❌ 12. Release preparation or an external effect starts before G2, or release scope/actor/version/tag/changelog is inferred from the mandate rather than selected by the owner.
- ❌ 13. Implementation begins before the HL is frozen, the exact phase TS/value denominator is approved, or the required direct units are dispatched.

**On failure:** Stop mutation, preserve evidence, return to the Coordinator with the exact failed invariant, and either revise through the existing authority or ask the owner to reject/supersede the retirement target. Never partially remove the command surface.

## 7. Principles 🔒 FROZEN

1. **Delete surface, preserve semantics** — The command may disappear only after every continuity guarantee has a verified home.
2. **One user job, one obvious entry** — A returning owner should not need internal lifecycle knowledge to choose between overlapping Coordinator commands.
3. **Role boundaries outrank convenience** — The surviving entry may route work but may not acquire authority that belongs to another workflow role.
4. **Evidence before retirement** — Preference and text counts initiate the hypothesis; scenario evidence decides it.
5. **Net simplification** — Success reduces the retained conceptual and instruction surface, not merely the command table.
6. **Canonical first, adapters thin** — Behavior lives in canonical workflows; adapters expose it without independent semantics.
7. **History remains true** — Current guidance is cleaned, while historical records keep the names and facts that were true when written.
8. **No substitute ceremony** — Removing resume must not create a renamed command, mandatory portfolio, or equivalent coordination layer.

## 10. RESEARCH Case 🟢 FREE

### Blind Spots

- Which resume behaviors are externally observable contracts versus incidental workflow prose.
- Whether closing and record recovery already have a safe existing receiver or require canonical restructuring.
- Whether supported adapters and update paths generate or copy resume artifacts from sources not found by a simple text scan.
- Whether any tests rely on resume as the only way to reach a protected state rather than merely checking the command exists.
- Whether convergence can reduce total instructions while keeping plan understandable and within an architectural remediation path.

### Hypotheses

| # | Hypothesis | Status |
|---|---|---|
| H1 | The returning-user job served by `/tfw-resume` is already covered by `/tfw-plan` plus lifecycle-specific commands, so a second public entry has no independent user value. | open |
| H2 | Every unique resume protection can be assigned to an existing canonical route without widening the wrong Role Lock or creating a replacement public command. | open |
| H3 | Canonical sources, skills, adapters, manifests, docs, tests, clean installs, and update receivers can remove resume consistently while historical traces remain untouched. | open |
| H4 | The surviving design reduces the combined 2,685-word workflow surface and does not solve command count by making plan a larger monolith. | open |

### Risks of Not Researching

Skipping research would confuse low user demand with semantic redundancy. The likely failure would be a cosmetically smaller command list that loses phase choice, historical safety, recovery, or adapter parity and can only be repaired by reintroducing equivalent complexity later.

### Proposed RESEARCH Focus

1. **Gather**: Enumerate all callers, receivers, state transitions, safety stops, generated copies, update paths, and scenario tests associated with resume.
2. **Extract**: Build a behavior-to-authority matrix showing which capabilities already belong to plan or a lifecycle-specific workflow and which have no safe survivor.
3. **Challenge**: Try to falsify retirement with the strongest historical, multi-phase, recovery, Role Lock, install, and adapter-parity counterexamples.

The research output must end with the G1 decision brief: recommended verdict, exact change design, rejected alternatives, value and cost, failure modes, and a clause-level Project North Star application map. It must not proceed directly to TS.

### Why Not Just...?

- Why not delete every file containing `tfw-resume`? — Text matches mix live surface with historical truth, and the command currently protects behaviors that must survive.
- Why not paste `resume.md` into `plan.md`? — Plan already exceeds its design limit, and some resume actions conflict with plan's Role Lock.
- Why not keep both because resume has unique code? — Implementation uniqueness does not prove that the public command is the correct home for those behaviors.
