## 1. Understanding

Implement the approved single-phase cutover as one coherent removal boundary. Full keeps the
authoritative task/status/event contracts and one complete tool-independent Knowledge Gate algorithm,
but ships no Python helper. The former payload implementation becomes upstream-only semantic tooling,
a bounded read-only doctor, and a self-contained versioned migration bundle. The committed portfolio
cache and all freshness/write duties disappear; prose length becomes guidance; hidden documentation
landings preserve trace links; Assisted and protected history remain byte-identical.

The owner already approved the TS, its normal implementation choices, and the immutable denominator
of 35 logical VALUE files / 3,600 touched text LOC. The approved AG grant satisfies the execution gate;
no routine approval will be requested again.

## 4. Recommendations (suggestions, not blocking)

1. Keep all machine-readable report fields explicit and deterministically ordered, including empty
   arrays. This makes the upstream doctor useful without turning its representation into Full authority.
2. Preserve semantic reader APIs when moving them, but delete index-only behavior rather than carrying
   deprecated aliases. The compatibility boundary is the versioned migration bundle, not a permanent
   index façade.
3. Generate one hidden landing per recognized task directory from real compiled pages only. Do not
   generate a parent catalogue or a default portfolio page as an incidental side effect.

## 5. Risks Found (edge cases, potential issues not in TS)

1. The current module mixes semantic readers, presentation, and product checks. A mechanical rename
   would retain prohibited index behavior; extraction must be verified by capability and source scans.
2. The migration currently imports the payload module before argument parsing. The moved executable
   must show `--help` without PyYAML and exit 2 before planning or writes when the dependency is absent.
3. Documentation output paths strip the configured task-container prefix. A no-HL fallback must target
   the generated `tasks/{container-relative-task}/index.md`, not the source directory path.
4. Existing integration/runtime-context tests contain historical literals intentionally. Current-rule
   scans must classify history rather than mass-rewrite those records.
5. Candidate accounting may be smaller than the 35-file maximum, but no unlisted VALUE constituent may
   be added. Any such need would require prospective authority before the write.
6. Pre-act protected boundaries are fixed: Assisted tree `871ce20594402353a51818681f6f14c8cc9a3feb`
   matches Baseline and execution base; 243 pre-Baseline journal/snapshot entries hash to
   `d2b6d21f227d165f99933cf1dfc34d6c6a73f3344ef421b24ba88a6e60aa5497`; the known event is blob
   `d156e68b55c47818820e364e2816630cbb03cef8` at both revisions.

## 6. Inconsistencies with Code (spec vs reality)

1. The TS requires upstream-only tooling, while the current `gen_index.py` and migration executable are
   shipped in `.tfw/scripts/` and four ordinary workflows invoke the helper.
2. The TS requires no index product, while current code still exposes default index write, `--check
   index`, freshness rendering, and `workspace/00-INDEX.md`.
3. The TS requires prose advice to be exit-neutral, while current status and event readers enforce
   numeric bounds and migration truncates `lifecycle_verbatim` and other status prose.
4. The TS requires exactly four doctor operations with exits 0/1/2, while the current CLI has three
   `--check` subjects, a separate Knowledge flag, index write behavior, and no indeterminate exit.
5. The TS requires hidden task landings and no top-level Tasks route, while the current docs generator
   emits `tasks/index.md`, adds `Tasks` to navigation, and can link a no-HL task to a directory with no
   landing page.
6. The TS requires explicit owning-workflow postconditions, while init/update currently delegate their
   final consistency decision to the soon-to-be-removed payload helper.
