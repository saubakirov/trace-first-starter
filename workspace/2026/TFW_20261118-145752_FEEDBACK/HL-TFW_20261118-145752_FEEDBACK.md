## 1. Vision

A contributor encounters friction while using TFW. While the details are still available, their agent turns the experience into a short report the contributor can check and share. The maintainer can decide whether to investigate, accept the need, suggest a local remedy or decline, even when they disagree with the proposed fix.

### 3.2 Value flow

```text
person encounters friction → agent retrieves one relevant local fact
                           → contributor verifies the shareable draft
                           → maintainer sees consequence and desired outcome
                           → maintainer can choose a next action
```

Draft algorithm: identify the user's request and the moment expectation diverged. Select the evidence that would change triage (version, setting, exact rule or minimal reproduction where available). Distinguish a person's request, an observed outcome, and an agent's inference. If relevant, compare the desired change with one applicable upstream TFW principle and state its practical consequence. Propose an exact correction only when supported. Stop once the decision is legible or the missing fact can be named. The person controls outbound sharing and can edit the draft.

## 5. Definition of done (proposed)

1. On the two actual submissions, show original → shareable draft. The maintainer can identify the user's intent, lost value, known evidence and requested decision from the first screen. Record which decision was possible and which fact, if any, was still needed.
2. A contributor with only a screenshot or quotation can report the symptom and mark attribution or cause as unknown. A richer case can include a precise optional change and a relevant TFW tradeoff. No invented reproduction.
3. The draft can be produced on demand without preloading a Full planning workflow, reading other sessions or routinely starting another agent. Check what each case actually required the reporter to read or do. Keep only fields that change the reader's decision or protect a sharing boundary.
4. A contributor can inspect the exact publishable text, including a compact visualization, and omit private project data. The next step for Issue and for an existing PR is clear. Any adoption or speed claim must match observed evidence.

## 6. Definition of failure

Revise the format if a maintainer must reconstruct the original chat, if a hypothesis reads as an observation, or if an actionable case is rejected for lacking a patch. Reduce the procedure if its cost prevents a person from submitting a useful report. If a necessary detail cannot be shared, record its limit and return the public-safe portion.

## 9. Risks

A polished theory can disguise missing evidence. A required root cause, patch or full retrospective would discourage people with incomplete but valuable reports. A long checklist can move the maintainer's work to the contributor without reducing total cost. Look for these failures when comparing each original with its draft.

## 10. Research case and alternatives

| Approach | Benefit | Burden or failure case |
|---|---|---|
| GitHub template alone | Immediately available to humans | If the missing fact lives in the agent's current context, the human still reconstructs it |
| On-demand short instruction and example (proposed) | Collect evidence at the point of failure, with a human-readable draft | If both cases can be handled equally well with just the template, remove the instruction |
| Common Issue / PR / MR standard | Familiar layout across projects | Change proposals and completed changes require different evidence. Extend only if actual examples show repeated benefit |
| Current chat practice | Very low effort for the reporter | Maintainer must recover context and scope before deciding |

Use the incoming examples to test whether the authoring procedure changes a disposition or saves a material follow-up. Also test whether each suggested field can be removed while leaving the decision intelligible. Two examples can expose counterexamples, but cannot establish adoption or general savings.
