## 1. Vision

A receiving team encounters a problem that the TFW maintainer cannot observe remotely. In the affected session the agent investigates from the framework developer's perspective. It connects the user's goal, the real operation, the installed TFW rule or reader, and the smallest native observation that explains the divergence. The contributor can share the finding in one screen. An upstream developer can pick up the diagnosis, choose where to change TFW, or run one specific outstanding check without reconstructing the incident.

### 3.2 Value flow

~~~text
user's lost outcome → reconstruct one actual operation
                    → compare installed TFW assumption with native behavior
                    → locate first divergence → test an alternative locally
                    → return finding + before/after + how a proposed fix would be checked
~~~

The local worker adopts the perspective of a TFW developer under its existing authority. Start from the installed file actually used. Inspect the relevant upstream purpose and constraint only where they affect the proposed result (for economics: transferable, honestly attributable usage). Prefer already available receipts, own-source metadata and read-only observations. Identify evidence by kind and version; publish only a contributor-reviewed, sanitized draft. The reporter inspects available evidence independently. A new paid run requires explicit agreement from that agent's own user. Changes to persistent configuration or source access require separate authority. At a material gap return what was checked, what was unavailable, and the one observation that would change the recommendation. For a simple product question, answer the decision directly.

## 9. Risks

The strongest objection to a developer-style field analysis is that an agent with one affected installation can overfit the adapter to it, or spend more than a maintainer would. Preserve the scope of the observation and link the proposed fix to an independent check. A reliable single case can locate a failure. Broader support needs evidence at its claimed scope.

## 10. Research case and alternatives

| Approach | Value | Cost or failure case |
|---|---|---|
| Short Issue template; maintainer diagnoses | Lowest contributor effort for product requests and well-understood failures | A maintainer may never have the exact runtime, store or orchestrator relationship needed to choose a fix |
| On-demand skill through the existing installer (recommended) | One invocation in the affected session produces evidence for an upstream decision | Eight upstream paths, including installed copies. Compare local diagnostic benefit against the reporter’s effort |
| Separate investigation or reproducer | Preserves the user's task context during expensive or uncertain work | Needs a portable handover and access; a fresh session may lose the only native binding |
| Current chat practice | Easy to send a symptom | Repeated clarification, uncertain ownership and speculative fixes fall to the maintainer |

**Saint-Exupéry subtraction.** Remove mandatory screenshots, quota percentage, wall-clock duration, exhaustive inventories of nine sessions, blanket reading of every NS principle, automatic PRs and exhaustive postmortems. Keep the exact attempted action, observed failure, governing TFW assumption, discriminating local observation, expected human benefit and a criterion for the fix. If dropping the counter-evidence could lead someone to count tokens twice or patch the wrong layer, retain it. Use only as much format as that result needs.

**Owner decision, 2026-11-19.** The reporting agent analyses existing evidence independently. A new paid run requires agreement from its own user. A supported cause, a targeted change in words and the check for accepting it complete the requested Issue. A diff is outside this deliverable.

**What could overturn the recommendation?** If agents on real installations cannot observe a native source or comparable counters, requiring a full local cause encourages confident guesses: favor a specific evidence request or an authorized isolated investigation. If local diagnosis usually uses only facts the maintainer already has, a simple template costs less. If one native observation changes the choice of fix while a template misses it, keep the on-demand diagnostic route. The examples are a qualitative design test, not a measured efficiency claim.
