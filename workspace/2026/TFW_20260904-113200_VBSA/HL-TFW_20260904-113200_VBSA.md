## 1. Vision 🔒 FROZEN

Every TFW phase declares the durable result that constitutes its delivered value, and the scope budget measures only the changes that create that result. Planning, execution, and review use one reproducible accounting contract, so mandatory traces, assurance work, and reproducible by-products can grow without changing the already measured delivery scope.

**Impact:** A phase is split or escalated because its delivered value became too large, not because TFW recorded, tested, or reviewed it. RF and REVIEW stop spending correction rounds on figures invalidated by the act of recording or checking those same figures.

> “Tell me how large the thing we are delivering became. Do not charge its receipt, tests, or audit trail back to the thing itself.”

The existing evidence also exposes two different questions hidden inside one number:

1. **How large is the delivered value?** This is the scope-budget question.
2. **How much material must be tested, evidenced, and reviewed?** This is an assurance-planning question and is already governed by evidence, review, and proportionality gates.

Treating the second as part of the first makes stronger assurance look like scope creep. Treating both as unlimited would be equally wrong. VBSA separates their governing mechanisms rather than creating a second numerical budget.

## 3. Target State (To-Be) 🔒 FROZEN

The governed object is a **value-bearing surface**, not an undifferentiated repository diff. Each changed file or declared path set has one semantic class:

| Class | Meaning | Spends the scope budget? |
|---|---|---:|
| `VALUE` | A durable artifact or product surface whose existence or change constitutes the accepted delivery | Yes |
| `ASSURANCE` | Ordinary tests, checks, fixtures, and temporary verification support | No by default; yes only when the assurance artifact is itself an accepted deliverable |
| `TRACE` | Task-local TFW state, lifecycle, research, handoff, result, evidence, and review records | Never |
| `DERIVED` | Mechanically reproducible output that is not independently accepted as the delivery | No; yes when that rendered or generated output is itself the accepted deliverable |

Semantic purpose outranks file type and location. A product prompt in this repository is `VALUE`; a prompt used only to generate evidence is not. A PDF requested by the recipient is `VALUE`; a disposable rendering used to inspect its source is `DERIVED`. A test suite requested as a conformance product is `VALUE`; ordinary regression tests written to assure another product are `ASSURANCE`. A result stored inside a task folder may be `VALUE`; the task folder alone cannot decide its class.

The budget result is derived from a fixed contract:

```text
budget result
  = diff(fixed baseline, fixed candidate)
  ∩ declared VALUE surface

TRACE additions after the candidate     ─┐
ASSURANCE additions                     ├─ do not change the result
reproducible DERIVED additions          ─┘
```

The contract names the baseline, candidate, classification/selector, metric definitions, and reproducing command. The Executor records that result once against the fixed candidate; the Reviewer re-runs the same method. A later `VALUE` change creates a new candidate and a new measurement. Merely writing RF, REVIEW, EV, status, journal, or research material cannot invalidate the figure.

### 3.1 Result Visualization

```text
BEFORE — the diff is treated as the budget

delivered work ──► RF count 57 / 4,463
                       │
                       ├─ REVIEW + traces ──► 69 / 5,517  ✗ old count is now false
                       │
                       └─ correction round ─► 78 / 6,065  ✗ correction grows the count again

AFTER — the declared value-bearing surface is the budget

TS: baseline B + VALUE selector S + metric rules
                    │
                    ▼
Executor candidate C ── measure diff(B,C) ∩ S ──► 7 files / 2 new / 648 touched LOC
                    │                                  │
                    ├─ RF / EV / status / journal      │ unchanged
                    └─ REVIEW / review-stage files     │ unchanged
                                                       ▼
Reviewer re-runs B + C + S ─────────────────────────► same result ✓
```

The stakeholder sees one answer to one question: how large the accepted delivery surface became. The receipt and the audit remain visible and mandatory, but cannot enlarge the answer they report.

## 4. Phases 🔒 FROZEN

### Phase A: Value-bearing budget contract and adoption 🔴

> **Requires:** Independent

**Deliverables:**

1. One canonical, domain-agnostic definition of the value-bearing surface and the four classification rules.
2. One measurement contract shared by planning, execution, evidence, and review: fixed baseline, fixed candidate, selector, metric definitions, and reproduction method.
3. Consistent role and template surfaces that cannot count task-local TFW traces or ordinary assurance work as delivered value.
4. Structural checks proving that trace-only changes do not alter a budget result, a `VALUE` change does, and every adapter consumes the same rule.
5. Backward-compatible treatment of existing projects and immutable histories; AFD, Helpdesk, and TFW are read-only research corpora, never migration targets.
6. A complete phase result in which canonical rules, active role consumers, adapter copies, verification, and update implications agree; no later synchronization phase is deferred.
7. A Project North Star principle placed in `NS2` immediately after **Purpose before activity**: **Subtraction before addition**, expressed by the owner's Antoine de Saint-Exupéry formulation, “Perfection is achieved not when there is nothing left to add, but when there is nothing left to remove.”

## 5. Definition of Done (DoD) 🔒 FROZEN

- ✅ 1. TFW defines one named budget subject: the declared **value-bearing surface** of a task or phase.
- ✅ 2. `VALUE`, `ASSURANCE`, `TRACE`, and `DERIVED` have non-overlapping default meanings, an explicit precedence rule, and examples covering code, prompts, documents, presentations, data, generated outputs, and tests.
- ✅ 3. Task-local HL, TS, ONB, RF, REVIEW, RES, status, journal, review-stage material, EV records, raw evidence, and logs are explicitly outside the scope budget and require no numerical shadow budget.
- ✅ 4. Ordinary tests and fixtures default to `ASSURANCE` and do not spend the scope budget; a test or conformance suite spends it only when the approved delivery itself names that suite as `VALUE`.
- ✅ 5. A file inside a task directory can still be `VALUE`, and a source file named like a TFW artifact can be `VALUE`; classification is never inferred from directory or extension alone.
- ✅ 6. All four existing file/new-file/modified-file/LOC measures are defined, but only meaningful measures apply to the `VALUE` subset: additions and deletions are reported separately; a rename is one logical changed artifact; binary or non-text `VALUE` participates in file counts with LOC = N/A, never zero; generated artifacts and cross-phase reuse have explicit treatment; no universal alternate-metric registry is introduced.
- ✅ 7. The accounting contract names a fixed baseline and fixed candidate, the declared selector/classification, and one reproducible method used unchanged by Executor and Reviewer.
- ✅ 8. Writing or appending any `TRACE`, `ASSURANCE`, or non-value `DERIVED` artifact after measurement cannot change the budget result; changing a `VALUE` artifact requires a newly identified candidate and recomputation.
- ✅ 9. Planning estimates, RF reporting, EV evidence, and REVIEW verification answer the same budget question and cannot introduce independent filters or competing totals.
- ✅ 10. Exclusion from the scope budget is explicitly not exclusion from implementation scope, evidence, review, quality, safety, compatibility, or proportionality checks.
- ✅ 11. Structural verification covers at least: trace-only growth, assurance-only growth, a test-as-product override, a deliverable inside a task folder, a generated final deliverable, and a true `VALUE` overrun.
- ✅ 12. Active adapters and configuration synchronization remain exact; no new configuration limit or standalone maintained artifact is introduced unless research proves an existing carrier cannot enforce the contract.
- ✅ 13. Existing tasks and their historical numbers remain untouched and readable. No file in AFD or Helpdesk is modified; their artifacts are cited only as observations.
- ✅ 14. The completed change remains within the configured budget as calculated by its own approved VBSA rule, and its RF publishes the reproducing basis rather than a mutable whole-tree total.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. Any mandatory TFW process artifact spends the delivery scope budget or can invalidate a previously correct budget result by being appended.
- ❌ 2. Tests are always counted or always excluded without the explicit test-as-deliverable override.
- ❌ 3. A folder-, filename-, or extension-only rule misclassifies a real deliverable or permits supporting product implementation to hide outside `VALUE`.
- ❌ 4. RF and REVIEW can use different baselines, candidates, selectors, metric definitions, or commands while claiming to verify the same figure.
- ❌ 5. The change replaces the current ambiguity with a second hard budget for trace or assurance volume.
- ❌ 6. “Not budget-bearing” is interpreted as “out of scope”, “optional”, “unreviewed”, or “unverified”.
- ❌ 7. LOC remains falsely universal for binary or non-text deliverables without a declared treatment that preserves a useful budget decision.
- ❌ 8. A new manifest, registry, script, field, or configuration key is added without a named reader and proof that an existing carrier cannot do the job.
- ❌ 9. The solution assumes software code is the value in every project or cannot express documents, presentations, prompts, data, or assurance products.
- ❌ 10. Any historical task artifact or any file in AFD or Helpdesk is rewritten, normalized, or corrected.

**On failure:** Stop before TS approval or return the implementation through the cited criterion. Do not repair a semantic accounting failure by raising the numerical ceiling.

## 7. Principles 🔒 FROZEN

1. **Name the governed object before measuring it** — the budget belongs to the accepted delivery surface, not to whatever a repository diff happens to contain.
2. **Semantic role over location** — purpose decides the class; paths provide selectors only after that decision exists.
3. **One measurement, one reference pair** — a figure without its baseline, candidate, and method is not an enforceable measurement.
4. **Trace integrity without trace taxation** — TFW traces remain mandatory and immutable, but never enlarge the value they record.
5. **Assurance is not product scope** — ordinary tests and evidence protect value through their own gates; they become budget-bearing only when they are the promised product.
6. **Structural enforcement** — every role consumes the same declared classification and reproduction method; prose agreement alone is insufficient.
7. **Domain-agnostic by construction** — code, documents, presentations, prompts, data, and other future delivery forms use the same semantic test.
8. **No shadow total** — an excluded class receives no second hard numerical budget that can recreate the same accounting loop.
9. **History is evidence** — previous tasks and external project traces are observed in place and never rewritten to fit the new rule.
10. **Subtraction before machinery** — prefer a rule in existing carriers and remove unstable totals; add an entity only when its unique job and reader are demonstrated.

## 10. RESEARCH Case 🟢 FREE

### Blind Spots

- Whether the four-class and LOC = N/A rules survive a completed document, presentation, image, or data delivery rather than predominantly code/text corpora.
- Whether logical VALUE-file count is a useful universal soft signal outside code repositories.
- Whether the six-condition Coordinator boundary rejects disguised new deliverables, late architectural expansion, cross-phase reuse, and retroactive discovery without escalating ordinary implementation learning.
- How existing carriers make every soft-trigger disposition observable without a new manifest or config key.
- Which named harms justify a task-local hard veto rather than a soft decomposition trigger, and how existing projects receive hard-to-soft forward semantics without rewriting history.

### Hypotheses

| # | Hypothesis | Status |
|---|---|---|
| H1 | `VALUE`, `ASSURANCE`, `TRACE`, and `DERIVED`, with semantic precedence for explicitly accepted deliverables, classify the observed TFW, Helpdesk, and AFD cases without contradiction | iteration 1: confirmed with accepted-output/necessary-constituent precedence and unresolved-as-VALUE; non-code replay pending |
| H2 | Ordinary tests can default to excluded `ASSURANCE` without weakening delivery quality because evidence, review, safety, and proportionality gates remain independently binding | iteration 1: conditionally confirmed; exclusion is arithmetic only and all assurance gates remain mandatory |
| H3 | Existing TS/RF/EV/review carriers can hold one deterministic selector and fixed baseline/candidate contract; no standalone budget manifest or new configuration key is necessary | iteration 1: confirmed; trigger-disposition enforcement pending |
| H4 | Hard upper scope budgets remain the right mechanism for decomposition and drift control; applying them to `VALUE` with delivery-appropriate metrics and bounded Coordinator authority is more effective than replacing hard ceilings with a softer or non-numeric structural control | iteration 1: refuted as stated; soft defaults plus reason-bound task-local hard constraints are the strongest survivor |
| H5 | Replaying the proposed rule against TFW RCFR, Helpdesk BIAI, and completed AFD phases yields one stable classification per corpus and removes the observed false overrun or self-reference without hiding genuine product growth | iteration 1: partially confirmed; RCFR stabilizes, AFD reproduces, and BIAI correctly remains a genuine growth signal |

### Risks of Not Researching

Without research, TFW may perfectly recalculate a hard-limit mechanism that no longer changes decisions. It may merely replace “count the whole diff” with an ambiguous label that agents can game, solve the current Markdown trace loop while remaining useless for presentations, binary documents, generated deliverables, or test products, and introduce a maintained manifest whose own drift recreates the problem.

### Proposed RESEARCH Focus

1. **Gather:** Reconstruct the exact budget subjects, baselines, candidate ranges, and disputed inclusions in TFW RCFR, Helpdesk BIAI, and representative completed AFD phases; inspect but never modify their traces.
2. **Extract:** Build a cross-domain classification matrix for product code, prompts, documents, presentations, data, ordinary tests, test products, TFW artifacts, evidence, logs, generated outputs, renames, deletions, binaries, and shared files.
3. **Challenge:** Try to game each classification, reproduce RF/REVIEW disagreement, and test whether an existing carrier plus fixed Git references is sufficient without a new artifact or configuration key.
4. **Redesign:** Treat hard budgets themselves as falsifiable. Compare hard ceilings, soft decomposition triggers, Coordinator-governed growth inside frozen outcomes, non-numeric structural controls, and removal of the mechanism against historical overruns and owner-waiver churn. Apply subtraction before addition: retain a control only if its unique value is evidenced.

**Iteration 2 focus:** replay non-code/binary delivery; attack the Coordinator authority boundary and hard-bound materiality; specify the minimal observable trigger disposition across existing carriers; and define forward compatibility without a new key or any historical rewrite.

### Why Not Just...?

- Why not exclude the entire task directory? — Some tasks place their accepted deliverable there, while this repository's product files may themselves look like TFW artifacts; location is not meaning.
- Why not exclude every test? — A conformance suite, evaluator, or test framework can itself be the promised product; the accepted-deliverable override is necessary.
- Why not keep two numerical budgets, product and process? — A process counter recreates the self-reference and makes required trace growth a new escalation path under another name.
- Why not freeze the whole-tree count immediately before RF? — Writing RF, review evidence, and lifecycle state still changes that count; a frozen snapshot makes the sentence historically true but does not make whole-tree size the right governed object.
- Why not let each project decide informally? — RF and REVIEW already show that two competent roles infer different subsets unless the decision has one durable carrier and one reproduction method.
