### G3 — Structurizr capability and extraction boundary

The [official product description](https://structurizr.com/) describes multiple software architecture views from one semantic model, authored with its DSL. This can reduce duplicate definitions across architecture diagrams; it is not evidence that the model matches every source or runtime path.

The [dynamic-view documentation](https://docs.structurizr.com/dsl/cookbook/dynamic-view/) specifies ordered relationship instances for a use case/story. This is a modeled scenario, not an execution trace. The [component-finder introduction](https://docs.structurizr.com/java/component/introduction) requires codebase knowledge and suitable identification rules, illustrated with Java/Spring. It explicitly rejects blind universal rules. No claim of automatic stack-independent architecture extraction or business-meaning recovery follows.

Documentation/ADR attachment is visible in the official documentation navigation but was not examined as a full content-management workflow here. Do not infer that attachment equals source ingestion, contradiction qualification or maintained topic synthesis. Those possible overlaps can be checked narrowly if an Extract choice depends on them.
