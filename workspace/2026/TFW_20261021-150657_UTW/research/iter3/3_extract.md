### E2 — Specimen 1: an incoming source with a consequential scope conflict

**Fictional service example, same facts in A–D.** Purpose: give operators a correct next step for an exceptional request. Existing accepted claim K1, grounded in policy S1, says that exceptional requests in branches North and South require supervisor approval. Incoming signed notice S2 says North may use self-service from Monday; South is unchanged. The notice's signer is identifiable, but their authority to amend S1 has not yet been established. No other source resolves the authority gap. The question is: **what can an operator do on Monday, and what decision is still missing?**

```text
BEFORE: S1 → accepted K1: North + South → supervisor approval
AFTER SOURCE ARRIVAL:
 S1 + accepted K1 remain preserved
 S2 → proposed exception: North from Monday → self-service
                 │
                 └─ amendment authority unverified → decision owed to policy owner
 South unchanged; North's operational change is not established by this specimen.
```

**Common reader-facing account after arrival:** “The accepted policy still requires supervisor approval in both branches. A new notice proposes North self-service from Monday; its amendment authority is unresolved. Do not present the proposed exception as accepted. South is outside the proposed change. The policy owner must resolve North's applicable rule; the unresolved matter remains visible to the responsible operator.” This is the same substantive content for every option, not a claim about an actual organization.

| Arrangement | Stored/derived material and reader entry | Actual update work proposed |
|---|---|---|
| A: current TFW | Retain S1/S2 identities and context; existing handover records the missing decision. A selected qualified record/relation carries disposition when warranted. The owning reference links to a concise account in the ordinary carrier. | Producer identifies affected claim; Coordinator/authorized qualifier routes the policy-owner decision, preserves scope and updates the existing reference. Reader follows existing source routes; no automatic topic page is presumed. |
| B: TFW + Structurizr | Same canonical material. A custom process view can distinguish “accepted approval route” from “proposed North exception”; attach the same account as documentation. | Same qualification work plus model meaning/layout and documentation import refresh. The model owner must not turn an unresolved edge into an accepted route. A second display does not answer the authority question. |
| C: selected wiki practices | Same canonical claims; a maintained “Exceptional requests” topic explains North/South and links S1, S2, K1 and the missing decision. A branch page may point to that one account instead of duplicating it. | An agent proposes affected-page changes; the existing accountable producer/qualifier checks meaning. After resolution, refresh the affected topic/links; retain prior source/disposition. The topic editor cannot accept the notice. |
| D: combination | Same topic as C; scoped process model/view as B; topic links to the exact model/view, which points back to the canonical disposition. | All required qualification plus coordinated topic/model refresh. One claim owner remains; no prose-to-model agreement is treated as independent confirmation. |

If authority is later verified by an actual policy-owner decision, only the affected North/effective-period claim receives the accepted successor. If authority is rejected, the proposal is retained with its rejection; no automatic “newest source wins.” These are alternative continuations, not invented outcomes. A and B can retain a concise synthesis through existing reference work; C/D differ by making multi-source topic upkeep a deliberate recurring responsibility. Whether that recurrence pays off is unknown.

**Strategic check:** replacing supervisor involvement may look faster. The stated purpose is a correct next step, not speed alone. Missing authority blocks calling this improvement accepted; even valid authority would not demonstrate better operator outcomes. No option's graph, link or activity log supplies that proof.

### E3 — Specimen 2: a changed documentation dependency

**Observed source structure, hypothetical change.** At the inspected repository epoch, `docs/scripts/gen_docs.py` selects static sources and workflow/template globs; `rewrite_markdown_links` rewrites mapped relative `.md` targets and carries fragments. It leaves an unmapped target unchanged. The generator is configured inside the documentation build; a separate deployment follows the build in the workflow. These are source/configuration facts from the prior stages, not successful execution observations.

Fictional change: a selected workflow page moves outside both the static mapping and those globs. A referring source link is updated to the new path; no alternate inclusion route is established. Responsible question: **does updating the link guarantee the guidance remains available on the built site?**

```text
BEFORE: selected source → mapped generated page → intended reader navigation
AFTER: moved source outside selection
       updated source link → unmapped target → unchanged by this rewriter
       page inclusion / rendered navigation / live availability: not established

Configured build boundary remains:
[selected sources → generator page inputs/navigation → site processing] → output
```

**Common reader-facing account:** “The source still exists, but this generator no longer selects it under the stated change. Updating the relative link does not add it to the mapping, and the rewriter leaves it unchanged. Check whether another inclusion path exists; repair the selected source or mapping within approval as needed, then inspect the affected built output. A successful build alone would not prove the intended guidance is reachable. Deployment and human use remain separate observations.”

| Arrangement | How the same account is exposed | What becomes stale and who repairs it |
|---|---|---|
| A | Existing change/decision account with the compact path above, linked to mapping and rewriter | Producer checks affected selection/link/output claim; existing review checks applicability. Unaffected pages need not be reconstructed. |
| B/E | Model identifies source selection, generator and site processing; selected dependency view plus attached same prose | Maintainer updates the semantic relation and any affected views/documentation. If the model omits selection details, it may stay unchanged while attached prose must change: correct abstraction is not necessarily staleness. |
| C | Maintained “How guidance reaches the site” topic connects source rules, navigation and the change decision | Topic owner updates only the affected account/links after checking source; current-looking prose without that check is stale meaning. |
| D | Topic supports why/limits; model supports selected relationships; both point to the same source epoch | Accountable maintainer reviews each affected representation, records what can remain valid and regenerates only useful views. More outputs do not mean more independent evidence. |

This specimen exposes a limit of “Structurizr alone is enough”: a model can carry the relationship and documentation can explain it, but someone still has to discover the source change and revise its meaning. It also exposes a limit of “a wiki is needed”: the common compact account already fits A, and B can display it without a topic-maintenance layer. Neither observation selects a winner without a real repeated-use need.

### E4 — One owner per meaning; several presentations are possible

| Layer | Authority and owner | Update/disagreement rule |
|---|---|---|
| Source S1/S2 or code/configuration revision | Original producer/source; preserved locator and scope | Source existence does not establish truth or permission; preserve conflicting evidence |
| Accepted claim/disposition | Existing TFW qualification/decision authority; actual policy owner in specimen 1 | Scope-bound acceptance/successor; unresolved conflicts name the missing decision |
| Topic/decision explanation | Named producer verifies an interpretation against accepted and unresolved grounds | Mark unresolved claims; update affected synthesis without silently replacing canonical authority |
| Semantic architecture/process model | Named model maintainer owns the abstraction; approval remains with the governing task | A model assertion is scoped interpretation unless independently observed; source/model mismatch requires a disposition |
| Diagram, imported document or export | Derived presentation of selected content | Rebuildable; rendering/validation success is not semantic currency or acceptance |

This arrangement is a proposed compatibility discipline, not a new mandatory registry. Existing records/handovers can carry the owners and references. For a single-use question, creating one useful account may be enough. For repeated topic questions, maintaining that account may avoid repeated reconstruction but adds review obligations. A model becomes useful when several views need the same meaningful elements/relations; a single adequate path may be cheaper.
