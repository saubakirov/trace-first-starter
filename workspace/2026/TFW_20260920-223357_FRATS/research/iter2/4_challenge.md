## Consistency Check

Pair checks apply when the alternatives are asserted as the same control. Several alternatives can
coexist as layers—for example, a task-local mandate plus OS enforcement—but one must not be used as
proof of the other.

**Incompatible pairs:**

| D1: traffic class | iterative design dialogue | D2: durable carrier | one writer-owned result artifact treated as the live dialogue channel | An artifact can consolidate the outcome, but repeated co-development is not made single-writer merely by editing one file. |
| D2: durable carrier | declared cross-role append | D3: identity layer | stable principal treated as sufficient writer authority | Attribution cannot authorize a foreign role to edit another role's artifact; the exception must be artifact- and field-specific. |
| D3: identity layer | mutable title or stable principal | D4: capability boundary | prose/mandate treated as technical least privilege | Name and mandate state who/what should act; neither constrains filesystem, tool, network or IAM access. |
| D5: contended resource | overlapping mutable paths | D6: lane mechanism | task-state scan treated as an exclusive lock | Two activations can observe the same free state. A scan can advise admission but cannot establish atomic exclusion. |
| D5: contended resource | saved branch/release state | D6: lane mechanism | `git worktree lock` or worktree count treated as landing serialization | Worktree administration is separate from shared refs, tags and release effects. |

**Eliminated configuration families:**

- **C3 as an ONB solution:** a new cross-role ONB append exception has no unique job once the
  Executor can record a sourced answer and authority-changing answers already route to TS/HL.
- **C4:** a new mandatory answer carrier plus maintained external scheduler adds two lifecycle
  systems without evidence that existing owned artifacts and a narrower landing control fail.
- **C7:** routine iterative dialogue plus a new carrier does not meet the no-dialogue happy path, and
  raw reduction cannot validate it. Dialogue remains available only for an explicitly selected
  workshop, not as the default control plane.
- **C11 as the default:** one repository-wide mutation lane is coherent and safe if honored, but the
  evidence does not justify blocking disjoint worktree mutation. It survives only as an emergency or
  project-chosen conservative mode, not H14's universal default.

**Unexpected survivors:**

- **C9:** the same role can preserve a bounded authoritative answer without claiming to originate
  it, provided source, epoch, governing baseline and consequence are explicit.
- **C12:** disjoint work can remain parallel while the shared target branch/release effect is
  serialized; worktree count is irrelevant to the admission decision.
- **C8:** an optional stable LEAD principal survives elimination, but only for reusable attribution
  continuity and only when the owner explicitly selects it.

## Findings

### C1: Six-edge replay eliminates concealed authorship and silent authority changes

| Case | Activation | Authority | Evidence | Recovery | Continuation | Exception result |
|------|------------|-----------|----------|----------|--------------|------------------|
| ordinary happy path | Coordinator/LEAD dispatches exact role/unit | HL/TS and mandate bound the unit | writer returns RES/RF/REVIEW | status, journal, lineage and Git identify current gate | durable result names the next trigger | no question or dialogue required |
| factual ONB blocker | one bounded question is sent to the authority source | answer must not widen TS/HL | Executor records answer, answerer, time/epoch, governing TS/HL ref and operational effect | resumed Executor reads ONB and baseline | work resumes only after the recorded answer | sourced transcription passes; unlabeled Coordinator editing does not |
| answer changes scope/acceptance/architecture | Executor remains blocked | accountable owner/Coordinator must amend HL or issue a TS revision | ONB links the authoritative revision; it does not restate it as local authority | superseded baseline remains immutable | new activation names the revised baseline | silent continuation on a chat answer fails |
| implementation evidence fails | Reviewer receives RF/evidence | Reviewer proposes; Coordinator rules within the declared REVIEW exception | failed evidence and proposed correction remain in REVIEW/RF | revision lineage preserves both attempts | REVISE returns to the same Executor; new Reviewer is not invented | repeated design chat is unnecessary |
| holder unavailable or task interrupted | Coordinator activates a replacement/resumed unit | ownership change is human-rooted and role-bounded | journal records dispatch/ownership change; prior artifacts remain | new unit reconstructs current state without private chat | exact next role and pending gate remain visible | a personal inbox as sole state fails |
| frozen baseline must change | blocker routes to the amendment owner | HL §12 and TS revision carry the decision | proposal, ruling and resulting baseline are linked | old frozen bytes remain addressable | work resumes only against the approved revision | local artifact edit cannot substitute for amendment |
| stale answer after baseline movement | task is reactivated against a newer baseline | prior answer is scoped to its recorded epoch/ref | ONB exposes the mismatch | reader detects that the answer predates governing TS/HL | revalidation or new bounded question is required | unsourced transcription fails |
| record recovery/dispute | recovery starts from task state and immutable lineage | authority is reconstructed from owner/mandate/ruling, not title | source refs and epochs distinguish observation from inference | Git and role artifacts survive lost chat/session | one valid next activation or escalation remains | new generic answer file adds no recovery fact |

The literal current ONB template fails because “Coordinator fills in” permits concealed cross-role
authorship under current Role Lock. Unsourced Executor transcription fails because a later reader
cannot tell whether the wording is authoritative or stale. A factual answer that silently changes
scope fails authority and recovery. A new answer carrier fails the unique-job test because it would
duplicate answer, source, epoch and consequence already representable in the writer-owned ONB while
adding another reader and lifecycle.

The surviving configuration is consequence-sensitive rather than writer-convenient: the Executor
records a bounded factual answer in its ONB with exact provenance; any change to scope, acceptance,
architecture or reserved authority is carried by the existing Coordinator/human-owned HL/TS route.
The live REVIEW append remains a separate explicit exception because it carries a Coordinator ruling
on a Reviewer proposal and already has a unique lifecycle job.

This supports H6 without claiming that no template/rule change is needed: the existing artifact
classes suffice, while their ownership/emission contract needs correction.

### C2: The named principal survives only an opt-in cross-unit attribution test

**Elimination attempt:** remove the stable agent principal and use only task/thread ID, human-facing
task title, parent, role, scope, human owner, `via`, dispatch and mandate.

That set is sufficient for one owner-launched operational unit and for resuming the same task. It
also preserves authority more safely than inferring it from a name. A mandatory principal for every
Researcher, Executor or Reviewer is therefore eliminated.

**Counterexample:** the owner explicitly selects the same declared LEAD participant across distinct
root sessions or replacement root units. Task/unit history proves that the units differ; provider
`via` proves only which product was used. Neither says whether the owner deliberately attributed both
root units to the same stable project participant. The durable fact is:

> these distinct units were intentionally operated as the same declared LEAD principal under
> separately bounded task-local mandates.

The material readers and consequences are limited but real:

| Reader | Consequence of preserving the fact | Consequence of omitting or overextending it |
|--------|------------------------------------|---------------------------------------------|
| accountable human selecting/resuming a LEAD | can address and audit continuity of the chosen project participant across units | must reconstruct continuity informally from provider/session names |
| Coordinator auditing delegation lineage | can distinguish an explicitly selected LEAD from generic sessions using the same provider | provider identity may be mistaken for one shared actor |
| later provenance reader | can attribute recommendations/delegations to the declared participant while retaining each exact unit | merging units or inferring authority from the profile corrupts provenance |

The principal therefore survives only as opt-in reusable attribution continuity. It remains
ergonomic on a shared host and provenance-bearing across selected LEAD units, not authentication,
approval, mandate, capability or human identity. Every unit still needs its own address, parent,
role, scope, channel and dispatch; every LEAD task still needs an owner-approved mandate. If no
reader needs cross-unit continuity, task/unit history is sufficient and the stable principal is
omitted.

This supports a narrow H12/H13 and preserves H11: owner-launched non-AT operation does not invent a
principal, while an explicitly selected persistent LEAD may use one for a unique durable fact.

### C3: L1–L3 do not survive the same concurrency attacks

| Attack | L1: serialize all repository mutation | L2: serialize overlapping resources | L3: serialize landing/release effect |
|--------|---------------------------------------|-------------------------------------|--------------------------------------|
| disjoint worktree edits | prevents conflict but blocks safe parallel work without evidence of shared invalidation | admits if scope sets are accurate | admits; any latent semantic interaction is caught at landing/current-baseline replay |
| same-path or coupled semantic edits | prevents concurrent start if every actor honors the lane | prevents only if overlap/coupling is declared before activation | permits divergent candidates; merge/review may reject one at landing |
| stale candidate after target branch moves | still needs current-baseline replay; exclusive mutation does not make old evidence current | same | central case: landing owner rebases/merges and reruns bounded integration evidence |
| abandoned holder | stalls every mutating task until human release/reassignment | stalls only claimed resources, but stale claims need expiry/recovery | stalls landing/release only; worktrees and read-only analysis can continue |
| human emergency override | requires explicit preemption and audit; otherwise process and human state diverge | same per resource | human landing/release authority can preempt, record disposition and preserve candidate history |
| two landing attempts race | prevented only if the procedural lane also owns the target ref | path claims alone do not fence branch movement | this is the resource L3 explicitly serializes |
| tag/deploy/release race | prevented only if included in “all mutation” and honored outside Git | not reliably covered by path claims | covered only when release target/environment is an explicit serialized resource with actual service/IAM enforcement |
| offline or non-participating writer | procedural rule can be bypassed | repo-local claim can be bypassed and a scan can race | target-branch protection/landing authority can reject unauthorized integration, while candidate work remains recoverable |

L1 is safer than uncontrolled mutation but is not supported as the default because its exclusion
scope exceeds the demonstrated shared resource. L2 is useful as activation-time risk reduction, yet
exact paths can expand and semantic coupling can cross declared paths; a repository-local claim also
becomes new shared mutable state with stale-owner recovery. L3 addresses the first conclusively
shared resource—target ref, release metadata/tag and external effect—while retaining worktree
parallelism.

The surviving architecture is a layered C12/L3 family:

1. read-only work remains parallel;
2. each mutating unit uses an isolated worktree, exact scope and producer-attributed candidate;
3. Coordinator/selected LEAD compares declared scopes before activation and avoids known overlaps,
   but that scan is advisory rather than a lock;
4. one landing owner at a time integrates into each target branch and runs current-baseline bounded
   evidence;
5. release/tag/deployment is separately serialized per target/environment and technically enforced
   where the platform exposes branch/IAM/service controls;
6. stale or abandoned candidates remain recoverable and may be reconciled, rejected or superseded
   without blocking independent work.

No new file lease or maintained global scheduler is justified by current evidence. A purely
procedural landing owner does not fence external actors; where exclusive enforcement matters, the
actual shared target must enforce it. This narrows H14: the supported default is one active
**landing/release effect per shared target**, not one active mutating worktree per repository. H15
survives because resource ownership—not agent/task identity—must bind the shared target.

### C6: H7 survives structurally but not as an unattended reliability claim

A selected LEAD can receive direct unit returns, activate the next unit and keep the owner out of
mechanical relay. The six-edge replay still requires:

- human-reserved decisions and amendments remain human-rooted;
- Reviewer remains an independently addressable unit and does not inherit Executor authority;
- unavailable LEAD state is recoverable from status, journal and artifacts;
- the LEAD's principal, if selected, does not merge Coordinator/Researcher/Executor/Reviewer units;
- landing/release authority is explicit and separately enforced where required.

This supports H7 as an interaction architecture. It does not prove provider reliability, autonomous
availability or G8-grade operation because no all-eight native trial was run.
