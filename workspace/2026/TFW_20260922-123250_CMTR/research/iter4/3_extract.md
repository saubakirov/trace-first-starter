## Findings

### E1 — Four claim levels require progressively stronger evidence

| Level | Claim | Minimum evidence | Current iteration-4 reach |
|---|---|---|---|
| L1 — Intended | The Coordinator requested pair X for launch Y | Durable exact creation arguments and rationale | reached: Sol + high recorded |
| L2 — Applied | Pair X actually governed the run | Provider-native resolved/effective model and effort after fallback, substitution, or policy | not reached: current Codex task return exposes neither field |
| L3 — Sufficient | Pair X cleared the quality floor for Y | Predeclared work oracle, accepted result, and material rework record with competing causes considered | not yet reached: iteration 4 is incomplete and its acceptance oracle was not declared as a model evaluation |
| L4 — Minimum sufficient | No lower-resource feasible pair clears the same floor at lower completed-task cost | Equivalent-work comparison against at least the adjacent lower candidate, with effective settings, outcome, rework, and cost per successful task | not reached: Sol + medium is counterfactual and no trial is authorized |

Delivery is orthogonal: a pair can be requested and the task delivered while L2 remains unknown. An accepted result can support L3 only for its exact work and predeclared oracle; it cannot skip to L4. This is the operational consequence of Gather's five evidence layers and project decisions D59/D78.

### E2 — The smallest prospective test of “minimum” is adjacent-effort, same-work, and predeclared

Configuration C5 isolates the disputed boundary with the fewest moving parts:

1. Freeze one bounded work packet: exact committed sources, prompt, authority, exclusions, tool access, and required deliverable.
2. Before either result, declare the outcome oracle: frozen-HL alignment, material factual/evidence errors, scope/authority breaches, unresolved contradictions, and material rework required for acceptance.
3. Launch two separate visible tasks on the same current Codex surface, differing only in Sol `high` versus Sol `medium`; preserve task order and context differences if true equality is impossible.
4. Record all five evidence layers. If effective settings remain unavailable, the test can compare requested configurations and outcomes but cannot claim applied-pair causality.
5. Use an independent assessment against the predeclared oracle. Count a correction only when it changes a material claim or acceptance state; do not use artifact count, prose length, or number of gates as quality.
6. Compare task success, latency/usage where exposed, and total material rework. The economic unit is cost per accepted result, including failed attempts and rework.

This is a prospective Phase C input, not an authorized pilot. It adds no permanent test or new core artifact; the existing dispatch, return, and review traces can carry the fields.

OpenAI's current deployment checklist independently supports the shape: preserve workload role and effective effort for the first comparison, run representative evaluations, compare task success/latency/token classes/cost per successful task, and compare GPT-5.6 with one effort level lower. It says lower effort is faster and uses fewer reasoning tokens, while `medium` or `high` can both fit work that diagnoses or compares options. That makes Sol + medium a legitimate adjacent candidate, not evidence that it would pass.

### E3 — The four quality factors need a decision boundary, not just a list

Applied to iteration 4, the factors point in opposing directions:

| Factor | Evidence pulling upward | Evidence pulling downward |
|---|---|---|
| Uncertainty / novelty | Independent adversarial attack and subtle causal/evidence boundaries | One completed RES, four exact questions, and a frozen HL constrain discovery |
| Dependency breadth | Claims span Codex, Antigravity, Claude, research policy, and prospective Phase C | No code, shared workflow, status, HL, provider pilot, or implementation mutation is allowed |
| Oracle strength | No automatic grader can establish judgment quality or minimum sufficiency | Coordinator gates, frozen DoD/DoF, durable sources, provider docs, and an independent later review are available |
| Consequence / reversibility | A mistaken policy could guide later role launches | This unit writes only reversible research artifacts; Coordinator retains acceptance and Phase C decisions |

Three non-contradictory threshold shapes remain in the configuration space:

- **Max-risk:** any high uncertainty, weak oracle, or high consequence raises the pair regardless of compensating factors.
- **Compensating:** strong oracle and reversibility can offset uncertainty or breadth; the rationale must state which factor changes the boundary.
- **Evidence-first escalation:** start at the lowest plausible pair allowed by consequence, then raise only after a named oracle failure; include failed-attempt cost.

Iteration 3's compact contract names the factors but does not choose among these threshold shapes. Consequently, both Sol + high and Sol + medium can be rationalized from the same facts. The rule currently disciplines vocabulary better than it discriminates the adjacent effort choice.

### E5 — Phase C falsification contract

| Claim under test | Required precondition | Falsifying observation | Inconclusive observation | Next-choice implication |
|---|---|---|---|---|
| The rationale discriminates the chosen pair | exact task plus adjacent lower candidate named before launch | the rationale cannot name a predicted material failure unique to the lower candidate, or applies identically to both | fluent reasons written only after seeing the result | keep the choice provisional; require a threshold or trial |
| The requested pair was applied | native resolved/effective readback is available for that surface | readback names another model/effort, substitution, clamp, or fallback | surface exposes only requested arguments | correct binding/readback; do not blame outcome on requested pair |
| The selected pair is sufficient | predeclared oracle and exact work packet | material acceptance failure attributable after context/tool/source causes are excluded | completion, style differences, or bounded corrections below the oracle | raise only for the failure type that occurred |
| The selected pair is minimum sufficient | equivalent-work adjacent-lower result and completed-task economy | lower pair clears the same oracle with no greater material rework and lower measured cost | different tasks, no effective settings, or incomparable context/order | no minimum claim; retain provisional candidate |
| A provider mode is launch-ready | current roster/selector, separate visible unit, exact addressed return, required readback | any required component is unavailable or silently changes the choice without detection | documentation/help without account/run evidence | bound claim to candidate mechanics or owner-assisted unknown |

The selection rule survives a failed lower candidate only if the failure was predicted by the quality-floor rationale and other causes were controlled. It is falsified as a *minimum* claim by a lower candidate that passes the same oracle at lower completed-task cost. A single successful selected launch cannot falsify or confirm minimum status.

### E6 — Economy has three separate orderings

1. **Published token-price ordering:** external API prices rank models for those API tokens.
2. **Requested reasoning ordering:** official guidance says lower GPT-5.6 effort generally uses fewer reasoning tokens and less latency.
3. **Completed-result ordering:** total cost includes input/output/reasoning/tool usage, retries, failed attempts, review, and material rework on the actual product surface.

Only the first two make Sol + medium plausibly cheaper. CMTR needs the third to claim “least-resource sufficient.” Codex Desktop quota conversion and effective reasoning usage are unavailable, so Phase B must not translate API price ratios into Desktop savings percentages.
