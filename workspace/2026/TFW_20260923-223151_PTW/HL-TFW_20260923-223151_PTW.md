## 1. Vision 🔒 FROZEN

The same Trace-First Workflow ideas serve an ordinary bounded Task. A clear human request authorizes work within its stated Boundaries: `tfw-daily-task` inspects the receiving project's governing rules, current sources and relevant earlier work, tests the intended result against the Project North Star, then executes, checks and leaves a selected Trace in one run. The worker uses the Coordinator's strategic judgment internally, including Working Backwards and reasoned critique, without imposing a second HL approval exchange on every small request. The person retains purpose, legitimate authority, acceptance and responsibility throughout. A discussion-led medium route with an owner-visible HL belongs to separate future work.

**Impact:** The owner gives one bounded request and receives a useful checked result without a ritual pause. Another authorized participant can later see why the work existed, who requested and performed it, what sources and earlier work mattered, what was produced and checked, and who owns the next decision. The user encounters the same TFW meanings taught through the philosophy, essay and SenseLab.

> **Imagined stakeholder quote, not testimony:** “I asked for the repair once. The agent found the project's current rules and earlier patch, made the change, checked it, and left enough context for my colleague.”

## 3. Target State (To-Be) 🔒 FROZEN

The deliverable is a portable, optional `tfw-daily-task` skill for a bounded one-worker request. Retain the proven SenseLab name as the proposed invocation; check any cadence ambiguity under `Naming Creates Behavior`. Its first receiving contexts are Full projects, but `daily/` stays outside their formal task corpus. For a new project, the proposed default is an immutable `daily/YYYY/YYYYMMDD-HHMMSS_slug/` folder with one compact `task.md` created from the Daily-owned `.tfw/extensions/daily-task/templates/task.md`; the existing SenseLab three-file record stays valid and unmigrated. The skill's semantic instructions and its own template are distinct from Full's HL/RF templates. One provider-independent semantic source and explicit opt-in entry points are required. Packaging must not silently enlarge Full's exact ten-command role set or make a provider copy a second source of truth; its precise install/update mechanics remain a decision-changing research hypothesis.

|---|---|
| Working Backwards and North Star | Internally describe the recognizable finished result and test its Goal and Value against the receiving project's governing North Star and relevant Values before changing anything. Show a preview to the owner only when the request itself asks for options or an unresolved consequential choice prevents work. |
| Goal and Value | State what should change and for whom before choosing files or actions. Use the result-first questions already present in HL and Assisted planning. |
| Question, Context and Boundaries | Resolve uncertainty from project instructions, current object sources and relevant earlier Tasks before interrupting the owner. Treat a past Task as history, not current authority. Name what the request permits, who accepts the result, and which act must stop if essential information or authority is absent. |
| Human authority and execution | The clear bounded request itself permits the corresponding work; do not require a separate HL, brief approval or general questionnaire. Perform independent authorized work even if one effect is blocked. A materially changed goal, external effect or missing legitimate authority is not inferred from silence. Formal Full approval applies only inside a formal Full Task. |
| Task and role | One bounded piece of work has a human accountable for purpose and an actual named worker. A working unit, model, profile or session title is never a grant of authority. |
| Trace | Preserve selected material words of the human with their author and source, material decisions, result or actual state, verification and the continuation point. Existing project identity rules apply; absence of a profile never authorizes an invented identity. |
| Evidence and acceptance | Check the claim that matters in the real task; report what was observed and what remains uncertain. Prepared, checked, accepted and released are not interchangeable claims. |
| Continuation | End with an accepted close or the exact next human/agent decision. Preserve earlier material meaning when it changes, using ordinary file history or a justified version. |

The working sequence is: interpret the human request → pass a **context gate** by inspecting governing project instructions, current object sources and relevant earlier work → pass a **boundary gate** by checking North Star/Values, formal-task ownership and authorization → record minimal Goal/Value/Context/Boundaries → act without a second approval exchange → check the actual result → leave selected Trace and close or name the authoritative next step. These are internal checks, not user-facing forms. A no-match search is recorded as such; it is not fabricated context. If a consequential fact or authority cannot be established, stop only the dependent action and report its exact blocker. No broad question sequence is a prerequisite for routine work.

There is no automatic file collision between SenseLab's `daily/` and Full's `workspace/`: the local Daily README explicitly keeps its records outside the formal Full lifecycle. There is, however, a scope ambiguity to resolve upstream: `.tfw/conventions.md` §13 says “Every task” produces RF, `status.md` and journal without qualifying which kind of task, and other artifact rules likewise say “every task directory.” The portable design must explicitly distinguish a local `daily/` record from a formal Full task in the applicable canonical rules. The substantive incompatibility arises if one labels a one-worker Task as formal Full while omitting its mandatory artifacts or independent REVIEW, or lets the Full Coordinator write implementation. Using the same HL thinking and presentation does not itself claim Full authority. Consequence and uncertainty determine whether stronger Evidence or independent review is needed.

The proposed greenfield record is `daily/YYYY/YYYYMMDD-HHMMSS_slug/task.md`, following SenseLab's date partition. Its stable ID is the folder name, independent of category and local status; collisions get a suffix, and existing folders are never moved to conform. A **Daily-owned template** at `.tfw/extensions/daily-task/templates/task.md` supplies the form for new records only. Its five compact parts are: (1) source and actual human/worker attribution; (2) Goal, Value, Boundaries and observed completion condition; (3) material Context including governing project source, current object, relevant predecessor or honest no-match, and North Star fit; (4) result, material decisions, proportionate check and limits; (5) authoritative Next or close. Exact source-linked human excerpts are kept only where material. Material changes append a dated reason or retain ordinary Git history; no old meaning is silently overwritten. One file is the minimum usable Trace, not a ban on task-local supporting files when a substantial revision or Evidence needs them. Work products live at their ordinary product paths. There is no mandatory HL, RF, `status.md`, journal or new `knowledge.md` in this local record. SenseLab/helpdesk retain their paths and local file split; project rules may require that split for future work. A new project's one-file default and the field triad must be compared for continuation quality and context cost rather than by file count. Where title write/readback exists, `DAILY · <exact folder ID>` is navigation only; it does not create an application task or authority.

| Packaging option | Immediate advantage | Structural cost | Direction |
|---|---|---|---|
| Add Daily as an eleventh Full manifest command | Reuses current command installer. | Changes the fixed role-command contract and its init/update/receiver checks; Daily is not a Full role. | Do not presume this integration. |

The date-only partition, immutable identifier and exact links make the archive stable even if subjects or teams change. This addresses the old `tasks/` migration lesson directly: no category path encodes mutable meaning, no global counter or board owns Daily state, and installation does not move historical tasks. A new `daily/README.md` is not required: the skill and its own template state the generic contract; existing project instructions govern local identity, authority and file rules. SenseLab's already existing README remains in place, without becoming a universal template or an update target.

For a new request, identify the object and intended result, make one bounded search for relevant current product sources and recent Daily records, and inspect only convincing matches. Continue the same record when the request revises the same bounded deliverable; create a new record when it has a separately accepted result, owner or Boundaries. In the new `task.md`, add exact `Related` links only when they affect the work. The old closed Task need not be edited merely to add a backlink; an exact-ID search can find incoming relations later. Do not reclassify or move old folders, create a mandatory category, maintain a shared journal, or treat textual similarity as evidence that an old rule is still valid. A current product document may serve as the shared reference when repeated work concerns that product.

| Organization choice | Benefit | Cost or failure mode | Decision |
|---|---|---|---|
| Flat yearly Task folders, no relations | No maintenance beyond each Task. | The next worker may repeat discovery or miss a useful earlier result. | Baseline, insufficient for the owner's recurring-work case. |
| Mandatory subject subfolders such as `daily/design/stickers/` | Nearby folders are visible in a file browser. | Compound tasks fit several categories; taxonomy and moved links need maintenance. | Do not require. |
| One long-running folder for a type of work | One apparent place to read. | Independent requests, owners, approvals and closures blur; the file grows and shared writes collide. | Use only for continuing the same deliverable, not a whole category. |
| Separate Tasks plus a maintained category journal | Each result retains its own authority and the category has an index. | An extra write after every Task; the journal can drift or conflict under several workers. | Defer unless a measured navigation failure warrants it. |
| **Separate Tasks, bounded search, exact links and current product sources** | Prior decisions are findable, while durable rules stay next to the object they govern. | The worker must judge relevance, currentness and authority of a match. | **Recommended default.** |
| Generated read-only category view | Browsable grouping without another source of truth. | Tooling and update cost; misleading if labels or links are wrong. | Optional later, only after real search failures. |

Knowledge follows the same materiality rule. Task-local decisions and observations remain in that Task. Neither a new `knowledge.md` in every Daily folder nor automatic promotion on repetition is required. Repetition can corroborate or reveal a conflict; it does not itself prove currentness or grant publication authority.

### 3.2 Value Flow

`human bounded request → mandatory project/current-source/related-work check → Working Backwards + North Star/Boundaries check → one worker acts without a second approval exchange → actual result + proportionate Evidence → selected Trace with exact relations where useful → human acceptance or authoritative continuation`.

At each arrow, the record preserves only the information needed to understand purpose, inspect the result, or make the next legitimate decision. Material reusable findings may later enter an existing product reference or qualified TFW knowledge; this is an explicit decision, not an automatic output of every Task.

## 5. Definition of Done (DoD) 🔒 FROZEN

- ✅ 1. The skill uses Working Backwards, a substantive North Star and Project Values check, reasoned critique, consequential Questions and the Saint-Exupéry Gate internally. A clear bounded request runs to a useful result without a second approval exchange or mandatory owner-visible HL.
- ✅ 2. One authorized worker completes a bounded Task and leaves a usable result and selected Trace: Goal, Value, material Question/Context/Boundaries, actual human source and worker, relevant current/prior sources, material decisions, Evidence, state and authoritative continuation or close. The dedicated Daily template can produce a new project's `daily/.../task.md`; an existing project's working split remains valid. Product files stay at ordinary paths.
- ✅ 3. The default `daily/` record is explicitly outside the formal Full task corpus, and the canonical rules state that boundary where “every task” could otherwise include it. The skill checks the receiving project's storage rules, preserves existing SenseLab/helpdesk records and never aliases local completion to a formal Full verdict. An active formal Full task remains governed by its existing role and artifact contract.
- ✅ 4. An observable pre-action gate records inspection of governing rules, current object sources and a bounded search for materially similar work or an honest no-match; it checks the request's authority and formal-task ownership. A missing essential fact blocks only its dependent action. Material scope changes return to the human, while a formal Task or material risk invokes its governing route and proportionate assurance.
- ✅ 5. One canonical portable skill source, one dedicated Daily `task.md` template, verified opt-in Codex and Claude entry points, and bounded examples work in at least two project contexts without SenseLab identities or content, a required service, an extra `daily/README.md`, a second semantic source, or an eleventh Full role command. The Daily template changes no Full HL/RF template and never rewrites an existing task. Where supported, the title is `DAILY · <exact folder ID>` for navigation only.
- ✅ 6. A repeat request finds relevant current product material and selected earlier Tasks through a bounded search, reuses them only after checking scope/currentness/authority, and records exact relations when they change the work. Independent outcomes retain independent Tasks; no mandatory category folder or shared journal is created, and SenseLab's functioning three-file local record is not replaced by installation.
- ✅ 7. A Daily Task can retain a material Fact Candidate with source and uncertainty, while durable project rules follow the existing authorized documentation or knowledge route. No automatic `knowledge.md` or publication duty is added to every Task.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. New labels, statuses, document roles or a different user ritual duplicate Goal, Value, Task, Trace, Evidence, acceptance or the existing edition's authority model; a small Task skips Working Backwards, North Star or consequential doubt, or adds a compulsory HL approval conversation.
- ❌ 2. A `daily/` record claims formal Full lifecycle authority, omits mandatory Full artifacts after entering that lifecycle, or one worker crosses an active Full Role Lock.
- ❌ 3. A title, profile, thread address, chat wording or urgency is treated as authority for scope, release, publication or communication.
- ❌ 4. Source text is fabricated, a material contrary instruction is omitted without disclosure, or secret material is copied into a shared Trace.
- ❌ 5. A consequence-bearing change is waved through because it is called Daily or touches few files; necessary verification, review or a reserved human decision is skipped.
- ❌ 6. Every small Task must choose a category, edit a shared journal, create a knowledge record or scan the whole archive; an old related Task is treated as current authority without checking its product source and scope.
- ❌ 7. The worker edits before inspecting applicable project rules and current object sources, or declares a context gate passed based on a guessed source or uninspected past Task.
- ❌ 8. Editing the Daily template silently changes Full artifact templates, rewrites an existing Daily record, or overwrites a receiving project's selected local record form during update.

**On failure:** retain the actual source and state, stop the affected action, name the missing authority or assurance, and route to the governing project workflow or human owner. Do not reclassify a formal task silently.

## 7. Principles 🔒 FROZEN

1. **Purpose before activity** — state Goal and Value before optimizing a Task; registration without a useful result is failure.
2. **Working Backwards and Questions before premature answers** — test the finished result against the North Star, resolve uncertainty from current sources first, and challenge a weak premise with reasons; interrupt the owner only for an actual blocked decision.
3. **Selected Trace, not transcript** — preserve material human source, context, decisions, actual state, result and continuation without elevating chat chronology to authority.
4. **Human authority, bounded delegation** — distinguish accountable person, actual worker and acceptance authority; name the Boundaries and stop condition.
5. **Continuation over isolated output** — leave a usable result and enough Trace for another authorized participant to continue.
6. **Assurance proportional to risk** — choose checks, Evidence and independent review for the consequence; the human request grants only the work within its Boundaries.
7. **Naming Creates Behavior and Portability** — prefer the method's existing terms and ordinary project files; any proposed new name must cue the same action across providers and editions.
8. **The Saint-Exupéry Principle for related work** — add a link or shared reference only when it changes a future decision; keep task history separate from current product truth and qualified knowledge.

- The proposed Daily-owned template must be checked for adequate Goal/Value/Context/Boundaries, source, result and continuation without reproducing a formal HL or Full state machinery. The field triad remains valid. Verify that an accepted template update applies only to new records and preserves project-selected local forms.
- The owner's recurring-work request raises a distinct question: what level of prior-task search and exact linking improves a new result enough to repay context cost? Test a design series, a repeat bug and a letter/proposal case. A shared current product source exists for SenseLab stickers; a comparable source may be absent or confidential elsewhere.
- The owner resolved the major speed trade: Daily is one-shot, without a fresh brief/HL approval exchange for a clear request. Test whether the context and boundary gates can remain internal and bounded on real small cases; an essential missing authority may still stop its dependent act.
- A greenfield one-file record may reduce files but can mix the human request, evolving results and source excerpts; compare it with the existing SenseLab three-file split before claiming lower token or maintenance cost.
- No independent cross-provider trial of a generic candidate has been observed; SenseLab's successful local use does not establish that claim.

### Risks of Not Researching

Copying the field skill verbatim would make SenseLab's profile system and complete message log appear universal. A false Full HL claim would confuse authority. A mandatory category/journal/knowledge layer or second approval exchange would impose recurring cost on every small request. Source comparison establishes the one-shot conceptual correction; exact context-gate cost, record split and optional installation compatibility remain decision-changing research questions.

### Proposed RESEARCH Focus

After HL review, render representative small repair and non-code Tasks from a dedicated Daily template with the internal context/boundary gate, then measure whether Working Backwards, North Star, critique and follow-through survive without an owner-visible HL approval step. Compare the one-file greenfield record with SenseLab's working triad for continuation and context cost. Audit unqualified Full task clauses and scope them precisely; route active formal Full tasks through their governing workflow. Compare bounded related-work discovery and exact task/product links with category folders, a rolling folder, maintained journal and generated view on sticker, letter/proposal and bug cases. Test currentness and the separation between a task-local Fact Candidate and published knowledge. Verify the `tfw-daily-task` name, optional package placement, template isolation, opt-in Codex/Claude entries and update behavior without altering Full's role command set or requiring a new `daily/README.md`. Use Light and Assisted as sources of existing meaning, not presumed installation targets.

### Why Not Just...?

- Copy the SenseLab skill to every project? It preserves a useful local implementation, but its project-specific identity and complete-message duties would become false universal rules.
- Install TFW Light wholesale into a Full project? Light's Trace and work cycle are relevant; replacing a project's installed edition or introducing another root state model is a different act.
- Send every small task through the formal Full lifecycle? It preserves formal assurance but spends separate-role and evidence costs even when a direct bounded check is sufficient.
- Put every design/letter/bug task in a named subject subtree? A compound Task fits several subjects; categories and moved paths become another maintained contract.
- Keep one permanent journal per subject? It repeats task-local decisions and gives several workers a shared mutable file; the stable part of the work may already belong in an existing product document.
- Create a knowledge record for each Daily Task? Most observations are local or unverified; existing qualification separates preserved candidates from accepted project knowledge.
