## 1. Vision 🔒 FROZEN

The same Trace-First Workflow ideas serve an ordinary bounded Task. Before execution, the agent works with the Strategic Architect mindset of the Coordinator: works backwards from the finished result, checks the Project North Star, asks consequential questions and challenges weak assumptions with reasons. The human sees and approves a proportionate plan in the familiar HL form. Within that approved bound and where the project's rules permit one worker, the agent then produces the result, checks it and leaves a selected Trace. The person retains purpose, legitimate authority, acceptance and responsibility throughout.

**Impact:** The owner can judge the intended result before work starts, and another authorized participant can later see why the work existed, who requested and performed it, what was decided and produced, what was actually checked, and who owns the next decision. The user encounters the same TFW meanings taught through the philosophy, essay and SenseLab.

> **Imagined stakeholder quote, not testimony:** “This is the same TFW I learned: the goal and value are clear, the result is usable, and the trace lets my colleague continue.”

## 3. Target State (To-Be) 🔒 FROZEN

The deliverable is a distributable `tfw-daily-task` skill that applies TFW's existing concepts to bounded work where the governing project contract permits one worker. Retain the field name as the proposed invocation because SenseLab already uses it and it names the work rather than a new method; evaluate its possible cadence ambiguity under `Naming Creates Behavior`. The first receiving contexts are the Full projects in which the field practice appeared. The recommended default is a project-local `daily/` record outside the formal Full task corpus, using one `task.md` that presents the existing HL sections before work and records result, check and continuation afterward. Cross-project portability requires one canonical skill source and provider entry points, while the receiving project's authority and identity rules still govern.

| Established TFW concept | Required behavior in a small Task |
|---|---|
| Working Backwards and North Star | Show the owner a concrete finished-state preview, its benefit, an explicitly imagined stakeholder reaction and a minimal result rendering. Test the proposed work against the receiving project's North Star and relevant Project Values before implementation. |
| Goal and Value | State what should change and for whom before choosing files or actions. Use the result-first questions already present in HL and Assisted planning. |
| Question, Context and Boundaries | Expose uncertainty that changes the result; cite relevant source material; challenge a weak or contradictory proposal with reasons; say what the agent may decide, what is outside the Task, who accepts the result and when to stop. Ask only questions that could change a consequential decision. |
| HL and approval | Present the Task using the existing HL template and vocabulary, with detail proportional to the work. Invite the owner to answer, reject or reframe the plan and its material hypotheses. Begin execution only after the owner approves the proposed result and Boundaries. Formal Full approval semantics apply only when the Task is actually admitted to that lifecycle. |
| Task and role | One bounded piece of work has a human accountable for purpose and an actual named worker. A working unit, model, profile or session title is never a grant of authority. |
| Trace | Preserve selected material words of the human with their author and source, material decisions, result or actual state, verification and the continuation point. Existing project identity rules apply; absence of a profile never authorizes an invented identity. |
| Evidence and acceptance | Check the claim that matters in the real task; report what was observed and what remains uncertain. Prepared, checked, accepted and released are not interchangeable claims. |
| Continuation | End with an accepted close or the exact next human/agent decision. Preserve earlier material meaning when it changes, using ordinary file history or a justified version. |

The candidate working sequence is: inspect purpose and sources; perform Working Backwards and the North Star check; present and discuss the HL-shaped plan; obtain owner approval; execute inside the approved Boundaries; check the result; record the selected Trace and return for acceptance or the next reserved decision. Approval of a plan does not itself authorize an unmentioned release, publication, communication or scope extension.

There is no automatic file collision between SenseLab's `daily/` and Full's `workspace/`: the local Daily README explicitly keeps its records outside the formal Full lifecycle. There is, however, a scope ambiguity to resolve upstream: `.tfw/conventions.md` §13 says “Every task” produces RF, `status.md` and journal without qualifying which kind of task, and other artifact rules likewise say “every task directory.” The portable design must explicitly distinguish a local `daily/` record from a formal Full task in the applicable canonical rules. The substantive incompatibility arises if one labels a one-worker Task as formal Full while omitting its mandatory artifacts or independent REVIEW, or lets the Full Coordinator write implementation. Using the same HL thinking and presentation does not itself claim Full authority. Consequence and uncertainty determine whether stronger Evidence or independent review is needed.

| Route for a new request | Plan shown to the owner | Worker and trace | Cost and consequence |
|---|---|---|---|
| Recommended `daily/` Task | Existing HL headings, proportionately filled; owner approves Goal, result and Boundaries. | One agent then acts; one `task.md` preserves approved plan, actual result, check and continuation. | Small installation and record cost; requires a precise clarification of “task” scope in Full's common rules and a clear transfer when formal assurance is needed. Full role separation itself stays intact. |
| Formal Full `workspace/TFW_…` Task | Governing HL and TS with the existing approval and freeze contract. | Distinct Coordinator, Executor and Reviewer; `status.md`, `journal/`, RF and REVIEW. | Existing assurance and authority; more people, gates and artifacts. A one-worker exception here would require a separate canonical change to Full Role Lock and Trace Discipline. |

The proposed default record is `daily/YYYY/YYYYMMDD-HHMMSS_slug/task.md`, following the existing SenseLab placement, with project work products at their ordinary paths. `task.md` holds the owner, actual worker, current state, exact source-linked human excerpts, HL-shaped plan, approval source, material plan changes, result, proportionate Evidence and next act. The approved plan remains inspectable; a material change requires another owner decision and a preserved earlier version or Git history. Existing SenseLab/helpdesk folders keep their paths and files. A receiving project may choose its own storage through its explicit rules. The formal Full HL header, coordination table and freeze machinery are not silently copied into a local record; the same HL sections and strategic discussion are visible to the owner. Research must verify the smallest adequate rendering against the actual HL template. If the provider supports title write and readback, use the existing navigation form with `WORK=DAILY` and the exact Daily identifier, for example `DAILY · 20260923-184200_login-fix`; title grants no authority and never creates a separate task in the app by itself.

## 5. Definition of Done (DoD) 🔒 FROZEN

- ✅ 1. The skill uses the Plan mindset: Working Backwards, a substantive North Star and Project Values check, reasoned critique, consequence-changing questions and the Saint-Exupéry Gate. The user sees a concrete future result in the familiar HL sections before deciding whether to approve the work.
- ✅ 2. Project work products stay at their ordinary paths.
- ✅ 3. The default `daily/` record is explicitly outside the formal Full task corpus, and the canonical rules state that boundary where “every task” could otherwise include it. The skill checks the receiving project's storage rules, preserves existing SenseLab/helpdesk records and never aliases local completion to a formal Full verdict. An active formal Full task remains governed by its existing role and artifact contract.
- ✅ 4. The owner approves the proposed result and Boundaries once after the questions and critique; the worker then acts within that authority. Material changes return to the owner, while a formal Task or material risk invokes the relevant existing boundary and proportionate assurance.
- ✅ 5. One canonical skill source, verified Codex and Claude entry points, and bounded examples work in at least two project contexts without SenseLab identities or content, a required service, or a second semantic source for provider copies. Where a provider supports it, the task title follows the existing `{WORK} · {TASK}` navigation form with the exact Daily identifier.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. New labels, statuses, document roles or a different user ritual duplicate Goal, Value, Task, Trace, Evidence, acceptance or the existing edition's authority model; a small plan skips Working Backwards, North Star, critical questions or the HL-shaped owner discussion.
- ❌ 2. A `daily/` record claims formal Full lifecycle authority, omits mandatory Full artifacts after entering that lifecycle, or one worker crosses an active Full Role Lock.
- ❌ 3. A title, profile, thread address, chat wording or urgency is treated as authority for scope, release, publication or communication.
- ❌ 4. Source text is fabricated, a material contrary instruction is omitted without disclosure, or secret material is copied into a shared Trace.
- ❌ 5. A consequence-bearing change is waved through because it is called Daily or touches few files; necessary verification, review or a reserved human decision is skipped.

**On failure:** retain the actual source and state, stop the affected action, name the missing authority or assurance, and route to the governing project workflow or human owner. Do not reclassify a formal task silently.

## 7. Principles 🔒 FROZEN

1. **Purpose before activity** — state Goal and Value before optimizing a Task; registration without a useful result is failure.
2. **Working Backwards and Questions before premature answers** — show the finished result, test it against the North Star, expose decision-changing uncertainty and challenge a weak premise before owner approval.
3. **Selected Trace, not transcript** — preserve material human source, context, decisions, actual state, result and continuation without elevating chat chronology to authority.
4. **Human authority, bounded delegation** — distinguish accountable person, actual worker and acceptance authority; name the Boundaries and stop condition.
5. **Continuation over isolated output** — leave a usable result and enough Trace for another authorized participant to continue.
6. **Assurance proportional to risk** — choose checks, Evidence and independent review for the consequence; approval of a small HL-shaped plan grants execution only within its Boundaries.
7. **Naming Creates Behavior and Portability** — prefer the method's existing terms and ordinary project files; any proposed new name must cue the same action across providers and editions.
