## 1. Vision 🔒 FROZEN

People can give a bounded, ordinary assignment to one agent, receive a usable result, and leave a small durable trace from which another authorized participant can continue. The route applies across domains and projects without requiring the formal Full lifecycle for every letter, document, correction, or small post-release repair. Its use remains proportional to consequence and authority, not merely to file count or urgency.

**Impact:** A colleague can identify the human requester, actual worker, purpose, scope, material instructions, current result, verification and next action without reconstructing chat or confusing the record with a formal TFW phase.

> **Imagined stakeholder quote, not testimony:** “I can see what was requested, what changed, who worked on it, how it was checked and whether I need to decide anything next.”

## 3. Target State (To-Be) 🔒 FROZEN

**Recommended product boundary:** `tfw-daily-task` is one optional, portable companion skill for bounded direct execution. It is not a fourth TFW edition, a shortened formal Full task, or a replacement for an already governed phase. Projects may opt into a `daily/` store; an existing explicit project path takes precedence. The skill works without a new runtime or global task registry and does not require all projects to adopt Full's `team/` schema.

| Concern | Target behavior |
|---|---|
| Entry | Understand the actual request and applicable project rules; start or resume one exact daily task; begin useful work without a separate ceremonial approval when scope and authority are already clear. |
| Plan | A compact, versionable HL-derived brief states Goal, Value, scope/boundaries and observable completion; it is not named or treated as a formal HL. |
| Human and worker | Name the human owner and source-linked authorship at the evidence available; record the actual agent/task or human worker separately, without turning profile, model or thread title into authority. |
| Source words | Preserve exact material excerpts, author and source; mark coverage and omissions honestly. The selected brief and decisions state current meaning. Never invent a quotation or copy secrets into shared traces. |
| Result | Keep current state, deliverable links, material decisions, verification and next action in the task-local record. Preserve meaningful earlier versions through Git or explicit versions. |
| Boundary | `daily/` records never write Full `status.md`, journal, HL, TS, RF or REVIEW, nor grant release or communication authority. Escalation preserves the daily record and links the formal task in both directions where authorized. |
| Navigation | Use a readable task identifier and a `DAILY · {TASK}` session title when the active surface supports exact title/readback. Titles are navigation only. Existing daily identifiers remain intact. |

### 3.1 Result Visualization

Six months after adoption, a colleague opening a small post-release repair sees this self-contained record, with the actual output linked from `task.md`:

```text
daily/2026/DAILY_20260923-223151_login-error/
  task.md       Owner · Worker · Status · Result · Check · Next · Closure
  brief.md      v1 Goal · Value · Scope · Done when; v2 only if meaning changes
  messages.md   U001 exact excerpt · Author · Source; U002 correction if material
```

| What the next participant reads | Example content | Value shown |
|---|---|---|
| Human request | “After release, login sometimes returns 500; restore login without changing registration.” | The original problem and constraint survive the session. |
| Current brief | Goal: login works for the affected case. Value: users can enter the service. Done when: the failure is reproduced, the fix is checked and the required release decision is recorded. | Purpose and acceptance are readable before implementation detail. |
| Current task | Owner: named human; Worker: exact observed task address; Result: linked change; Check: observed failing/passing case; Next: owner release decision if still reserved. | Another person can inspect or continue without mistaking prepared code for a released fix. |

The example is a rendering of the intended format, not a claim that this repair happened or that any deployment was authorized.

### 3.2 Value Flow

`bounded human request → selected exact source + compact Goal/Value/Done → one agent produces result → checks what matters → task-local result and next authority → another participant can continue`.

At each arrow, the record preserves only the information needed to understand purpose, inspect the result, or make the next legitimate decision.

## 5. Definition of Done (DoD) 🔒 FROZEN

- ✅ 1. A project can install and invoke one portable `tfw-daily-task` skill without copying SenseLab-specific identities, URLs, or project content.
- ✅ 2. A new or resumed daily task has an inspectable owner, actual worker, source-linked material instructions, Goal, Value, boundaries, result, verification, current state and next authority in a small task-local trace.
- ✅ 3. Naming and storage keep daily work distinct from Full; existing daily paths remain readable; the session title is applied and checked where available without acting as authority.
- ✅ 4. The route finishes authorized simple work without a needless approval step and refuses or escalates when consequence, missing authority, formal phase ownership or independent assurance require it.
- ✅ 5. Guidance and real bounded demonstrations show compatibility with at least two different project contexts and make limitations and manual owner decisions explicit.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. A Daily record writes or changes a formal Full task's `status.md`, journal, HL/TS/RF/REVIEW, or presents local `done` as a Full verdict.
- ❌ 2. A title, profile, thread address, old chat, or apparent urgency is treated as authority for scope, release, publication or communication.
- ❌ 3. Source text is fabricated, significant contrary instructions are omitted without disclosure, or secret material is copied into a shared trace.
- ❌ 4. The skill requires a universal project profile schema, maintained task index, new service, mandatory independent role chain for every small task, or a code-only definition of useful work.
- ❌ 5. A small but consequential change is declared safe solely because it is called Daily or touches few files; verification and reserved decisions are skipped.

**On failure:** retain the actual source and state, stop the affected action, name the missing authority or assurance, and route to the governing project workflow or human owner. Do not reclassify a formal task silently.

## 7. Principles 🔒 FROZEN

1. **Purpose before mechanics** — Goal and Value determine the useful result; the agent does not finish at record creation.
2. **Selected trace with exact provenance** — source-linked excerpts preserve human wording while a brief and task record carry current meaning and state.
3. **Human authority and honest attribution** — owner, message author, worker and accepter are distinct; recording an identity never grants a decision.
4. **Proportional assurance** — verification follows risk and consequence; a daily label neither waives checks nor automatically invokes Full.
5. **Project independence** — ordinary files are portable, local rules take precedence, and no vendor session is the sole project memory.
6. **One truth per route** — Daily and formal TFW may cite each other but never share or impersonate their lifecycle carriers.

### Hypotheses

| # | Hypothesis | Status and decision consequence |
|---|---|---|
| H1 | The value comes from connected, concise records, not from a daily cadence. | Supported by SenseLab and helpdesk examples; retain the familiar call name, define scope by work rather than calendar. |
| H2 | Local Daily mechanics can be generalized without carrying project identity rules. | Partly supported: both examples work, but SenseLab skill directly names its `team/` contract. Portable identity behavior needs TS design and a cross-project demonstration. |
| H3 | One worker plus direct checks suffices for every “small” change. | False as a universal rule: SenseLab's release case needed dedicated release evidence; retain risk-based escalation and owner authority. |

### Risks of Not Researching

Copying the field skill verbatim would make SenseLab's profile system and full message retention appear universal; putting the route into Full without an explicit boundary could create a second lifecycle authority. Local source comparison already resolves these design-changing questions enough for an HL proposal. A separate Researcher iteration is not proposed unless the owner identifies a decision-critical gap.

### Proposed RESEARCH Focus

If a material gap remains after HL review: verify the exact optional distribution path, receiving-project compatibility, and whether one common source can serve Codex and Claude without an implicit Full installation.

### Why Not Just...?

- Copy the SenseLab skill to every project? It preserves useful behavior quickly, but project-specific identity and full-message obligations would travel silently and copies would drift.
- Add another TFW edition? Editions are independently copied project baselines; this is an optional task route that should coexist with existing editions.
- Send every small task through Full? It preserves formal assurance but spends separate-role and evidence costs even where a bounded direct check is enough.
