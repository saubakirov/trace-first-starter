## 1. Vision 🔒 FROZEN

A review records the debt it found in its own task and writes nothing else. Whether that debt deserves
work is decided at the moment it is found: what deserves work becomes a task, and what does not stays a
trace in the REVIEW that found it. There is no project registry to append to, to prune, or to feel guilty
about.

The registry that exists today — 121 rows, 77 of them open, most never acted on — stops being a live
artifact and becomes a snapshot, preserved verbatim beside the Task Board it now resembles.

Withdrawing the outlet is half the point. A channel that will accept an unfinished thing at any time is a
standing permission to leave it unfinished, and an always-available section is an invitation to write
something into it. A channel that instead demands a disposition — do the work as a phase, open a task, or
rule on the record that it does not matter — withdraws that permission at the one moment when the work is
still fresh enough to finish.

**Impact:** Every reviewer's second write disappears. No participant maintains a shared list; no receiving
project inherits a growing one; nothing new is created to replace it. The count of maintained project
artifacts falls by one and rises by none.

> "I stopped opening a file I never acted on, and nothing was lost — the item is in the review that found
> it, and the ones that mattered are tasks."

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. Debt capture is relocated into a new per-task artifact — the move this task exists to reject.
- ❌ 2. A project-level debt view is introduced that a person maintains by hand, or that a receiving
  project must run code to produce.
- ❌ 3. Any of the 121 rows is deleted, renumbered, re-sorted or reworded, or a `TD-N` citation stops
  resolving.
- ❌ 4. The release ships with any canonical file or adapter copy still naming a live root registry.
- ❌ 5. Debt becomes undiscoverable: the canon states no operation by which open items can be listed.
- ❌ 6. The retirement is delivered to receiving projects as a script, a check or a command.
- ❌ 7. The task grows into knowledge staging, the portfolio index, or the existing scripts — all three are
  outside this contract.
- ❌ 8. The phase crosses a configured scope budget without an explicit owner ruling based on an exact
  file, new-file and LOC count.
- ❌ 9. Any path survives by which work may be left unfinished on the ground that it can be logged as debt
  — the outlet reappears under another name, in another artifact, or as an undisposed item.
- ❌ 10. The disposition gate becomes a fourth ceremony: an item is "disposed" by a formula nobody chose,
  or "not material" becomes the default an agent writes to clear the gate.

**On failure:** stop and return to `/tfw-plan`. Keep every trace. For a frozen outcome change, file a §12
amendment with evidence, cost and a considered alternative — do not patch around the retirement by
reintroducing a registry under another name.

## 7. Principles 🔒 FROZEN

1. **Subtraction is the deliverable.** The result is measured by what is gone. A change that ends with more
   maintained artifacts than it started with has failed regardless of its other qualities.
2. **Capture where the finding is.** Debt is written once, in the artifact that found it. A second copy is
   a synchronization problem, not a view.
3. **Dispose before closing, never defer.** Every captured item is paid, promoted or ruled not material
   before its task closes. A queue of undecided items is the graveyard, and it re-forms wherever deferral
   stays free.
4. **An open channel is a permission.** A section that will always accept an entry invites one to be
   written, and an outlet that always accepts an unfinished thing permits it to be left unfinished. The
   control is to close the channel, not to ask for restraint in front of an open one.
5. **History is preserved verbatim and never edited.** Retiring a mechanism does not retire its record.
6. **Nothing a receiver must run.** Code is legitimate for migration, documentation build and the site;
   it is never part of the method, of a role's obligations, or of what a receiving project is asked to
   execute in an environment we do not know.
7. **One release surface.** Canon, workflows, templates, adapters, migration text and documentation land
   together, or the retirement is not real.

### 7.1 Quality Contract 🔒 FROZEN

- The TS maps every principle above to a verifiable AC.
- Every changed file is counted before the TS is written; adapter propagation is counted, never hidden
  behind "mechanical copy."
- No rule is added to compensate for a rule being removed. If the retirement needs a new obligation to
  work, the retirement is wrong.
- The snapshot is produced by copy, and its row count is stated and checked against the source.
- No provider or tool name enters a normative sentence.

### Risks of Not Researching

We would retire the only path by which an old defect is ever rediscovered, on the assumption that nobody
uses it — an assumption drawn from write history, not read history. The reverse is also live: without H4
we could commit to a promotion rule that turns 77 rows into 77 task proposals.

### Proposed RESEARCH Focus

1. **Gather**: every read of `TECH_DEBT.md` in the canon, the adapters, the build and the task corpus —
   who opens it, at which step, and what they do with the result.
2. **Extract**: the exact retirement mechanics of the Task Board at 2.0.0 — what was changed, in what
   order, and what the field reports said afterwards. It is the closest available precedent.
3. **Challenge**: argue the opposite — that the registry is the only project-level memory of unfinished
   work and its loss is unrecoverable. Find the strongest case against retirement, on evidence.
4. **Extract (H5)**: read the 121 rows against `review.md` Step 5's own quality filter — *"only promote
   items that would cause real problems if left unfixed"* — and against each row's source TS. Two counts
   come out: rows that fail the project's own filter, and rows whose fix was already inside the scope of
   the task that filed them.

### Why Not Just…?

- **Why not prune it again?** It was pruned on 2026-04-15 (41 rows) and refilled to 121 in four months.
  Pruning treats the symptom the mechanism guarantees.
- **Why not a task-local debt file, as TFW-60 Phase B wrote it?** It adds a file per task, absorbs no
  existing responsibility (REVIEW §5 already holds the item) and preserves the accumulation — HL §7.1 of
  TFW-60 forbade admitting an artifact that removes no duplicate write.
- **Why not a generated project debt view?** A view a receiver must generate is code we ship and oblige
  them to run in an environment we do not know — the owner's ruling of 2026-08-30, and Principle 5.
- **Why not just stop writing to it and leave it in place?** A live file the canon still lists is a file
  the next agent appends to. The rename is the enforcement (PV 1, Structural Enforcement).
- **Why not just enforce a quality filter on what gets written?** There already is one. `review.md` Step 5
  instructs the reviewer to *"reject filler observations — only promote items that would cause real
  problems if left unfixed"*, and `constraint.md` F3 declared such filters mandatory on 2026-04-03. The
  file grew from 1 463 to 12 352 words with that filter in force. A filter in front of an open channel is
  the thing that has already been tried.
