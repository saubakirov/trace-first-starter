## 1. Vision 🔒 FROZEN

A TFW project holds only two kinds of files: the result and the selected trace. Everything a role
needs while working — raw command output, logs, exports, screenshots, archives, helper scripts —
lives outside the project in TFW's machine-local folder under the task ID and is gone when the task
closes. The evidence folder is a registry of what was verified, how, and what was seen; a reviewer
repeats the check instead of trusting bytes. A comment exists only where it carries value for the
reader of that file; comments are no longer a channel for notes between agents, excuses or deferred
work, because the reason for a decision already has a home in the trace. Repositories stop growing
from junk, searches find decisions instead of dumps, and agents spend tokens on meaning.

**Impact:** receiving projects stop accumulating hundreds of megabytes of evidence and Daily
leftovers per quarter; clones, updates and reviews stay fast; a task folder or Daily record can be
read whole; code and configuration carry no correspondence.

> Explicitly imagined owner quote, not testimony: "Before, the agent paged through logs and
> screenshots in the task folder. Now it reads a ten-line registry and sees what was verified and
> how — and the repository has stopped growing."

## 3. Target State (To-Be) 🔒 FROZEN

Frozen claims:

- **C1 — One home per file.** Everything a role produces is either the result (VALUE), the selected
  trace (TRACE) or working material. Working material lives outside the project tree, under the
  task or Daily record ID, in TFW's existing machine-local root or the system temporary directory
  as research selects; it is created by the role that needs it, is referenced from the trace only by
  its ID-relative name (never a machine-absolute path), and never outlives the task: it is removed
  no later than `Closing and record recovery` step 6.
- **C2 — The evidence folder is a registry.** `evidence/` contains only the EV file(s). Each row
  carries what was verified, how (command or action and the Candidate commit or live target), what
  was observed, and the result. No attachments section, no binaries, no logs, no archives, no
  copies, however small.
- **C3 — Verification by repetition.** The Reviewer establishes a claim by repeating the command on
  the fixed Candidate or by opening the live result and records its own observation; a verdict never
  depends on another role's working material.
- **C4 — Daily follows the same rule.** A Daily worker keeps working material in the same
  machine-local place under the record ID; before each orderly return the record folder contains
  only the record file(s) and every product sits at its ordinary project path.
- **C5 — A comment is value or absent.** In any value file — code, tests, configuration, prompts,
  templates — a comment exists only when it carries value for that file's reader or is read by a
  program (interpreter line, tool directives, license header, TFW managed-block markers). Comments
  are not a channel: no messages to other agents, excuses, deferred-work notes, legacy chatter,
  jokes or notifications. The reason for a decision lives in the trace. Configuration comments that
  explain a setting keep their value; docstrings and other candidate exceptions are decided by
  research and bound in TS.
- **C6 — Receivers choose cleanup, agents comply forward.** The migration guide of the release that
  carries this explains in plain terms why comment correspondence harms (it goes stale, becomes a
  wall and a slow conversation between agents, lets an agent leave a note instead of finishing, and
  costs tokens), offers a separate TFW cleanup task now, later or not at all, and records the answer
  in the existing update receipt. Whatever the answer, new agent writes follow C5. No update ever
  rewrites a receiver's code or history.
- **C7 — This repository eats its own cooking.** Its live code and configuration are cleaned of
  non-value comments in this task; frozen task, Daily and historical folders are untouched; this
  task's own `evidence/` holds only its EV and its working material lives where C1 says.
- **C8 — Nothing new is added to carry this.** No new root folder, no project-wide registry, no new
  command, no code or test, no dependency. Enforcement uses what exists: exact-path staging and
  `git status`, two Reviewer checks in `verify.md`, the EV template shape, and Closing step 6.
  `.tfw/` gains at most the migration guide.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. The Reviewer of this task cannot establish a material claim without working material that no
  longer exists.
- ❌ 2. The selected location is unwritable in an agent sandbox the owner actually uses.
- ❌ 3. The cleanup removes a program-read line (managed-block marker, interpreter line, tool
  directive, license header) or breaks install/update.
- ❌ 4. Any change rewrites or deletes a historical task, Daily or receiver record, or an update
  touches receiver code.
- ❌ 5. A changed workflow grows in words, or the task adds code, tests, a command, a registry or a
  dependency.
- ❌ 6. A task artifact carries a machine-absolute path, a private project name or a personal address.

**On failure:** the Executor stops at the affected acceptance criterion and returns through
`coordinator_route`; the Coordinator rules the round or routes the strategic question to the owner
through §12 (DoF 1 → retain working material until the Reviewer's verdict or let TS name retained
items; DoF 2 → an in-project ignored folder as the fallback location). Nothing is force-pushed or
rewritten; DoF 6 is fixed before the commit is accepted.

## 7. Principles 🔒 FROZEN

1. **One home per file** — result, trace or working material; a file in the wrong home is a defect,
   not a convenience.
2. **Observation over attachment** — the registry row carries what was seen and how, not a pointer
   to bytes.
3. **Verify by repeating** — a reviewer re-runs or re-opens; it does not trust another role's dump.
4. **A comment is value or absent** — comments are never a channel; the reason lives in the trace.
5. **Subtract before adding** — no new root, command, code or registry; existing structures enforce.
6. **Forward rule, optional cleanup** — people choose whether to clean the past; agents comply from now
   on everywhere.
7. **Eat your own cooking** — the repository that ships the rule satisfies it first, including this
   task's own trace.

## 10. RESEARCH Case 🟢 FREE

### Blind Spots
- Whether Codex, Claude Code and Antigravity sandboxes, as configured by ordinary users on Windows,
  macOS and Linux, permit writes to `~/.tfw/` or the system temporary directory.
- Whether any past review in this repository or a receiver found a defect only through raw
  executor files rather than by repetition or opening the result.
- How agents actually use comments in receivers' configuration files (the owner reports
  correspondence; no content was inspected here).
- Whether docstrings are read by any tool the receivers depend on.
- How much of the "historical … remains readable" prose in `.tfw/` is rule and how much is chatter.

### Hypotheses

| # | Hypothesis | Status |
|---|----------|--------|
| H1 | Codex, Claude Code and Antigravity with ordinary sandbox settings can create, read and delete files under TFW's machine-local root (`~/.tfw/`, `%LOCALAPPDATA%\tfw\`) on Windows and POSIX; the system temporary directory is the fallback. *False case:* a sandbox confines writes to the project tree. *Consequence:* working material stays in the project but outside Git (ignored folder). | open |
| H2 | Reviewers establish claims by repeating the command or opening the live result, not by reading the executor's raw files. *False case:* a past REVIEW found a defect only in a raw log. *Consequence:* working material is retained until the Reviewer's verdict, not until close. | open |
| H3 | After acceptance, raw material adds nothing a registry row cannot carry. *False case:* a later task needed bytes from a closed task's evidence. *Consequence:* TS of high-risk tasks may name retained items explicitly. | open |
| H4 | Most commits per task are habit, not rule; committing at role returns cuts them several-fold without harming continuation or review. *False case:* a rule or recovery path depends on intermediate commits. *Consequence:* commit reduction leaves this task. | open |
| H5 | The comment rule holds against its loopholes: explanations do not migrate into docstrings, identifiers or commit messages, and a Reviewer can check this without code. *False case:* the Executor of this very task needs a docstring to satisfy a tool, or the check is impractical. *Consequence:* a narrower rule, or docstrings admitted as program-read where a tool consumes them. | open |
| H6 | "Working material outside the project; only the record in the record folder; products at ordinary paths" suffices for Daily without losing results. *False case:* a Daily product has no ordinary path (a one-off chart, a demo video). *Consequence:* the record gets an explicit product list and a named home for one-off products. | open |
| H7 | The "historical … remains readable, never issued" prose in `.tfw/` is mostly rule protecting old receivers; chatter is small. *False case:* a large share is notes between agents. *Consequence:* the cleanup goes to the agreed separate task; C5 still applies to new writes. | open |

### Risks of Not Researching
The location would be chosen by taste and fail in the first sandbox; the removal point would be
chosen without knowing whether reviewers ever needed raw files; the comment rule would ship with an
obvious loophole; Daily would lose one-off products silently.

### Proposed RESEARCH Focus
1. **Gather**: run write/read/delete trials under `~/.tfw/work/` (or the Windows root) and the system
   temporary directory from Claude Code and Codex on this machine; collect vendor documentation on

2. **Extract**: which root works everywhere; whether any verdict depended on raw files; which

3. **Challenge**: what would make the registry insufficient; what would make the rule unenforceable

### Why Not Just...?

| Approach | Value | Adoption / operating burden | Risks / tradeoffs | Decision and reason |
|---|---|---|---|---|
| Working material outside the project, registry in `evidence/`, removal at close; comments are value or absent (recommended) | Repository stops growing; one rule covers tasks, Daily and comments; no new mechanism | Agents change a habit; one more object in the existing close step | Sandbox may refuse; a reviewer may want raw files | Recommended — it is NS2.4 applied to the end and adds nothing |
| Keep everything in the project but cap size and types | Everything at hand | Caps to maintain | Repository still grows by many small files; logs leak paths; caps are a size rule, not a term (F40) | Rejected — the owner wants working material out of the project |
| Working material in the project but ignored by Git (`evidence/raw/`) | Any sandbox allows it; same path everywhere | None | Junk still sits in the project and is invisible in other worktrees; Daily folders stay cluttered | Fallback only if H1 fails |

**Leave unchanged:** receivers continue to add hundreds of megabytes of evidence and Daily
leftovers per quarter (≈900 MB and 243 MB on one machine today), reviewers keep trusting or
re-opening dumps, and comments keep carrying agent correspondence that goes stale and costs tokens.

**Critical challenge:** the strongest objection to the owner's proposal is that a registry row is
chosen by the Executor — it can keep the convenient lines while the rest vanishes with the working
folder, and some observations (a live system at one moment) cannot be repeated. Against the
recommendation: if H2 is false, verification by repetition is not enough for high-risk work. The
answer is C3 plus DoF 1: the Reviewer's own repetition or opening is the proof, and a TS for risky
work may name items that are retained; the recommendation is wrong only if reviewers routinely need
the Executor's bytes, which research will show.
