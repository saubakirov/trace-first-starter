## 1. Vision 🔒 FROZEN

Every newly initialized Full TFW project starts with one working folder, `workspace/`, without a container-choice question. Existing projects keep their chosen working folder; the temporary `[workspace, tasks]` arrangement is retired where its second container serves only history. Historical files keep their paths and remain readable and citable, while ordinary work stops rediscovering them as current obligations.

**Impact:** New users receive one clear default. Existing users receive a compatible, repeatable update that preserves their work and asks only about a material unresolved choice.

> “A new project has workspace. My existing project keeps my choice, and its old history no longer interrupts current work.”

## 3. Target State (To-Be) 🔒 FROZEN

### Project behavior

| Project before installation/update | Result | Container-specific question |
|---|---|---|
| New Full project without configured TFW work | `task_containers: [workspace]`; only `workspace/` is created for tasks | None; an explicitly requested custom path remains a project choice |

| Existing `[workspace, tasks]`, absent/empty `tasks` | Normalize to `[workspace]` | None |
| Existing `[workspace, tasks]`, established historical-only `tasks` | Current work uses `[workspace]`; history stays at `tasks/` | None; apply the version-addressed compatible migration |
| Existing `[workspace, tasks]`, live work or unresolved continuation in `tasks` | Preserve operational reachability until the affected group's disposition is resolved | One material decision if existing evidence/authority cannot settle it |
| Other configured paths/orders, including `[tasks, workspace]` | Preserve the project choice | No normalization merely because multiple paths exist |

The mixed list alone does not prove that its second container is inactive. Existing task-local states, recorded project decisions, and continuation obligations determine whether the historical-only route is safe. Missing state, an old date, or a legacy identifier does not establish completion. A recorded decision to retain an active secondary container remains a project choice; later updates do not ask again about the same unchanged case.

For **this repository**, the owner's recorded direction to retain the old corpus in place and stop treating it as current work supplies the intended disposition. Old task states remain historical facts; the container decision does not claim those tasks achieved `DONE` or `REJECTED`.

### Historical access

| Operation | Working container | Historical container |
|---|---|---|
| Create a task | First configured working path | Never |
| Ordinary current-work discovery / Knowledge Gate | Included | Excluded |
| Open a specifically cited task/file | Available | Available at the original path |
| Compile documentation / resolve identifiers | Available | Available; enumeration for these purposes is permitted |
| Change lifecycle during migration | No inferred transitions | Original task states and artifacts preserved |

The working setting contains active paths. Projects retaining history may need one optional configuration setting for historical paths; new projects receive no empty archive setting, marker files, or archive scaffolding. Its exact representation is settled before TS approval after checking existing readers. SLC creates no second lifecycle system, task index, automatic copy process, or general archive-management feature.

The update applies configuration and necessary digest-state reconciliation as one connected semantic group. It accounts for exact tasks in the affected container, preserves active-work digests and accumulated knowledge, and never infers historical membership from an ID prefix. Re-entry observes current state and safely completes or refuses a partial migration. Repeated updates do not recreate `tasks`, repeat completed migration, or repeat a resolved choice.

The documentation URL prefix `tasks/` is outside the working-folder naming change. Existing URLs, identifier grammars, immutable history, and relative paths remain readable; there is no tree-wide replacement of the word `tasks`.

## 5. Definition of Done (DoD) 🔒 FROZEN

- ✅ 1. A fresh supported Full installation and first task creation use only `workspace`; upstream's `tasks` corpus or mixed config is not inherited. No container-choice question or empty archive infrastructure is introduced.
- ✅ 2. Existing `[workspace]`, `[tasks]`, and custom paths/orders retain their choices and valid creation behavior. Current guidance distinguishes the default from compatibility.
- ✅ 3. Mixed configurations follow §3: empty or established historical-only storage transitions without routine questions; unresolved work stays reachable. Later updates preserve a resolved choice.
- ✅ 4. Historical containers are excluded from routine current-work discovery and the Knowledge Gate; exact lookup and documentation still work at original paths and URLs.
- ✅ 5. Config and affected digest state remain coherent through success, repeat, and interrupted-update re-entry. SLC introduces no removed-ID error and preserves unaffected digests and knowledge.
- ✅ 6. This repository uses `workspace` for current work and retains `tasks` for history. Existing task files/states are byte-identical; only necessary container-level explanation may change inside `tasks/`.
- ✅ 7. Released changelog routing reaches the version-addressed migration, including a same-major upgrade. Verification covers the §3 cases and distinguishes source checks from actual receiver behavior.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. A new project inherits `tasks`, two working containers, or archive configuration/folders it does not need.
- ❌ 2. An update replaces a single/custom choice or hides unresolved work merely because its folder is old or second in a list.
- ❌ 3. Migration moves, renames, copies, deletes, or relabels task artifacts, or falsely declares all tasks complete through a container-level statement.
- ❌ 4. Historical identifiers, links, or documentation routes stop resolving, or retired history re-enters routine current-work checks.
- ❌ 5. SLC breaks knowledge-state reconciliation, resets receiver knowledge, removes unrelated digests, or repeats a completed transition/unchanged decision.
- ❌ 6. Delivery requires a new lifecycle vocabulary, maintained registry, per-task marker, receiver runtime dependency, mass reference rewrite, or mandatory per-task interview.

**On failure:** Refuse the affected migration group before applying it where possible. After partial application, use existing update recovery and preserve subsequent project work. Return purpose/architecture conflicts to the Coordinator; do not repair through unrelated historical edits or a whole-tree restore.

## 7. Principles 🔒 FROZEN

1. **Saint-Exupéry as a design test.** Every field, rule, and consumer change must perform a necessary job. Remove the archive interview, false closure declaration, universal enumeration ban, automatic task-copy route, and speculative extra phase; retain continuity and compatibility.
2. **Default and project choice have different owners.** The framework ships `workspace`; an existing project owns its configuration. Single `[tasks]` remains valid even when its origin is unknown.
3. **Historical access has a precise purpose.** Preserve paths and identifiers while excluding retired containers from routine current-work discovery. A seal governs operations, not the truth of task lifecycle.
4. **Use the existing update mechanism.** Compatible cases follow the version-addressed guide; unresolved material choices receive one grouped decision. No archive approval workflow is created.
5. **Ship the complete change.** Default, actual initialization, receiver transition, historical readers, and this repository agree in one phase. File count is not the measure of correctness.
