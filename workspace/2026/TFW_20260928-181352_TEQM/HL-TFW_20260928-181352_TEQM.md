## 1. Vision 🔒 FROZEN

The owner can compare the resources spent developing helpdesk and afd over a selected period, open any task's complete cost, and identify the product functions and workflow roles consuming time, money and tokens. Every completed pilot task carries a readable report and a reproducible task-local record with 3–5 domain/feature keywords, result and coverage. A common measurement format supports different products with their own vocabulary; later adoption can extend to other teams, providers and TFW versions.

**Impact:** The first decision is where the owner's development resources go and what a helpdesk task costs. Separate time, token and money views reveal different expensive areas without collapsing them into a single score. The initial unit is a TFW development task, including its phases and revisions; operational helpdesk tickets and deployed products' running costs are outside this proposed first boundary.

## 3. Target State (To-Be) 🔒 FROZEN

| Owner question | Proposed output |
|---|---|
| Which project consumes more? | A selected-period comparison of helpdesk and afd with token volume, money basis, aggregate agent execution intervals and coverage. |
| What consumes time, money or tokens within a project? | Three separate rankings, each expandable by primary product area → task → phase/role/model. Known revision cycles and execution/wait intervals provide evidence; a causal explanation is not invented from totals. |
| What does one helpdesk task cost? | Complete task consumption across its lifetime, including all phases, roles, retries/revisions and reporting overhead. An available data subset is labeled partial. |
| What is a typical helpdesk task's cost? | Mean and median for explicitly selected completed tasks, their count and range; rejected/cancelled work remains visible. These are descriptive figures, not a universal price or an efficiency ranking. |
| Which product functionality received the work? | Stable product identity, one primary product area for additive totals, and 3–5 product-specific domain/feature keywords proposed at close and correctable without a new approval gate. |
| How do I compare accumulated work? | Regular task/phase reports plus a rebuildable overview, with combined consumption-date, project/task, keyword, role and model filters; visible source coverage, refresh epoch and corrections. Portable task records support aggregation of contributions from different computers. |

**Artifact contract:** A completed task has one `economics.md` beside `status.md`. Each completed phase has its own `economics.md`; the task-level file combines phase consumption and task-level coordination without double-counting. The same Markdown file contains a structured, machine-readable numeric/identity block and a human-readable report; a second JSON report copy is unnecessary. `status.md` remains the lifecycle/routing authority. Collection happens during work; finalization produces the terminal report. Source observations and partial ongoing-task coverage must remain available for the period view; their capture/storage mechanics are a research outcome.

**Time contract:** Calendar elapsed time runs from task start to terminal result. Agent time is the sum of defined, observed execution intervals by role; parallel role intervals may overlap, so role-hours can exceed elapsed hours. Time spent in tools may be inside an agent interval and must not be added to it a second time. Idle/wait classifications need actual events; elapsed minus summed role time is not a valid waiting-time formula.

**Money contract:** Show observed provider charges where available and a dated tariff-based estimate where calculable. Subscription expenditure is a separate period-level fixed cost; a project's/task's share is an explicit allocation policy. Never add tariff estimates and allocated subscription expense into one total for the same consumption. An allocation across projects needs a declared eligible cost pool and coverage; unobserved other use must not silently be charged to the two pilot products.

**Period contract:** Period spending uses observations whose consumption occurred in the period, including ongoing and unsuccessful tasks. A completed task's full cost uses all its lifetime observations, even across month boundaries. Dividing this month's spending by this month's closed-task count is not generally a task unit cost.

**Attribution contract:** One primary product area receives an ordinary task's full cost; genuinely cross-cutting work uses an explicit shared category. Keywords are overlapping search filters, not additive allocations. Routine percentage splitting is deferred. Product identity and the product vocabulary are separate from TFW version, coordination mode and model metadata. Every numeric observation belongs once in a parent task total; summing a parent aggregate and its child rows is invalid.

```text
              |                                |

             |                            selected dates + product/tags
     full task/role/model detail          + task + role + model filters
             +------------------+--------------------+

```

A platform turn ending can update observations; it does not itself declare a TFW task complete. A task-close invocation classifies once and includes that invocation's cost where observable. Repeated aggregation must not double-count cumulative counters or recursively classify the generated report. Ongoing tasks have partial observations and provisional classification, clearly labeled.

On phase/task finalization, the report and its numeric sources are refreshed, then become eligible for overview import. Explicit refresh also supports ongoing tasks. An already imported revision changes no totals; new observations add consumption; corrections replace the affected interpretation and leave an inspectable revision. Import delay, missing sources and conflicts are visible. An unavailable overview does not destroy the task-local report. ## 5. Definition of Done (DoD) 🔒 FROZEN

- ✅ 1. A real supported pilot path yields reproducible task-bound token and execution-time observations; unavailable fields are explicit. Task identity survives phase/role separation and totals contain each observation once.
- ✅ 2. Each completed task/phase has one `economics.md` beside `status.md`, containing structured data and its readable report, result/revision evidence, 3–5 supported domain/feature keywords and an explicit primary area or shared/unclassified state. The root file reconciles child phases and its own coordination once.
- ✅ 3. The owner can compare helpdesk and afd over a chosen period and inspect a helpdesk task's lifetime costs; ongoing and unsuccessful work remains visible in period spending. The pilot demonstrates both product identities without claiming unsupported historical recovery.
- ✅ 4. Money is labeled as observed charge, tariff estimate, allocation or unknown; its source, currency/date, method and coverage are visible. Parallel agent-time sums and calendar elapsed time are separate.
- ✅ 5. Capture and classifier overhead are visible; an independent Reviewer verifies the implemented bounded contract and the owner accepts the delivered result. No personal effort or activity monitoring is collected in this first version.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. Task economics is reconstructed from text length or guessed counters and presented as observed consumption.
- ❌ 2. Parent/child totals, cumulative snapshots or overlapping cost bases are counted more than once.
- ❌ 3. Missing data is silently zero, tariff estimates are represented as actual bills, or partial project coverage is represented as a complete spending comparison.
- ❌ 4. Tags multiply costs, a period/task denominator mixes incompatible windows, or summed role time is represented as the owner's labor or calendar duration.
- ❌ 5. A universal team score or productivity ranking substitutes for the selected project-cost questions.
- ❌ 6. The pilot requires raw private reasoning/transcript harvesting, unrelated role history, production access or a mandatory mutable portfolio authority.
- ❌ 7. The proposed route cannot produce real task-level usage, yet implementation proceeds claiming the measurement outcome has been met.

**On failure:** Preserve the observed limitation and return the affected product promise for discussion. A different provider/surface or narrower capture target needs an explicit scope decision before it replaces the intended result.

## 7. Principles 🔒 FROZEN

1. **Business questions select fields.** Start with the owner's project/task decisions; keep future comparison metadata small.
2. **Three resources, three answers.** Tokens, money and time have independent units and may rank projects differently.
3. **Product vocabulary belongs to the product.** Share measurement semantics across installations and reuse existing domain/feature terms locally.
4. **Evidence before precision.** Preserve measurement method, source epoch, coverage and unknown states.
5. **Task-local truth, derived overview.** On-demand project views are disposable projections of inspectable task records.
6. **Proportionate operating cost.** One bounded close-time classifier is the initial recommendation; measure its overhead before optimizing the inference infrastructure.
7. **Quality stays visible.** Preserve result, review and rework alongside spending; failed work still consumes resources.

### Portable task data and BI — Coordinator proposal, 2026-09-29

**Owner requirement:** regular UPM/DARYN-style reports, accumulated history and combined task/date/keyword/model/role views; consider team contributions from different computers. **Coordinator recommendation:** task-local numeric JSONL batches plus the existing economics.md, with DuckDB as an optional analytical reader/cache. SQLite, DuckDB and Parquet were the owner's candidate mechanisms, not approved technology constraints. This proposal adds no fifth research iteration or service launch.

**Proposed layout — names are guidance pending TS:**

```text
Task/
  status.md
  economics.md                  readable report + structured metadata/summary
  economics/
    sources/
      <unique-batch-id>.jsonl    immutable numeric observations and intervals
  Phase-A/
    status.md
    economics.md
    economics/sources/          phase-owned contributions, linked at task level

Analyst's local directory, outside tracked task truth/
  economics.duckdb              rebuildable selected-project cache
  overview.md                   generated readable comparison
```

The JSONL files are source measurements, not a second JSON copy of the finished report. Source batches plus the report's versioned metadata, bindings, classification and pricing basis must suffice to rebuild the supported views after platform logs rotate. A common database alone cannot make that promise. Agents normally read the compact report; deterministic tools read numeric batches without putting them into model context. Every captured source observation has one owner; root/phase reports reference the same facts without copying costs into additive parent rows.

| Choice | Benefit | Implementation/operating cost | Consequence / recommendation |
|---|---|---|---|
| Markdown summary only | Immediately readable, minimal files | Lowest capture packaging cost; manual comparisons | Retains today's sample value, but summary margins cannot answer arbitrary combined filters |
| JSONL sources + SQLite overview | Transparent portable records; straightforward indexed store and transactions | Collector, importer, schema, report queries; one managed write path | Valid alternative if incremental bookkeeping dominates; keep the same exchange contract |
| JSONL sources + DuckDB overview | SQL over file batches and analytical groupings; optional persistent cache | Same collector/import responsibilities plus an optional DuckDB runtime for the analyst | Recommended for this report/comparison use; engine is replaceable without changing task records |
| Parquet sources + DuckDB | Compressed columnar batches suited to larger archives | Binary encoding, schema handling and inspection tooling at every producer | Defer source-format conversion until measured archive size/query latency warrants it; a derived Parquet export can come first |
| Live shared database/service | Central continuously updated view | Deployment, authentication, availability, ingestion and operations | Revisit when file exchange no longer meets an agreed freshness need |

**Why this recommendation:** the current need is transparent batch collection and analytical slices across many task folders. DuckDB documents direct [JSON loading](https://duckdb.org/docs/current/data/overview) and [multi-file Parquet queries](https://duckdb.org/docs/current/data/parquet/overview). Its embedded read/write mode is owned by [one process](https://duckdb.org/docs/current/connect/concurrency); producers therefore exchange source batches instead of concurrently writing one network database. [SQLite](https://www.sqlite.org/whentouse.html) is also suitable for local application data, with a single writer at a time; choosing it would not solve cross-computer exchange by itself. These documentation checks support a design choice, not a benchmark or a measured speed guarantee.

**Smallest useful data contract:**

| Preserved information | Business purpose |
|---|---|
| Stable project/task/phase IDs; provider/session/native observation ID; source/version/coverage | Merge copies and retries once; survive different workstation paths and identify missing sources |
| Usage timestamp or observed time window, UTC/timezone basis; separate capture time | Date filters reflect consumption evidence, not the day someone copied the report |
| Raw numeric categories and normalized counters; model/effort; explicit role/session binding | Recalculate model/role/date intersections without estimating usage from prose |
| Execution interval, duration source/method, unmatched boundaries | Keep execution time, elapsed time and heuristic activity distinct |
| Primary area, 3–5 keywords, declared team, TFW version/mode, result/rework references | Product/feature and later practice comparisons without personal activity tracking |
| Schema, report/binding/classification revisions; tariff identity/date and monetary basis | Explain corrections and reproduce a previously published report |

A native observation's identity does not change when its task binding, role, decoder or model label is corrected. Provider namespaces must avoid collisions; a host path is a source locator, not a project or consumption identity. A role/session reused across tasks needs an explicit attribution interval; ambiguity remains unallocated. Historical coarse snapshots retain their available granularity. A cumulative delta spanning a date boundary is not silently split into invented daily usage.

**Refresh and team exchange:**

1. A local numeric adapter captures a bounded task/session snapshot. One bounded close-time classifier proposes the product terms; totals and exports are computed without another model pass.
2. It publishes a complete source batch and a matching report revision with a fixed capture cutoff. Incomplete files are not importable. Report-generation/classifier usage is included where observable; a later refresh can account for the closing tail without recursive classification.
3. Phase/task completion triggers the report update; explicit refresh also covers ongoing tasks. The current pilot must specify its actual trigger and display failed/missing capture rather than promise universal hook support.
4. Participants exchange these task contributions through existing repository/file-transfer arrangements. Unique immutable batch files avoid several agents rewriting one numeric log. This first proposal needs no live network database or new transfer service.
5. One aggregator validates complete inputs and reconciles native IDs and source revisions. The same import is a no-op; an older revision cannot overwrite a newer one; corrected interpretation revises the affected fact, not its consumed amount twice. Unresolved conflicts are reported. Declared duplicate exports reconcile across computers. An absent input does not silently erase previously imported history.
6. The overview refreshes transactionally and shows a receipt: source revisions, added/unchanged/corrected/conflicting observations, totals before/after, and last successful import. Local report readiness and overview synchronization are separately visible. The common store is disposable; retained source batches and metadata allow rebuilding it.

**BI scope:** project/primary-area totals, task list and full task detail, daily consumption, model/role breakdown, keyword intersections and selected cohort comparisons. Period spend includes ongoing and failed work. Completed-task averages use full task costs and explicit cohorts. Use current classification by default, retain earlier report revisions, and distinguish observed-price history from recalculation under a common reference rate card. Subscription allocation requires its own declared pool and policy. A tag vocabulary is namespaced by product; a team field is declared business metadata, not inferred from a login.

The database is a calculation layer; it does not itself deliver a convenient interface. The proposed first viewer is one local overview with filters, a task table, daily consumption and links to the task reports. Markdown/CSV exports preserve a simple usable fallback. A hosted BI platform, accounts and dashboard administration are separate later choices. The displayed mockup specifies the useful views, not a delivered interface or an approved UI framework.

**Cost and strongest objection:** portable sources, importer reconciliation and report queries are real implementation work; DuckDB is an added analyst dependency. If small archives and mostly incremental updates make SQLite simpler, use SQLite behind the same contract. No timing or effort estimate is established yet. Parquet and a live company service add no necessary first-use value without a demonstrated volume/freshness constraint. Rejecting the source journal leaves the owner with attractive but non-rebuildable aggregate snapshots. Under D68/D82 this economics tooling is an optional extension; ordinary TFW lifecycle/status/knowledge operation acquires no mandatory runtime or portfolio authority.
