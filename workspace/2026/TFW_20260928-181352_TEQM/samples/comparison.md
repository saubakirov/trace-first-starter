# Итог проверки трёх платформ — 2026-09-29

## Вывод Координатора

Все три платформы дали рабочий путь получения числовых данных настоящих задач из локального хранилища. Для первого варианта отчёта обязательный запуск через CLI не нужен. Чтение производится снаружи сессии; её не требуется возобновлять.

Доступ к данным проверен на этой машине и указанных версиях. Устойчивый автоматический сбор после каждого завершения ещё не реализован. Эта проверка закрывает выбор доступного источника; незакрытые детали становятся конкретными требованиями к сборщику.

Здесь разные задачи, модели, объёмы работ, стадии и способы координации. Их абсолютные суммы не определяют, какая платформа эффективнее. ROBBIE показывает вложенных субагентов; Codex и Antigravity — отдельные сессии ролей. Это полезные разные случаи для одного формата учёта.

## Что принять и что исправить

### Codex

- Локальный источник найден и использован: наблюдаемые накопительные счётчики, разбиение по input/cache/output/reasoning, модели из turn_context и временные события.
- Повтор одного накопительного значения не создаёт новый расход. Положительные приращения сошлись с last_token_usage; финальные суммы по сессиям, моделям и дням совпали.
- 45,13 ч UPM и 4,47 ч DARYN — сумма duration_ms завершённых ходов, включая инструменты и ожидания внутри хода. 8 и 2 незакрытых хода соответственно исключены из длительности, но их наблюдаемые токены включены.
- Условные $690,23 и $127,81 — единый сценарий API Standard / short, не подтверждённые списания и не доли подписки.
- Текущее имя фазы в названии сессии не делит её исторический расход между фазами. Привязку надо сохранять при запуске и смене роли/фазы.

### Claude

- Второй образец подтвердил сбор соседней основной сессии и трёх её субагентов. Ограничение get_usage.context не является отсутствием токенов в Desktop: нужные поля лежат в локальных JSONL.
- Дедупликация нужна по ID ответа; блоки одного ответа могут повторять usage и постепенно увеличивать output. Для проверенного образца автор использует финальное/максимальное значение, а не сумму строк. Общий сборщик должен проверять согласованность ревизий, полноту ID и отсутствие родительского дублирования.
- Пересчёт сохранённого snapshot: 420 274 576 токенов, API-эквивалент $184,9487669. Это подтверждает арифметику образца, не полноту скрытых запросов compaction/advisor.
- **7,87 агенто-часа — эвристика по промежуткам между записями до 5 минут.** Её нельзя записывать как измеренное время работы наравне с Codex duration_ms. Длительность наблюдения 11,06 ч — ещё один отдельный показатель.
- Тарифы Fable 5.1, Opus 5.5 и Sonnet 5 сверены с [актуальной официальной таблицей Anthropic](https://platform.claude.com/docs/en/about-claude/pricing). Допущение автора о Sonnet 5 cache-read $0,20/млн подтверждено. Денежная оценка остаётся сценарием стандартного API: фактическое обслуживание/подписка этим не подтверждаются.
- Файлы читались последовательно без единого фиксированного cutoff; snapshot содержит последнюю запись 19:09:18.664Z при округлённом обозначении 19:09:18Z. Для работающих сессий будущий сборщик должен сохранять границу каждого источника.
- Отдельный JSON полезен как исходный материал этой проверки. Продуктовый итог по утверждённому контракту остаётся одним economics.md со встроенными структурированными данными.

### Antigravity

- Самый цельный из присланных примеров: завершённая продуктовая задача, семь отдельных сессий, роли и фазы, расходы сбора вынесены отдельно.
- **Цена $4,1594 рассчитана по неверным ставкам для gemini-3.8-flash.** На 2026-09-29 [официальный Standard API](https://ai.google.dev/gemini-api/docs/pricing) до 31.12.2026: $0,75/млн входа, $0,075/млн cache-read, $3,75/млн выхода с thinking.
- Если принять предоставленную автором трактовку f2 как fresh input и f5 как cache-read, соответствующая оценка токенов = **$14,49500865**, примерно **$14,50**. Это условный пересчёт, исключающий неизвестную стоимость хранения кэша, внешних инструментов и подписки.
- **10,08 ч — сумма промежутков от первой до последней записи семи сессий**, включая паузы. Это session span, не доказанное активное время агентов. Отдельно автор получил 51,46 мин model duration и календарный срок 7 ч 37 мин.
- Равенство f3 = f9 + f10 проверяет арифметику выхода. Оно само по себе не доказывает названия остальных внутренних полей или правила биллинга. Декодер protobuf и его соответствие версии должны быть явными в адаптере.
- Формулировку «прямой счёт равен нулю или неизвестен» не принимать: в общем отчёте фактический счёт здесь unknown. Заявление об экономии 61,3% также не переносить — оно опирается на неверный тариф и условный сценарий.

## Кто проще

По полноте первого человеческого отчёта выделяется Antigravity. По простоте программного чтения у Codex и Claude преимущество: счётчики имеют именованные поля JSON. Antigravity требует SQLite и декодирования внутреннего бинарного формата. Сравнительных замеров сложности сопровождения или скорости реализации нет; «Antigravity лучше во всём» из этих примеров не следует.

## Рекомендуемая первая реализация

```text
При старте роли: task / phase / role <-> platform / session ID
                                  |
                 +----------------+----------------+
                 |                |                |
             Codex JSONL     Claude JSONL    Antigravity SQLite
                 |                |                |
                 +------ числовые адаптеры ---------+
                                  |
           проверка повторов / нормализация / датированный тариф
                                  |
                3–5 keywords + одна основная область
                                  |
             economics.md задачи и каждой фазы
                                  |
              сводка по проектам и выбранному периоду
```

1. Числа, повторные записи, тарифы и суммы обрабатывать обычным кодом; сохранять источник и неполноту.
2. Связь задачи с сессией фиксировать при запуске роли. Историческое обнаружение оставить отдельным способом восстановления.
3. Модель использовать для 3–5 предметных keywords и основной области, опираясь на задачу и результаты. Сохранять модель/версию TFW/способ координации отдельно от продуктовых тегов.
4. Время снабжать видом и методом: duration события, модельная длительность, span сессии, срок задачи или эвристическая оценка. Отсутствующее значение — unknown.
5. На завершении обновлять economics.md, включая расходы классификации/отчёта с явным cutoff. Повторный сбор тех же событий не увеличивает итог.
6. Базовые признаки результата и переделок брать из status/RF/REVIEW. Количество токенов само по себе не является качеством; универсальную оценку команды эта первая версия не вводит.

Новый общий ресерч и искусственная задача для доказательства доступа не нужны. Следующий документ — конкретный TS автоматического сбора и общего отчёта. Утверждение TS, запуск реализации и проверка результата остаются следующими отдельными действиями.
