## 1. Vision 🔒 FROZEN

Installing or updating TFW moves only the framework — about one megabyte — instead of the whole
development repository and its history, however large that repository grows. The shipped
instructions name one way to fetch it, so no agent improvises a download or rediscovers the same
trap in each project, and an update spends its time on the receiving project rather than on
material it will never install. When a newer release exists, the Coordinator says so in one line
when new work starts; the owner decides whether and when to update.

**Impact:**

- A new user's first contact with TFW transfers ≈1 MiB of framework instead of ≈123 MiB and 3,902
  files of the framework's own task history.
- Every update in every receiver transfers ≈0.6 MiB instead of ≈114 MiB; the development
  repository's growth (26× in two months) no longer reaches receivers.
- A receiver that falls behind is visible at the moment work starts, instead of lagging silently.

> *Imagined quotes, not testimony:*
> — new user: "I asked my agent to set up TFW; it pulled less than a megabyte, and my project got the
> framework and nothing of anyone else's history."
> — owner: "I opened a project I had not touched for two weeks; the first line said it was eleven
> releases behind, and the update took minutes instead of a hundred megabytes."

## 3. Target State (To-Be) 🔒 FROZEN

1. **Light fetch is the written method.** `update.md` names one exact way to obtain only the
   framework-owned payload of the pinned object, and a disclosed fallback when an environment cannot.
   The existing pin and provenance guarantees stay as they are: operator-named tag, `VERSION` equal
   to the tag, full SHA recorded, immutability recheck, no reading of live source `HEAD`.
2. **Light install.** `.tfw/quickstart.md` and the root README install prompts obtain only what a new
   receiver installs (`.tfw/` and edition material), never the whole repository or its history.
3. **Release archives carry only the framework.** A source archive of any release — GitHub
   "Download ZIP" or a tag archive — contains the framework material and nothing of `workspace/`,
   `tasks/`, `docs/` or other development content. It also gives a one-link fallback where the Git
   method is unavailable.
4. **Version line at new-task start.** The new-task startup card shows the installed version and the
   newest release at `tfw.upstream`, from one short check. When newer exists it offers `/tfw-update`
   now or after the current task. It never updates by itself; a failed check shows as unknown and
   blocks nothing; pre-release tags do not count; the upstream repository itself shows no offer.
5. **Update time goes to the receiver.** The update neither transfers nor examines non-framework
   content. If research shows that the procedure's own repeated steps dominate update time, bounded
   removal of those steps is in scope, without weakening preservation of receiver state and
   customizations, pinning or owner decisions.

**Non-goals:** moving or rewriting the repository's task history or evidence (a separate hygiene and
evidence-limits task); GitHub Releases, e-mail or any other push notification; background, scheduled
or per-session checks; hooks, scripts or any shipped code; plugin distribution (APD); the Assisted
edition update; automatic updating; incremental "changed files only" transfer (the whole framework
is ≈0.6 MiB).

## 5. Definition of Done (DoD) 🔒 FROZEN

- ✅ 1. A fresh agent following the shipped `update.md` updates a scratch receiver while transferring
  only the framework payload of the pinned object: under 2 MiB for the current payload (measured, not
  estimated), and every framework-owned file hash-equal to the pinned tree.
- ✅ 2. The method, or its disclosed fallback with the reason, is observed in Windows Git Bash and
  Windows PowerShell; the Codex sandbox is observed or reported unavailable with the reason;
  unobserved environments are named as unobserved.
- ✅ 3. The pin and provenance guarantees of `update.md` are unchanged in meaning.
- ✅ 4. A fresh agent following `.tfw/quickstart.md` or the root README installs TFW into an empty
  scratch project, transferring under 2 MiB, and the installed `.tfw/` equals the tag's framework
  payload minus the documented project-state exclusions.
- ✅ 5. A local `git archive` of the Candidate commit contains only framework material and stays
  under 1 MiB compressed; the GitHub archive is observed after the owner's separate push or stated as
  unobserved.
- ✅ 6. The startup card's version line is observed when the receiver is behind, current, offline or
  unreachable (unknown within a few seconds, nothing blocked) and in the upstream itself; it never
  starts an update.
- ✅ 7. Either the RF lists each removed or shortened update step with its measured cost and why
  preservation holds, or it records with evidence that no procedure change was warranted.
- ✅ 8. `update.md` stays within the ≤1400-word workflow rule; adapter copies are byte-equal; no new
  shipped script, hook, dependency or required tool beyond Git.
- ✅ 9. Independent REVIEW APPROVE, owner acceptance and a truthful changelog entry.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. A receiver gets any path outside the framework payload, or its project state, configuration
  or customizations are overwritten.
- ❌ 2. The method falls back to a full download silently, or byte identity is claimed without
  verification.
- ❌ 3. The version check delays new-task start materially or fails it offline, or any update happens
  without the owner.
- ❌ 4. Shipped code, a hook, a script, a service or a new required tool is introduced.
- ❌ 5. A verification step that protects receiver state is removed for speed.
- ❌ 6. Repository history or evidence is moved or rewritten, or a private receiver name or machine
  path enters this public repository.

**On failure:** stop the affected change and keep the current wording; the finding returns to the
Task Coordinator; any change to a frozen claim goes to the owner through §12.

## 7. Principles 🔒 FROZEN

1. **Only the framework travels.** A receiver never downloads, stages or examines material it will
   not install.
2. **One written method, no improvisation.** The shipped text names the exact method and its
   fallback, so no agent has to rediscover them.
3. **Prompt methodology, no code.** Every change is instruction text or plain configuration.
4. **The owner decides updates.** The version line informs; the operator names the version.
5. **Subtract before adding.** Each added line replaces vaguer text or removes a step.
6. **Host-neutral correctness.** The primary method works with any Git host; a host-specific archive
   link is only a fallback.
7. **Honest limits.** Unobserved environments and effects are named as unobserved.

## 10. RESEARCH Case 🟢 FREE

### Blind Spots

- Which light-fetch method is robust across Git versions, shells, sandboxes and proxies.
- Where the update session's time actually goes.
- Whether init or quickstart needs root files beyond `.tfw/` and `editions/`.
- Whether any maintainer procedure depends on today's full-tree archive behaviour.

### Hypotheses

| # | Hypothesis | Status |
|---|----------|--------|
| H1 | One Git method (partial clone limited to framework paths, or blobless clone plus `git archive --worktree-attributes`) transfers under 2 MiB and yields byte-identical framework files in Windows Git Bash, Windows PowerShell and the Codex sandbox. False case: an environment lacks support or converts line endings → the archive link becomes the documented fallback or primary. | open |
| H2 | Download is a minority of update duration and the procedure's repeated steps (triple re-hash, project checks that `.tfw/` cannot affect, oversized receipts) dominate. False case: the download dominates on ordinary networks → no procedure change; true case → a bounded removal list. | open |
| H3 | A latest-release check via `git ls-remote --tags` costs about a second and fails fast offline and in sandboxes. False case: it can hang for tens of seconds or is blocked → the rule states an explicit limit or skips the check where network is known to be absent. | open — partly observed (1.1–1.3 s; bad host 0.3 s) |
| H4 | Install needs only `.tfw/` and `editions/` (plus the README files and LICENSE for archives). False case: init or quickstart reads other root files → list them explicitly. | open |

### Risks of Not Researching

A method that fails in the Codex sandbox or rewrites line endings on Windows would ship a broken
update step to every receiver; guessing where the time goes could remove protection for nothing.

### Proposed RESEARCH Focus

1. **Gather**: run candidate fetch and install methods in scratch directories in each available
   environment; measure transferred bytes and time; hash-compare against the tag tree; check every
   `git archive` use in maintainer procedures.
2. **Extract**: time a trial update of a scratch receiver copy step by step under the current rules.
3. **Challenge**: what can be dropped (for example, whether `.tfw/.upstream/` staging is needed at
   all) and what would make the chosen method wrong.

### Why Not Just...?

| Approach | Value | Adoption / operating burden | Risks / tradeoffs | Decision and reason |
|---|---|---|---|---|
| Exact Git method in shipped text + archive-only `.gitattributes` (recommended) | ≈0.6–0.8 MiB per update, ≈1 MiB install, ≈0.5 MiB ZIP instead of 178.9; host-neutral primary | Text plus one small attributes file | Environment support (H1); first update still old | Recommended: fixes the cause where it arises, adds one small file that also serves ZIP users and the fallback |
| Archive link only (tag archive via GitHub, no Git method) | ≈0.5 MiB; no Git needed to download | Instructions only | Couples correctness to one host; integrity check of an archive is weaker | Kept as fallback, not primary (NS3, principle 6) |
| Release asset attached to each GitHub Release | ≈0.5 MiB; enables watcher e-mails | An extra release step every time; needs Releases | Assets are replaceable after the fact; checksums needed | Rejected: more ceremony per release |
| Move task history out of the public repository | Smallest clone for everyone | A large separate task | Breaks trace links; old history stays in Git objects | Out of scope: separate hygiene and evidence task |
| Version notice by GitHub Releases or e-mail | Informs external watchers | An extra release step | Useless to the owner, who authors releases | Not selected by the owner |
| Weekly summary across the owner's projects | Portfolio view | Scheduled job on one machine | Not portable, not framework | Not selected |
| Session-start hook | Automatic | Code in every receiver | Violates prompt-only and portability | Rejected |
| Check at task close instead of start | Update lands at the safest moment | Same cost | Many tasks never close; the check comes after the task already ran on old rules | Not selected; the start line offers "after this task" instead |

**Leave unchanged:** every update in every receiver keeps transferring ≈114 MiB and growing with
the development repository, every install ≈123 MiB with full history, agents keep improvising and
diagnosing the fetch, and receivers keep running old versions unnoticed.

**Critical challenge:** the strongest objection is that the download may be a minority of update
time: if R1's ten minutes of apply were spent on re-hashing, project checks and a long receipt,
removing 113 MiB saves a minute and the update still feels slow. H2 tests this, and §3 claim 5
admits bounded removals only with evidence. A second objection: this changes only what
follows TFW's own instructions — a manual `git clone` of the repository or its GitHub page still shows
the full history, which only the separate hygiene task can change. Against the owner's "only the
fresh part" idea: once only the framework is fetched, the whole framework is ≈0.6 MiB, so transferring
only changed files would save a fraction of a megabyte at the cost of new complexity. Against
"check every time": the check is a 3 KB request of about a second, once per new task; it becomes
noise only if repeated per message or per session, which §3 claim 4 excludes.
