## 1. Vision 🔒 FROZEN

Maintainers can make a legitimate change to this repository without unrelated tests turning it into a long repair campaign, and TFW users can finish a task without restarting review just to correct its closing records. The Saint-Exupéry principle determines the design: unnecessary tests, build dependencies and repeated closing obligations have been removed, while checks that detect real defects and independent review remain. Every remaining check or closing step has an explainable purpose, and earlier evidence is usable when it still supports the final result.

**Impact:** Maintainers have less test machinery to run and maintain; task owners spend less time and agent work on repeated verification and administrative recovery. They retain confidence that a real defect will not be ignored and that DONE names a checked, usable result. Success means removing unnecessary work at its cause, not merely running the same bureaucracy faster or deleting useful safeguards.

> Stakeholder-perspective target, not a verbatim quotation: “A harmless correction no longer costs me another review campaign. A real defect still gets caught, and finished really means ready.”

## 3. Target State (To-Be) 🔒 FROZEN

PTTC delivers two connected changes: **a simpler test system in this repository** and **a simpler way to finish work under Full TFW**. The first removes unnecessary verification work; the second prevents closing records from generating that work again.

| Phase / where the result lives | What will actually change | Why it matters |
|---|---|---|
| **A — this repository:** test code in `docs/scripts/` and `tools/tests/`, plus existing project verification guidance and commands where needed | Remove obsolete or duplicated checks; separate checks of text and Git data from checks that need a built website; keep historical acceptance from freezing today's wording and releases. Explain which checks a change needs and when earlier results still apply. | A maintainer can make a legitimate correction without an unrelated site build or a test that rejects the change merely because it differs from an old snapshot. Real integration defects remain detectable. |
| **B — Full TFW:** existing conventions, closing/review/knowledge workflow instructions and their templates; synchronize affected adapters | Distinguish a changed deliverable from a mistake in its closing record. Verify final changes made during documentation or knowledge capture, repair incomplete records without restarting unchanged product work, and name who handles a real defect. | The owner gets a finished, checked result instead of another paperwork-driven review cycle. Other projects use these rules with their own checks, without installing this repository's test infrastructure. |

Before retaining or adding a mechanism, identify the harm it prevents and whether a simpler design removes the need for it. The phase TS fixes the exact implementation and verification boundaries. No new test-runner platform, global status store, universal test-count cap or mandatory executable for receiving projects is part of the result.

### 3.2 Value Flow

**How the changes above save work without hiding defects:**

```text
A change arrives
  |
  v
Name what could be wrong because of this change
  |
  +-- Earlier evidence still covers it?
  |     Reuse only results whose relevant inputs, test and environment still apply.
  |
  +-- Something relevant changed or is not yet proved?
        Run the checks needed for that risk; use a build when output is involved.
  |
  v
Independent review checks the result and the applicability of its evidence
  |
  v
Complete required documentation / knowledge capture
  |
  +-- It changed the accepted deliverable --> check the affected final output
  |
  +-- Only a closing record needs repair --> repair and validate that record
  |                                         preserve the earlier event
  v
All required work is satisfied; status, outcome and references are complete
  |
  v
DONE: the final result and the grounds for accepting it can be inspected
```

Phase A removes checks and build dependencies that serve no relevant risk. Phase B removes repeated closing obligations when the accepted work has not changed. A real defect, changed authority or insufficient evidence returns to the responsible Coordinator/Executor/Reviewer for the affected work; it cannot pass through the record-only branch. A purely administrative correction creates neither a new product requirement nor a knowledge candidate by itself.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. A test is removed, loosened or muted only to obtain green results, or user knowledge is rewritten to satisfy a stale oracle.
- ❌ 2. Savings rest on omitted necessary checks, unproven cache validity, different benchmark conditions, double-counted time or invented token costs.
- ❌ 3. Tests of strings or a self-authored instruction interpreter are presented as proof of actual agent compliance.
- ❌ 4. DONE precedes required final-output checks, or record repair regenerates an unbounded closure obligation without a material changed claim.
- ❌ 5. The result only accelerates unnecessary machinery, layers another control over an avoidable cause, or adds complexity without establishing its protective consequence and considering a simpler adequate alternative. A universal runtime, counter or repeated monitoring service remains outside scope.
- ❌ 6. PTTC silently rewrites incident history, weakens authority/reviewer independence, changes CRUE-owned release policy, or imports this repository's test environment into receiving projects.

**On failure:** Preserve the observed failure and current honest state; route a concrete breached criterion to the proper owner. Reconsider the mechanism rather than hide the failure, expand the experiment silently, or manufacture an owner decision.

## 7. Principles 🔒 FROZEN

1. **Saint-Exupéry — the governing design principle:** seek the simplest complete and coherent verification and closure system. First ask whether a mechanism is needed, what can disappear, and whether removing the cause eliminates the control. Retain necessary protection; add only what a simpler adequate design cannot provide. Mechanical deletion, shorter prose, fewer files or faster runs alone do not prove improvement. Simplification must preserve purpose, value, correctness, architecture, modularity, inspectability and continuation. This principle governs research, both phases and acceptance, including PTTC's own process.
2. **Protected consequence and risk before assertion or diff size:** distinguish semantic judgment, structural validity and real integration; neither one character nor a TRACE/ASSURANCE label proves harmlessness.
3. **Existing evidence is an input, not an exemption:** reuse only what still supports the actual claim; independent review is judgment, not ritual full-suite duplication.
4. **Final state follows final effects:** capture and its affected-output checks precede a valid close; genuine new defects can reopen bounded work.
5. **One owner per rule:** portable methodology stays in canonical files; project commands and infrastructure stay project-owned.
6. **Cost includes attention:** measure useful protection and avoidable agent/owner work, not test count alone.
7. **Bound the experiment prospectively:** approve representative cases, measurements and stop rules before spend; measured limits are not universal quotas or targets.
8. **No unapproved publication:** announce readiness and await the owner's separate final approval before any PTTC-related push or release publication.
