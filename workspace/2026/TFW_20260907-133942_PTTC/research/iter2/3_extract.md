## Findings

### E1: Shared output setup versus pure-family separation

The actual dependency boundary is between tests that read generated site/ output and tests that inspect source, Git objects, task files or temporary state. The current module declares build_site with module scope and autouse=True, then places both classes in the same module. The source therefore supports two concrete constructions:

| Construction | Preserved behavior | New obligation | Failure mode if chosen poorly |
|---|---|---|---|
| Explicit opt-in in the existing module | Keep the existing module-scoped fixture and one shared site build for every output consumer that explicitly requests it; pure tests request nothing. | Identify every real output consumer and add explicit fixture use; record the consumer set in future evidence. | A missed consumer can fail at its own output assertion; an overbroad fixture parameter recreates the coupling. |
| Move the pure family to a separate module | Leave the output module's shared autouse setup intact and place pure source/Git checks where no site fixture applies. | Create or use an actual module boundary and preserve imports, names and evidence attribution across the move. | A cosmetic split can add topology without removing a hidden dependency, or can revive/rename superseded tests during relocation. |

The official [pytest fixture guidance](https://docs.pytest.org/en/stable/explanation/fixtures.html#autouse-fixtures-fixtures-you-don-t-have-to-request) states that fixture services are accessed through test-function arguments, that fixture scope can be module-wide, and that autouse fixtures are activated without a request. It also cautions that unnecessary dependencies can prevent a useful test from being attempted when an unrelated fixture errors. Applied to this source, explicit opt-in is the smallest sufficient construction when the existing module can enumerate output consumers: it removes autouse from the shared fixture without changing its module scope, so it does not imply one build per HTML test. Moving the pure family is a valid fallback only if the consumer list cannot be made explicit without ambiguity; it is not required for visual neatness.

**Provisional extracted boundary:** retain one shared module-scoped setup for genuine output consumers, make its use explicit, and leave pure checks without a site prerequisite. This is a candidate for Challenge, not an implementation instruction or executed result.

### E2: Knowledge oracle with protected meaning and flexible explanation

The current Phase E predicate has two distinct jobs:

1. structural/provenance protection: exactly one selected row, stable decision identity, task/phase lineage, selected Git-object references and the current/superseded relation;
2. selected-string sensitivity: rejection of known attribution, state and historical/current mutants.

The first job protects the knowledge claim. The second is useful as a finite regression guard for named failure modes but cannot define semantic equivalence for arbitrary prose. A full-row exact snapshot therefore overclaims, while unrestricted prose flexibility under-specifies lineage. The smallest coherent boundary extracted from both RES reports is:

| Field class | Extracted treatment | Why |
|---|---|---|
| Decision key and row cardinality | Immutable structural predicate: one row for each selected decision and no duplicate replacement | Prevents loss, duplication and silent identity change. |
| Task/phase lineage and current/superseded relation | Protected predicate, with explicit source revision | Prevents a valid successor from being relabeled as an old artifact or an old artifact from becoming the current claim. |
| Required immutable source/reference identities | Protected exact references to named Git objects or required artifacts | Preserves replayable historical evidence and provenance. |
| Attribution relation when it is the claim | Protected distinction between acting-principal attribution, working-unit identity and proposal origin where the decision relies on it | The audit's attribution mutant can alter authority meaning; this is not a harmless wording edit. |
| Explanatory prose, citation wording and non-authoritative description | Current semantic content, not blanket byte equality; changed meaning returns to the appropriate Reviewer/Coordinator/owner route | Avoids freezing incidental wording while keeping material changes visible. |

**Provisional extracted boundary:** REWORK the full-row oracle into this hybrid protected-field predicate plus a named semantic review branch for changed meaning. Keep the existing selected counterexamples as regression evidence. Do not create a general semantic validator, a registry or a cache. A fake or unverifiable SHA, authority or lineage reference is not a benign wording change; it is indeterminate or material until the responsible owner resolves it.

### E3: Board-regex guard and historical wrapper

The board-regex check protects a distinct source-level consequence: generator code must not reintroduce the retired root-board parser. It scans generator source lines, skips comments and exempts the migration and test scripts. It does not prove generator behavior, generated output correctness or agent compliance. The current source and Python search semantics support this narrow classification:

- **Provisional board-regex disposition: KEEP narrowly.** Keep it as a pure source guard, move it out of the site-build dependency through explicit fixture use, and document its scope as prevention of the retired parser pattern. Do not promote it to a semantic or runtime proof.
- **Provisional historical-wrapper disposition: KEEP as a thin compatibility entrypoint.** The later same-name definition delegates to the revision-2 predicate, so it preserves a historical selection name without reviving the superseded body. There is no in-repository caller evidence for an external public API; that is a bounded uncertainty, not an automatic debt item. If a future change removes the wrapper, a named consumer or material consequence must be supplied before treating the removal as a defect.

This pair is deliberately asymmetric: the regex has a distinct current architectural consequence visible in the source; the wrapper has a compatibility consequence visible in the name/delegation shape but no proven external consumer. Neither disposition authorizes code changes in this research stage.

### E4: One closure-record integrity obligation, with two materiality branches

Administrative carrier repair and a terminal record missing an outcome test the same underlying obligation: the closure record must truthfully identify the completed claim and its result. They should not become two separate trials merely because one is phrased as a repair and the other as an absent field.

| Branch | Affected claim | Minimal evidence | Owner and stop/return |
|---|---|---|---|
| Record-only defect | No change to accepted output, oracle, authority or relevant dependency; the carrier has a missing outcome, malformed link or correctable record field. | Exact carrier path, source revision, owner/authority, repaired field and preserved history; no fake identity is accepted as verified. | Coordinator validates the task-local carrier and journal; Reviewer is not reopened solely for unchanged record repair. Stop after exact validation. |
| Material or indeterminate record | SHA, authority, output identity or lineage cannot be verified, or capture changed an accepted output/oracle/authority. | Exact affected output, source/oracle revision, evidence applicability and completed bounded output check. | Reviewer routes material change; Coordinator records the return; owner rules reserved authority changes. Stop after the first complete affected-output result and one existing material return, or report incomplete at the approved cap. |

**Provisional extracted boundary:** call both branches closure-record integrity; administrative repair is benign only after unchanged claim/oracle/authority is established. No numeric return quota, bookkeeping-only loop or third probe is introduced.
