## 1. Vision 🔒 FROZEN

Every task-bound TFW session now enters through a reliable command contract: the intended canonical workflow is actually loaded, its role and ordered gates govern the run, and only then does the session receive a concise, evidence-selected sidebar title. The exact entry architecture and title grammar are chosen after competing explanations and alternatives are tested, not from the Coordinator's preference.

**Impact:** A person coordinating several agents can distinguish them without opening chats, while each agent follows the correct role workflow rather than improvising from the request or a weak entry cue. This reduces wrong-session instructions, skipped gates, role confusion, repeated explanations, and time spent checking which agent owns which work.

> “I can tell you apart by role, task, and phase before I open the chat.”

The final sidebar uses one researched grammar. The three slots below state the information outcome, not their still-open wording:

```text
[WORK CUE] · [TASK CUE] · [PHASE CUE, WHEN NEEDED]

The owner sees, without opening a chat:
  what this session is doing · which task it belongs to · which phase it owns
```

Research must determine whether the work cue should be a formal role, exact skill, workflow function, or hierarchy marker; whether the task cue can safely use `ABBR`; and whether a bare phase token is sufficiently clear in a fixed position. Extra title fields or entry prose are admitted only when they materially improve recognition or compliance rather than decorate the interface.

## 4. Phases 🔒 FROZEN

This is a two-phase task. Reliable command entry is foundational: a naming rule inside a workflow has no dependable effect if the slash-command entry does not load or continue to obey that workflow. Session naming is a separate, user-visible result and can be reviewed without conflating it with the entry architecture.

### Phase Dependencies

```text
Phase A — Command entry reliability
    │   proves how a command reaches one canonical algorithm and binding Role Lock
    ▼
Phase B — Session identity ergonomics
        places the researched naming action at satisfiable points in that algorithm
```

| Phase | Depends on | Shared files | Can run in parallel with |
|---|---|---|---|
| A | Independent | `.tfw/workflows/**`, `.tfw/adapters/**`, installed command receivers | — |
| B | A | The workflow and receiver set selected by Phase A | — |

### Phase A: Command entry reliability 🔴

1. Census all 11 `/tfw-*` commands, their canonical workflows, and the four adapter definitions in the manifest; record declared, installed, and non-installed routes separately.
2. Compare the current entry topology with the pre-RCFR baseline and determine what actually changed in wording, copied context, authority, and runtime behaviour.
3. Distinguish four failure classes with evidence: the skill/command was not invoked; the canonical workflow was not loaded; the workflow did not cover the encountered path; or the workflow was loaded but its role, sequence, or gate was not followed. Keep room for a fifth, evidence-discovered cause.
4. Compare at least: byte-identical workflow copies, the current thin proxy, a stronger minimal proxy with explicit pre-action load/order/Role-Lock/stop language, and any viable direct single-authority design found by research.
5. Measure each candidate by behavioural adherence, effective startup words/tokens including double reads, distribution drift and parity risk, adapter portability, maintenance cost, and the observability of its claim. Do not assume that a full copy costs more runtime context: it may replace a proxy-plus-workflow read.
6. Preserve one canonical workflow as the algorithm authority and one binding role per command. Adapter material may copy or dispatch that authority but must not invent a second algorithm.
7. Produce an evidence-backed entry contract for every command/adapter class, including an honest limitation where the host cannot expose whether a read occurred or whether a later response remained compliant.

### Phase B: Session identity ergonomics 🟡

1. Research and define one compact, provider-neutral title grammar and its resolution rules rather than selecting words by Coordinator preference.
2. Cover new and existing tasks across every task-bound TFW workflow, including planning, resume, research, execution, and review paths.
3. Resolve the task and phase from authoritative task state when present, not only from explicit user wording.
4. Preserve the current question-first creation sequence: a new task is named only after its approved identifier exists.
5. Specify a non-blocking, explicit fallback when the host cannot rename the session.
6. Compare formal role, skill name, workflow function, task-first order, task abbreviation, full identifier, phase markers, symbols, separators, and lead-session labels under real sidebar constraints.
7. Verify coverage from the actual workflow and adapter surface rather than a manually assumed file list.
8. Preserve context compression: no new universal preload and no unmeasured growth hidden across source and copies.
9. Keep `Main Coordinator` and any new role model under CRATM; RTPSN may evaluate visible labels for an already-defined hierarchy but creates no role or authority.

## 6. Definition of Failure (DoF) 🔒 FROZEN

- ❌ 1. The task declares thin proxies to be the cause merely because a failure occurred after RCFR, or treats the two observed incidents as proof that `plan.md` was not loaded.
- ❌ 2. A loaded workflow is counted as an obeyed workflow, or static source parity is presented as behavioural compliance.
- ❌ 3. Full workflow copies are restored without measuring startup context and drift cost, or a stronger proxy is shipped on wording alone without behavioural evidence.
- ❌ 4. An adapter copy or wrapper introduces role logic, gates, or an algorithm that can disagree with the canonical workflow.
- ❌ 5. Only the observed CRATM `/tfw-plan` symptom is patched while another command, role, resumed path, or adapter class still has the same unclassified boundary.
- ❌ 6. The Coordinator freezes `PLAN · CRATM · A`, `LEAD`, or any other preferred wording before alternatives are researched and challenged.
- ❌ 7. A title is composed before the task identifier or phase is authoritatively known, or chat wording, a directory guess, an index, or agent memory outranks task state.
- ❌ 8. Compactness destroys task uniqueness, phase clarity, accessibility, searchability, or cross-host rendering without a declared fallback.
- ❌ 9. Failure to rename blocks valid work, or a workflow claims that renaming or command compliance occurred when the host did not expose evidence.
- ❌ 10. A new always-read file, registry, daemon, hook, or session-management subsystem is introduced without measured value that exceeds its context and maintenance cost.
- ❌ 11. The task introduces or changes `Main Coordinator`, role permissions, delegation, channels, worktrees, or session ownership.
- ❌ 12. The solution silently regresses RCFR context reduction or expands startup prose without recording and justifying the resulting word/token cost.

**On failure:** stop the phase, preserve the evidence, and return the contract or implementation boundary to the Coordinator. Do not ship a one-host workaround as the provider-neutral TFW rule.

## 7. Principles 🔒 FROZEN

1. **Causality before remedy** — reproduce and classify the failure before choosing copies, proxies, or stronger wording.
2. **One canonical algorithm** — the workflow owns ordered reads, role, gates, and stops; an adapter only makes that authority reliably reachable.
3. **Role Lock before task action** — the command entry must bind the declared role before planning, research, execution, review, or durable writes begin.
4. **Invocation, load, coverage, and compliance differ** — evidence for one must never be used as proof of the others.
5. **Research before vocabulary** — a plausible compact label is a hypothesis until alternatives survive evidence and challenge.
6. **Resolve before naming** — a visible identity is useful only when every component is known rather than guessed.
7. **Recognition before formalism** — the sidebar title serves rapid human orientation; formal authority remains in artifacts and Role Locks.
8. **Proportionate assurance** — spend context only where it measurably improves adherence; never hide the token, money, time, or maintenance cost of assurance.
9. **Resume is a first-class entry** — continuing existing work must receive the same command and identity guarantees as creating new work.
10. **Capability honesty and bounded adjacency** — disclose unsupported behaviour, and leave CRATM role topology and orchestration unchanged.

## 10. RESEARCH Case 🟢 FREE

### Blind Spots

- Which visible cue produces faster, less error-prone recognition: formal role, exact skill, workflow function, task-first label, or a hierarchy marker?
- How much title width is actually visible in supported sidebars, and how do ASCII, Unicode, emoji, search, and truncation behave?
- Can the approved task abbreviation replace the whole identifier without unacceptable collisions or loss of traceability, including legacy identifiers?
- Is a bare positional phase (`A`, `A3-Q-R`) self-explanatory, or does it need `Phase`, `Ph.`, punctuation, colour, or a symbol?
- How should a lead session differ from master planning without RTPSN inventing CRATM authority?
- Which supported hosts let an agent rename the current session, and at what satisfiable point does each task-bound workflow know its inputs?
- Did RCFR introduce a measurable command-entry regression, or did recent failures expose a pre-existing workflow coverage or post-load compliance problem?
- What evidence can distinguish slash-command invocation, canonical file loading, algorithm coverage, and later adherence in each host?
- What is the net effective startup-context and distribution-drift tradeoff of a byte-identical full copy compared with a stronger proxy or direct canonical entry, and does it improve behaviour?
- Why does the current manifest declare plural `.agents/workflows/` while the tracked Antigravity receivers use singular `.agent/workflows/`, and which path is actually authoritative and live?

### Hypotheses

| # | Hypothesis | Status |
|---|---|---|
| H1 | A short workflow-function vocabulary such as `PLAN`, `RESEARCH`, `EXEC`, `REVIEW`, and a distinct lead cue is recognized faster and more accurately than formal role names or exact skill names without implying false authority | needs-research |
| H2 | A compact positional grammar can use the approved task abbreviation and a short or bare phase cue — candidate `PLAN · CRATM · A` — while deterministic collision and fallback rules preserve recognition, searchability, rendering, and traceability better than full IDs or longer role-first/task-first forms | needs-research |
| H3 | Recent deviations reflect a measurable command-entry regression introduced by changed entry cues; alternative explanations are a command not invoked, a canonical workflow not loaded, an uncovered algorithm path, post-load noncompliance, or another evidence-discovered cause. Current evidence weighs against pure non-loading in the two observed incidents | needs-research |
| H4 | One of byte-identical full copies, current thin proxies, strengthened minimal proxies, or a direct single-authority entry yields materially better cross-role adherence and total value; compare the full net tradeoff because a full copy may remove a proxy read while increasing distribution and drift cost | needs-research |

### Risks of Not Researching

Skipping research would do two unsafe things: convert one attractive title into policy without ergonomic evidence, and convert temporal proximity to RCFR into a causal diagnosis despite evidence that both observed sessions loaded `plan.md`. The result could keep paying for proxy-plus-workflow double reads, multiply distributed copies for negligible behavioural gain, or preserve a weak entry contract while polishing titles that agents never reliably apply.

### Planned Iteration Split

| Iteration | Focus | Hypotheses | Required outcome |
|---|---|---|---|
| 1 | Command-entry reliability and causal diagnosis | H3–H4 | Compare current/pre-RCFR topology and controlled role/adapter trials; distinguish invocation, load, coverage, and compliance; recommend an entry architecture with explicit cost and evidentiary limits |
| 2 | Session naming ergonomics and integrated design | H1–H2 | Consume Iteration 1 constraints, compare title candidates in realistic sidebars and task states, and recommend grammar, resolution points, fallback, and verification |

The split is ordered rather than parallel: Iteration 2 may not assume that an instruction placed in a workflow is reliably reached until Iteration 1 reports the actual boundary.

### Proposed RESEARCH Focus

1. **Gather**: census the 11 commands/four manifest adapters, current and pre-RCFR entry texts, runtime traces, fixed-context word/token costs, current session titles, identifier collisions, sidebar constraints, rename capabilities, and workflow resolution points.
2. **Extract**: build two linked configuration spaces: entry architecture × compliance evidence × context/drift cost, then work cue × task cue × order × separator × phase notation × hierarchy distinction × collision fallback × host capability.
3. **Challenge**: reproduce competing command-failure classes; test representative roles and adapters; then test the strongest title candidates against same-task multi-role sessions, collisions, legacy tasks, no phase, complex phases, resumed tasks, unsupported hosts, misleading role semantics, and truncation/search.

### Why Not Just...?

- Why not move `/tfw-plan` naming back to Step 0? — A new task has no approved identifier there; the title would require a guess.
- Why not adopt `PLAN · CRATM · A` now? — The owner likes it, but its abbreviation, separator, phase clarity, hierarchy semantics, and cross-host behaviour have not been tested against alternatives.
- Why not restore full copies now? — Codex was already proxy-based before RCFR, other adapters still use full copies, and the two observed incidents loaded the workflow. Full copies remain a serious candidate, but not a proven cure.
- Why not strengthen the proxy now? — Stronger wording is plausible, but text presence alone cannot show that the command was invoked, the file was read, the encountered path was covered, or the rule remained salient later.
- Why not add the same naming lines to every workflow? — It creates drifting copies, touches non-task commands, and increases fixed context without classifying their inputs.
- Why not let Codex auto-generate titles? — The observed CRATM title omitted role, identifier, and phase, which are the dimensions the owner uses to distinguish agents.
- Why not solve this inside CRATM? — CRATM owns role topology and session orchestration; the naming failure already exists in the base single-session workflow contract.
