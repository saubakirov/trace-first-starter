## Findings

### C1 — Command-first dispatch and authority race

Stress sequence: the Coordinator is authorized for Researcher at lifecycle `RES`, launches a new task with only `/tfw-research <task>`, and the child begins before an address can be committed to `dispatch`. Under the approved HL, the child validates task/phase status, frozen HL or exact owner-decision grant, native origin/actual launcher, Role Lock and lifecycle. The parent writes truthful destination provenance from a receipt or first gate when observed. It does not backdate an event or append an invented startup ticket. Later addressed sends require the now-known exact ID. If the native surface supplies neither a verifiable source nor a self/child ID at the point needed for durable provenance, that provider path must stop or use an owner-assisted visible launch. This is a focused change to `.tfw/conventions.md` activation/dispatch timing, Plan Step 7 and role readers, not permission to omit lineage. Current text would refuse this sequence; HL A4 explicitly authorizes the target behavior.

### C2 — GATEWAY, dialogue and live switching

Stress sequence: GATEWAY is selected with `tfw-gates-only`; it launches one planning Coordinator, receives an approved phase map, then separate ready phase Coordinators. Each worker's `coordinator_route` is its own phase Coordinator; the phase Coordinator alone uses `owner_gateway`. A worker attempting to send to GATEWAY is refused even if GATEWAY created or requested the session. A single delayed metadata liveness check may be used after silence; unchanged live status yields no owner update. Current status validation already accepts gates-only with `gateway:{address}`, but session-title and Plan text must stop requiring `iterative` for GATEWAY. Conversely, a bounded two-peer dialogue with an owner gateway must become valid under the approved independence rule, with an exact immutable peer/purpose/output/stop grant. `tools/tfw_state.py` currently rejects that combination; changing only prose would leave it invalid.

For an owner switch after research, keep the Researcher and its current route through the durable RES return. The future decision event names the next Coordinator checkpoint; only there does status adopt the new `activation`/reporting selection and cite the event before the next role launch. An immediate revocation prevents new delegated launches while the current unit stops safely and returns its actual state. A pending TS/HL owner verdict remains a gate. The smallest tested candidate is Extract S1: `activation` describes the current launcher authority, `reporting` distinguishes native from explicit owner transfer, and `selection_ref` cites the immutable owner decision when one exists; `dialogue` and `owner_gateway` stay orthogonal. Initial manual/gates-only defaults do not manufacture an owner grant. S2's separate `operating_mode` and delegated `activation` ceiling permits contradictory combinations unless every reader resolves precedence, so it adds ambiguity without protecting another named value. The exact default/legacy field grammar belongs in TS implementation, with current PCUX status untouched until that schema exists.

Across autonomous, manual and bounded-dialogue cases, the Coordinator still performs Working Backwards, structured distillation, consequential critique, owner-visible hypothesis triage, model/effort launch selection and the Saint-Exupery subtraction check. The changed `plan.md` candidate requires the separate owner verdict on its actual passages. A mode switch never turns that role into a passive command dispatcher. ### C3 — Compact independence and surface failure

An admissible compact route needs three distinct role units with exact `/tfw-*` activation, own artifacts, direct gates to their Coordinator, continuation by the same ID where a round requires it, and a Reviewer that did not produce the candidate. Sharing one checkout is compatible only with serialized writes and a fixed Candidate; a shared model, agent principal, or nested UI label does not merge or prove units. Claude documentation says `SendMessage` can resume a named/ID-based custom subagent, while name reuse is guarded only within stated versions/session conditions; exact IDs remain safer for returns and corrections. It also says a subagent message cannot grant a pending permission. These mechanisms warrant a live role-chain check, not a provider-wide full-cycle claim. [Claude Code — Create custom subagents](https://code.claude.com/docs/en/sub-agents). The owner's selected Claude report and Antigravity IDE report lack the full TFW trial; browser-dependent work remains undecidable until an accepted addendum or active-surface check. Scope or Coordinator context growth exits compact eligibility even if the phase count remains one.

### C4 — Shared-workspace and close failure sequence

Stress sequence: Claude's owner clicks a future Executor card before TS approval. The card must not be issued yet; if clicked, the role refuses at lifecycle check. At the valid gate, one local workspace is selected, the Executor becomes the only repository mutator, commits a tested Candidate and stops mutation. The independent Reviewer reads that exact SHA and returns its verdict to the Coordinator. A correction returns to the same Executor and Reviewer; any changed VALUE creates a new Candidate and new review basis. After acceptance, docs and knowledge effects are Applied or reasoned N/A, changed final claims get an independent check, and a truthful task changelog entry is part of the checked result before close. H3/H4 and a release/tag remain outside this research/close path.

For cleanup, archive of a Claude chat is not the same as removing its worktree/branch. If archive restoration depends on them, retain the exact dependency with a specific reason or obtain an authorized disposal route that gives up that restoration promise. Confirm task ownership, no live role, no unpreserved dirt, and Candidate reachability from a retained integration ref before removing any disposable tree/branch. Git documents `merge-base --is-ancestor` for checking ancestry and `worktree remove` restrictions for unclean/locked trees. [Git — git-merge-base](https://git-scm.com/docs/git-merge-base), [Git — git-worktree](https://git-scm.com/docs/git-worktree).
