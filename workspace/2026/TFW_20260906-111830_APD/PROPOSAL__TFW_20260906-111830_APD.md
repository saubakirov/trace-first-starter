## The finding

TFW Assisted 1.6 already exists as a public, self-contained Russian-language edition under
`editions/02-assisted/`. Its documented first use requires a person to copy the edition contents into a
project root, open that project in Codex, and ask Codex to initialize it. The method deliberately needs no
Python, Git, shell command, helper executable, or manual service-file editing after the copy.

The remaining adoption friction is the delivery step: finding the correct edition, copying the correct
boundary rather than the enclosing directory, receiving updates safely, and understanding whether the
installed files are a product, a template, a skill bundle, or a project contract. The owner's idea is that
an installable plugin may reduce this friction and make Assisted easier to distribute.

That idea is not yet a product decision. An OpenAI relationship, an official plugin surface, a Codex local
plugin, a ChatGPT app, a connector, a skill installer, and an independent package are different mechanisms
with different trust, permission, hosting, update, and portability consequences. Calling all of them a
"plugin" would hide the decision this task needs to make.

## The question

Should Assisted acquire an installable distribution package, and if so which supported mechanism removes
enough real user friction to justify its permissions, vendor dependency, release work, security review,
support obligation, and migration path?

The proposal must answer five linked questions before any implementation:

1. **User problem:** which observed onboarding steps fail, confuse, or discourage Assisted users, and how
   often? A packaging solution without an evidenced failure rate is convenience theatre.
2. **Available surfaces:** what Codex and ChatGPT currently mean by plugin, skill, app, connector,
   marketplace item, and project-local instruction package; which surfaces are officially publishable by
   an external maintainer?
3. **Authority boundary:** which files the package may create or update, what it must never overwrite, what
   the human approves, and how an existing project proves that protected state survived.
4. **Portability:** how Assisted remains usable from ordinary files and its documented manual path when
   OpenAI software, a catalogue, a network connection, or a plugin is absent.
5. **Lifecycle:** who owns releases, compatibility, security reports, updates, rollback, deprecation, and
   user support after distribution begins.

## Candidate configurations to compare

| Configuration | Potential gain | Principal cost or risk |
|---|---|---|
| Keep the documented copy-and-initialize path | No new runtime, permission, catalogue, or support dependency | Discovery and correct-copy friction remain |
| Publish a Codex-native plugin/package if an official external channel exists | One recognisable install action and possible discovery inside the tool | Vendor-specific packaging, review rules, compatibility and ongoing releases |
| Distribute a minimal installer that places the existing ordinary files | Works outside a catalogue and can preserve the Assisted payload unchanged | Executable supply-chain risk and a new cross-platform product to maintain |
| Publish only a discovery skill that guides a verified copy | Smaller permission surface and less new code | May not reduce the hardest copy/update friction |
| Provide a hosted starter or repository template | Familiar versioning and transparent file diff | Still asks users to understand repository/template operations |

These are research candidates, not approved architecture. The HL must remove configurations that do not
exist on current supported surfaces before comparing implementation cost.

## Informal definition of done

1. Current official Codex and ChatGPT extension/distribution surfaces are named precisely, with primary
   sources, eligibility, publication route, permissions, review requirements, geography, and maintenance
   constraints.
2. Assisted's current onboarding journey is measured from discovery through first valid task; concrete
   failure points are separated from preferences.
3. At least the five candidate configurations above are compared on user steps, files touched, authority,
   update/rollback, provider dependence, security, discoverability, implementation size, and continuing
   support cost.
4. One `GO`, `PREPARE`, or `NO-GO` recommendation is made. `GO` names the exact supported mechanism;
   `PREPARE` names the missing evidence or platform capability; `NO-GO` keeps the manual path and explains
   why packaging would cost more than the friction it removes.
5. The recommended route preserves the complete manual installation path and ordinary-file authority. A
   user never loses access to their project because a vendor surface, marketplace, or plugin disappears.
6. If implementation is justified, a later TS can state an exact payload boundary, protected manifest,
   migration path, test fixtures, release responsibility, and acceptance evidence without inventing a
   missing product decision.

## What must not happen

- Do not build, install, publish, submit, or announce a plugin in this proposal task.
- Do not treat an OpenAI programme or partnership as a prerequisite; APD remains independently decidable.
- Do not move Assisted project truth into an account, hosted memory, plugin registry, or proprietary
  runtime.
- Do not replace the verified manual path. An installable package may add a route, not make ordinary files
  unusable without it.
- Do not add an executable installer merely because it is technically possible. Executable code requires
  a measured benefit and proportionate supply-chain controls.
- Do not merge Full TFW distribution into this scope. The owner named Assisted as the target edition.

## Why this is a separate low-priority task

`AILAB_20260906-104830_OCS` asks whether collaboration with OpenAI creates measurable personal,
educational, course, laboratory, and social value. Plugin feasibility does not answer that question and is
not required for an educational pilot or an open-source support application. Keeping it inside OCS would
spend research capacity on a speculative distribution mechanism before establishing whether collaboration
helps the course at all.

APD therefore waits as a proposal. It becomes active only when the owner chooses `/tfw-plan`, approves an
HL that names the evidenced onboarding problem, and decides that distribution work outranks the current
course and laboratory priorities.
