# TFW Assisted 1.6

Assisted — самостоятельный русскоязычный набор для повторяющейся работы в Codex. Он связывает устойчивый контекст проекта, участников, задачи со следом, подтверждённые знания, шаблоны, команды и воспроизводимый порядок проверки.

Это публичная нейтральная производная field-proven TFW Assisted 1.6. Starter не содержит персонализированную карточку, `project_id`, human profiles, `workspace/`, task evidence или machine-local bindings и после копирования готов к обычной инициализации.

Скопируйте **содержимое** этой папки в корень проекта. Не работайте внутри вложенной папки стартерa.

## Где источник истины

| Что | Источник |
|---|---|
| Цель, рамка и карточка проекта | `PROJECT.md` |
| Общий контракт работы ИИ | `AGENTS.md` |
| Канонические команды | `.agents/skills/` |
| Участники | `team/` |
| Задачи, решения и проверки | `workspace/<ID>/TRACE.md` |
| Проверенные сведения проекта | `knowledge/records/` |
| Кандидаты общей памяти | `knowledge/inbox/` |
| Форматы результатов | `шаблоны/` |

## Первый запуск

1. Откройте корень проекта в Codex и отправьте: **«Инициализируй этот проект по TFW Assisted».**
2. Codex одним сообщением задаст не более трёх существенных блоков: что это за проект, каковы полное имя (имя и фамилия) текущего человека, его роль в компании и роль в проекте и кто ещё участвует; каковы цель, аудитория, эффект и признаки успеха; какие ограничения, профессиональную роль и ментальную модель принять.
3. После ответа Codex сгенерирует стабильный `project_id`, заполнит `PROJECT.md`, создаст отдельные профили с двумя полями роли и запишет профессиональную роль ИИ и ментальную модель в настроечный блок `AGENTS.md`. Инициализация не создаёт рабочую задачу.
4. Начните новую сессию: после изменения `AGENTS.md` это обязательно.

В уже инициализированном проекте Codex не запускает повторную инициализацию. На неизвестном устройстве он одним обычным сообщением спрашивает полное имя с фамилией, роль в компании и роль в проекте; существующий профиль и identifier использует без перезаписи, новому человеку создаёт только отдельный surname-based профиль. Если фамилии нет или фамильный identifier занят, Codex уточняет данные и ничего не перезаписывает. На общем компьютере имя спрашивается в каждом новом человеческом чате.

Device-local выбор Assisted хранится вне общей папки в `%LOCALAPPDATA%\tfw\assisted\bindings.yml` на Windows или `~/.tfw/assisted/bindings.yml` на POSIX. Full `bindings.yaml` и legacy `tfw-assisted/bindings.yml` не читаются, не импортируются и не изменяются. Поэтому второй компьютер того же человека настраивается отдельно. Обычному участнику не нужно знать внутренние идентификаторы, форматы или команды.

Знакомство выполняет сам Codex по инструкциям проекта: пользователю не нужны Python, Git, терминал, shell-команды, исполняемый helper или ручной поиск служебных файлов. Codex выбирает доступные средства текущей среды; если безопасно сохранить выбор на этом компьютере нельзя, он продолжает работу в текущем чате и прямо говорит, что в следующий раз спросит снова.

## Как идёт работа

Путь задачи стабилен: `workspace/<ID>/`. Новые задачи используют `ID = YYYYMMDD-HHMMSS__slug` без login/handle; владелец всегда записан в поле `Владелец`. В новом slug запрещено `__`, а коллизия пути приводит к новому фактическому timestamp, а не к перезаписи. Legacy-ID `YYYYMMDD-HHMMSS__handle__slug` сохраняются при one-to-one миграции без изменения ID.

Статус живёт только в `TRACE.md` и принимает `new`, `doing`, `review`, `done` или `blocked`. Изменение статуса не перемещает папку. Каждая Codex-задача до содержательной работы получает строгое имя `plan | <ID>`, `handoff | <ID>` или `review | <ID>`; для legacy-задачи только видимое имя исключает средний handle, а полный ID и путь остаются прежними.

Обычный вопрос, чтение или знакомство с проектом ничего не создают. Любая постановка работы естественным языком может запустить TFW path; slash-команды ниже — точный служебный интерфейс для явного запуска этапов, а не обязательное знание пользователя. До активной работы помощник:

1. понимает текущее состояние, желаемое изменение, адресата и владельца приёмки;
2. фиксирует вопросы и допущения, границы, источники, DoD и DoF;
3. создаёт отсутствующую `workspace/<ID>/`, устанавливает и проверяет `plan | <ID>`, затем создаёт `TRACE.md` и план по `шаблоны/план_работы.md`;
4. предъявляет план на Gate 0 и просит выбрать ручной или автономный режим.

После утверждения работа идёт последовательно в одной task folder и одном trace:

`/tfw-plan` → Gate 0 → новый чат `/tfw-handoff` → новый чат `/tfw-review` → явная человеческая приёмка.

В **ручном режиме** пользователь сам запускает каждый следующий чат по точной команде. В **автономном режиме** plan с отдельного явного разрешения создаёт и контролирует Codex-задачи только этой задачи, ждёт обязательные отчёты, при `FAIL` запускает новый handoff и новый review, а человеку выносит один финальный пакет после `PASS`. Одновременно task folder редактирует только одна роль; plan не пишет в trace, пока дочерняя роль активна.

Во время работы trace отдельно хранит текущего участника, его корпоративную/проектную роли, владельца задачи и роль ИИ, а также источники, решения, проверки и путь к результату. Для `review` и `done` поле `Результат` указывает на существующий путь от корня проекта. Перед сокращением контекста исполнитель сохраняет в единственной активной задаче текущее решение, проверку и следующий шаг, а перед завершением проверяет структуру, допустимый статус, результат, внутренние ссылки и отсутствие секретов.

Общие файлы проекта могут находиться в локальном или синхронизируемом shared-хранилище. Перед записью помощник перечитывает target и baseline, изменяет минимальный набор файлов и выполняет post-read/hash. Это помогает обнаружить конфликт, но не обещает безопасную параллельную запись или завершённую удалённую синхронизацию. Локальные bindings не входят в shared manifests.

## Команды

| Команда | Что делает | Где останавливается |
|---|---|---|
| `/tfw-plan <тема>` | Создаёт/именует задачу, согласует Gate 0 и режим; в автономном режиме последовательно координирует отдельные handoff/review | На ручной передаче, blocker/deviation или финальной человеческой приёмке после `PASS` |
| `/tfw-handoff <ID или путь>` | Первым gate проверяет `handoff | <ID>`, исполняет план/исправления, завершает knowledge decision, самопроверяет и отчитывается координатору | На `Статус: review`, обязательном gate или доказанном blocker |
| `/tfw-review <ID или путь>` | Первым gate проверяет `review | <ID>`, независимо проверяет DoD/DoF, не исправляет результат и отчитывается координатору | После `PASS` в `review`, после `FAIL` в `doing` или на blocker |
| `/tfw-update <источник>` | Prompt-only получает целый пакет, показывает service/protected manifest, ждёт одно согласование и выполняет version-specific migration | На единственном Gate записи, конфликте либо полном проверенном обновлении |

`tfw-identity` обслуживает startup автоматически и не является обязательной пользовательской командой. Он динамически обнаруживает профили, различает роль в компании и роль в проекте, не выбирает участника по умолчанию и пропускает human onboarding в автономных handoff/review.

`PASS` оставляет задачу в `review` до решения человека. `FAIL` меняет только поле статуса на `doing`; путь и результат остаются теми же. В автономном режиме отсутствие обязательного preflight/final отчёта, неверное имя или расхождение с trace не считаются успешным этапом. Только явная человеческая приёмка после `PASS` позволяет установить `done`.

После добавления или изменения команды начните новую сессию, чтобы обновлённый договор гарантированно загрузился.

## Память

`TRACE.md` — первичный след задачи. Долговечная находка после проверки риска может стать отдельным кандидатом в `knowledge/inbox/`. Кандидат не считается подтверждённым фактом и не продвигается автоматически в `knowledge/records/`.

Секреты в память не записываются. Медицинские, персональные, юридические, финансовые и другие чувствительные сведения удерживаются до явного подтверждения. Детерминированная проверка распознаёт только формальные признаки секретов; смысловую границу соблюдает помощник.

## Версия и обновление

Номер текущего набора лежит в `VERSION`, изменения — в `CHANGELOG.md`. Опубликованный marker этой версии — `1.6`.

Обновление меняет служебную часть: `AGENTS.md`, `README.md`, `PROJECT.md`, `MIGRATION.md`, `VERSION`, `CHANGELOG.md`, `шаблоны/`, `.agents/skills/`. Папка `.codex/` не входит в clean payload. По умолчанию `workspace/`, `knowledge/` и `team/` защищены. Version-specific migration применяет только явные old-source → new-target карты; уже валидные identifiers сохраняются, а local bindings Full/Assisted и legacy registry никогда не читаются из пакета, не мигрируются и не переносятся между устройствами.

Источником `/tfw-update` может быть путь, архив, URL, облачная ссылка, вложение или иное доступное представление целого пакета. Навык не содержит собственного downloader/unpacker и не требует конкретную ОС, Python, shell или архиватор: помощник сам выбирает доступные инструменты текущей среды. До согласования пакет приводится к безопасной временной рабочей копии и проверяется статически; никакой код непроверенного источника не запускается. Недоступный или невалидный ресурс не обходится: помощник называет точную причину и просит доступное представление либо экспорт без изменения проекта.

Карточка проекта, профессиональная роль и ментальная модель возвращаются дословно. Обновление выполняет помощник целиком после одного согласования; ручных шагов копирования на пользователя не перекладывают.

### Обновление до 1.6

| Исходная версия | Что написать | Почему |
|---|---|---|
| 1.5 | `Используй /tfw-update и обнови этот проект из доверенного пакета 1.6 <точный путь, архив, URL или объект>` | Пакет 1.6 содержит точную migration map, сохраняет project identity, персонализацию и valid identifiers, исключает local stores и добавляет prompt-only identity без обязательного helper |
| 1.4 и ниже | Следуйте точной цепочке для исходной версии в `MIGRATION.md` | Старые схемы требуют собственных hash-preconditions и не объединяются с маршрутом 1.5→1.6 догадкой |

Каждый маршрут имеет один Gate записи. Для 1.5→1.6 помощник показывает service/protected manifests и source-version preconditions, сохраняет существующий валидный `project_id`, карточку, цели, роли, legacy-source `work/` как target `workspace/`, остальные knowledge и все valid profile filenames/identifiers как target `team/`. Stock knowledge targets обновляются только при exact hashes из `CHANGELOG.md` либо по отдельному точному records Gate; любой необъяснённый protected diff останавливает запись.

## Проверка задачи

Проверка входит в обычный порядок ведения задачи:

1. до результата создать `workspace/<ID>/TRACE.md`;
2. указать текущего участника, его корпоративную/проектную роли, владельца, роль ИИ, желаемый результат, критерии, статус, результат и решение о знании;
3. разместить обратный план до хода работы;
4. вести источники, решения, сомнения, проверки и следующий шаг;
5. перед завершением проверить допустимость статуса, существование результата, внутренние ссылки, обязательные поля и формальные признаки секретов.

## Честные границы

Assisted поддерживает дисциплину и заявленную атрибуцию, но не аутентифицирует людей, не подтверждает полномочия, не гарантирует безопасное одновременное редактирование одного trace, не доказывает завершение удалённой синхронизации и не работает при закрытом Codex. Автономный режим действует только при реально доступных thread-операциях и явном ограниченном разрешении; иначе plan использует ручной режим. Он не выполняет автоматическую консолидацию, продвижение, чистку, дедупликацию или разрешение конфликтов общей памяти.

Для перехода существующего Light-проекта сначала следуйте `MIGRATION.md`: исходные файлы и traces должны сохраниться до замены активного контракта.
