# /tfw-update

## Role lock

Ты Update Coordinator. Сначала только читаешь и готовишь один полный план. Изменения разрешены лишь после явного одобрения точного списка путей. Эта процедура не является программой обновления и не обещает атомарность многофайлового изменения.

## 1. Compare — без записи

1. Получи точные каталоги доверенного публичного source и downstream target. Подтверди, что source не является target и не находится внутри него.
2. Прочитай `VERSION`, `CHANGELOG.md`, `maintenance/release-manifest.json`, `maintenance/maintenance-policy.json` из source и те же доступные записи из target. Не исполняй код source.
3. Построй для обоих деревьев полный отсортированный список регулярных файлов: относительный путь, размер и SHA-256. Ссылки, абсолютные/выходящие пути, коллизии Unicode/case-fold и неоднозначный тип блокируют работу до записи.
4. Проверь source по статическому manifest: он исключает себя, но включает policy; каждая оставшаяся строка совпадает с фактическим файлом. Хэш подтверждает выбранные байты, а не происхождение source.
5. Определи accepted baseline target из policy и фактических байтов. Если baseline не принят или изменился во время чтения, остановись.

## 2. Classify — одна authority на путь

Назначь каждому рассматриваемому пути ровно один класс:

| Класс | Правило |
|---|---|
| public | заменить/создать только при совпавшем принятом stock baseline |
| customizable | заменить только неизменённый stock; изменённый файл сохранить |
| downstream-only | сохранить побайтово |
| retired-known-stock | удалить только при точном принятом stock SHA-256 |
| unresolved | остановиться до первой записи и запросить решение |

Всегда downstream-only: `PROJECT.md`, `work/`, пользовательские записи `knowledge/`, `people/*.md`, персонализация, неизвестные target-only пути и постороннее содержимое `.codex/`. Stock `knowledge/INDEX.md` и `people/README.md` остаются public согласно policy. Изменённые шаблоны, overlay и assets сохраняются, если отдельное явно одобренное правило миграции не говорит иное.

## 3. Plan — один явный gate

Покажи человеку одну таблицу:

- source и target версии;
- точные пути `create`, `replace`, `delete`, `preserve`, `stop`;
- baseline каждого изменяемого/удаляемого target-файла;
- защищённый before-manifest;
- риски, способ проверки и восстановление из заранее созданной копии.

Запроси одно явное одобрение этого точного плана. Нельзя трактовать согласие на исследование или прошлое обновление как gate. Наличие хотя бы одного `unresolved` означает, что плана на применение ещё нет.

## 4. Recheck и обычные изменения

После gate и до первой записи:

1. заново прочитай source manifest/policy и полный target inventory;
2. повтори хэши всех source-файлов, всех изменяемых target-путей и всех защищённых путей;
3. сравни с одобренным планом; любой drift возвращает к Compare без записи;
4. создай отдельную резервную копию только тех target-файлов, которые план разрешает заменить или удалить;
5. обычными доступными файловыми средствами выполни одобренные действия по одному пути; перед каждым действием ещё раз проверь его точный baseline;
6. после каждого действия перечитай путь и сравни ожидаемые байты; после всех действий сними полный after-manifest.

Если действие завершилось частично или проверка не совпала, прекрати следующие изменения, перечисли фактические успешные и неуспешные пути, отметь результат `partial` и передай его на проверку. Не называй частичный результат успешным и не утверждай, что каталог изменился транзакционно.

## 5. Verify и следующий источник

Готовый target должен:

- содержать ожидаемую версию и все фактические public-файлы из нового статического manifest;
- сохранить собственные downstream-only и изменённые customizable-файлы побайтово;
- не иметь необъяснённых изменений;
- пройти независимое сравнение before/plan/after.

Скопированный `release-manifest.json` остаётся статической authority обновлённого target и может быть прочитан при следующем переходе. Никакая продуктовая команда не применяет его автоматически.

## 6. Downstream → public: только candidate

Обратное направление никогда не меняет public core напрямую.

1. Сравни downstream с его известным public baseline и выдели полезные отклонения.
2. Отбрось частные пути, содержимое, хэши, точные counts, timestamps, людей, роли, идентификаторы, организацию, бренд, проектную историю и уникальный операционный контекст.
3. Создай candidate в явно выбранном новом каталоге вне public/source/target; в нём допустимы только общие capability/rule и краткое обоснование.
4. Перед любым переносом в public назначь независимую смысловую и privacy-проверку, затем отдельное решение о выпуске.

Полевая копия остаётся read-only evidence. Push, tag и публикация не входят в эту процедуру.
