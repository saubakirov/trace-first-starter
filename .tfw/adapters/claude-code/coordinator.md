### Desktop

The documented `claude --desktop` command opens Desktop in the selected checkout without a prompt.
It accepts no model, effort or permission-mode flags. Use it only where creation applies the
already selected Desktop settings and exposes a distinct address; otherwise keep that launch
owner-assisted. Do not create with substituted settings and repair them afterward. Confirm the
created unit through the exposed session list before its command-only activation; opening the app
alone proves neither session creation nor addressability. Do not add a `claude -p` warm-up turn to
record permissions: it would precede the required first message. `--desktop --resume <id>` presents
an existing session; it is not fresh provisioning or permission to read another role's history.

### Remote Control

The reporter's Linux recipe creates an interactive session without an initial prompt:

```sh
tmux -L <unit> new-session -d -s <unit> -c <checkout> "claude --remote-control '<title>' -n <unit> --model <model> --effort <effort> --permission-mode <mode>"
```

Bind the selected checkout and a unique task-owned tmux server before creation. If the Coordinator
runs under systemd, the reporter used `systemd-run --user --scope` to keep the child server outside
its unit; verify actual lifetime isolation on that host. Observe the role in the owner's Remote
Control view and use `ListAgents` to bind its exact returned address, not a title-derived guess.
Use that address for `SendMessage`; request `notify_when_idle` only where supported for sessions on
the same machine. An idle notice is a wake-up, not a gate. Returns still go to `coordinator_route`.
Do not attach to or capture the role's pane. After safe durable return and when correction access
is no longer needed, stop only the recorded task-owned server with `tmux -L <unit> kill-server`;
verify disposition rather than promising that termination preserves a resumable session.
