# Migrating to TFW 2.0.0

> **Who this is for:** a project on TFW 1.x updating to 2.0.0 or later.
> **What it is:** the procedure. `update.md` handles the payload; this file handles your
> existing task corpus, which the payload cannot touch.
> **What it is not:** a changelog. The CHANGELOG says what changed and why; this says what
> you do, and in what order.

---

## What 2.0.0 breaks

One thing, and everything here follows from it: **the root Task Board is retired.** A task's
live state moves into the task's own directory, so two people can advance two tasks without
editing the same file.

| Before 2.0.0 | From 2.0.0 |
|---|---|
| a `## Task Board` table in your README | `{task}/status.md`, one per task, closed schema |
| status changes edited into that table | one write, inside one task directory |
| history in commit messages and chat | `{task}/journal/`, one immutable file per event |
| the board as the portfolio view | `{container}/00-INDEX.md`, **derived** and never authoritative |
| whoever the commit author was | `team/{handle}.md`, declared attribution |

Your board is not deleted. It is captured verbatim into `BOARD-SNAPSHOT.md`, and every row
is accounted for by name before anything is removed.

## Before you start

**Do not migrate while a participant is mid-gate.** The migration reads your board and
writes one file per live task. If someone is waiting on an approval, or an agent is running
a workflow that is about to write a status, let that finish first.

This is not a lock and TFW does not have one. It is a quiescence rule, and it exists because
during the first real 2.0.0 migration another agent rewrote the source board **three times**
while it was being read. The migration survived — it reads a committed revision by default,
which is why — but the accounting would have been about a board nobody had.

Commit, or at least stage, whatever is in flight. The board is read from `HEAD`.

## The order

**Migrate, then generate, then remove the board.** Reversed, you lose the board's contents
and the migration has nothing to read but an empty table.

Each step below says what happens if you skip ahead.

### 1. Update the payload

Run `/tfw-update` (or follow `.tfw/workflows/update.md`) up to and including its Step 7. You
now have `.tfw/scripts/`, the templates, the workflows, and a `tfw.version` of 2.0.0 or later.

**Delete the framework files that left the payload.** Copying the new payload over yours
adds and overwrites; it never removes. So a file the framework retired stays in your `.tfw/`
forever, and a second copy of a template is a second thing that can be edited by mistake.
Find them:

```bash
# every .tfw/ file you have that the new payload does not
cd .tfw && find templates workflows -type f | while read f; do
  [ -f ".upstream/.tfw/$f" ] || echo "RETIRED: .tfw/$f"
done
```

At 2.0.0's successor that prints `templates/topic_file.md`, `templates/team_profile.md` and
`templates/journal_event.md` — three templates that moved into directories mirroring their
output (`templates/knowledge/topic.md`, `templates/team/profile.md`,
`templates/journal/event.md`). Delete the old paths once the new ones are in place.

Two decisions `update.md` puts to you, repeated here because they are the two that get set
by accident:

- **`tfw.task_containers`** does not exist before 2.0.0, so there is nothing to preserve —
  you are choosing it. `[tasks]` keeps one container; `[new, tasks]` creates new tasks in
  `new/` while every existing `tasks/...` path still resolves.
- **`initial_seq`** is deleted. Identifiers come from the clock and nothing reads a counter.

**Add `__pycache__/` to your `.gitignore` if it is not there.** Running a shipped Python
tool writes `.tfw/scripts/__pycache__/`, and a project whose ignore rules never needed a
Python entry will otherwise see the payload dirty its own tree on first use.

### 2. Account for the board — dry run first

```bash
python .tfw/scripts/migrate_board.py --manifest MIGRATION.md
```

This writes nothing except the manifest. Read the manifest before going further: it names
every board row and every task directory individually and states where each one ends up.

**If it reports zero rows, do not pass `--allow-empty-board` to make it proceed.** Three
causes, in the order they actually occur:

| Cause | Fix |
|---|---|
| your board is somewhere other than the root README | `--board tasks/README.md` |
| its heading is not `## Task Board` | `--board-heading '## Board'` |
| the board was already removed | `--board-rev <commit-that-still-had-it>` |

A project whose root README is generated legitimately keeps its board elsewhere — that is
the first cause because it is the one that happened.

`--allow-empty-board` is correct in exactly one case: a project that genuinely never had a
board.

#### What the manifest will tell you about odd directories

A task directory whose name the identifier grammar does not parse — the grammar is
`YYYYMMDD-HHMMSS__slug`, or legacy `PREFIX-N` optionally followed by `__slug` — is reported
under **Unresolved inputs**. No state file is written for it, and nothing is asserted about
whether work happened there.

`TFW-01_my_task` with a single underscore is the common case, and it lands here. If you want
such a directory picked up, **rename it by hand** to `TFW-01__my_task`. The tool will not do
it for you: renaming a directory breaks references into it, so it is a decision with a human
behind it, not a normalization.

The same rule governs `UNDECLARED` — see below.

### 3. Apply

```bash
python .tfw/scripts/migrate_board.py --apply
```

Writes `BOARD-SNAPSHOT.md` and one `status.md` per live task. It refuses to overwrite
anything; if a task already has state, use `--skip-existing` and it will write the rest.

Facts your board never carried are written as `unrecorded`. That is deliberate — a guess in
a state file is worse than a gap.

### 4. Generate the derived view

```bash
python .tfw/scripts/gen_index.py
```

Writes `{container}/00-INDEX.md`. Add a permanent route to it from your README.

**Skipping to step 5 from here leaves you with no portfolio view at all** — the board is
gone and nothing has replaced it.

The index is derived. When it disagrees with a task, the task is right; delete it and
nothing is lost.

### 5. Remove the board

Now, and not before. Delete the `## Task Board` section from your README. Its bytes are in
`BOARD-SNAPSHOT.md`, and every identifier it carried is named in the manifest from step 2.

**Doing this before step 2 is the one unrecoverable mistake in this procedure.** The
migration would then read a README with no table and, absent the empty-board refusal, would
have written a snapshot recording zero rows over a board that had dozens.

### 6. Declare who is acting

```
team/{your-handle}.md      from .tfw/templates/team/profile.md
```

Required, not optional: every journal event carries `actor` and `on_behalf_of`, and both
name a handle this directory declares. `on_behalf_of` is always a human.

Create the directory together with its first profile. If `/tfw-update` already did this, you
are done here.

### 7. Ask the project whether it is consistent

```bash
python .tfw/scripts/gen_index.py --check project
```

The last step. It reports on the payload, `team/`, the container configuration, retired keys,
the version marker and carrier validity — then exits. It repairs nothing and writes nothing.

Its output also names what it did **not** check. Read that part.

## Three things that will not be obvious

### `build.*` in your config keeps pointing at the old path

`update.md` preserves `build.*` because it is yours. So if a release relocated a tool — and
2.0.0's successor moved the migration tooling from `docs/scripts/` into `.tfw/scripts/` —
your `build.verify` still names a path that no longer exists, forever, and silently.

Re-read that block by hand. `--check project` reports it.

### `UNDECLARED` is not a value you fix by editing

If your board carried a status outside the declared vocabulary — free prose, a retired label,
an emoji nobody kept — migration writes `lifecycle: UNDECLARED` and puts the original in
`lifecycle_verbatim`. It never guesses a declared value.

**Migration must never normalize it. An accountable owner may resolve it**, by setting the
correct value and recording a `transition` journal event carrying `from: UNDECLARED`. The
distinction is the whole point: the tool has no basis for the guess, and a person does — and
the event is what makes the resolution a trace rather than a silent rewrite.

Left alone, `UNDECLARED` is treated by every consumer as non-actionable and reported. That is
safe, and it is not a resting place.

### A project migrated before the tooling moved carries the old path in a comment

Each generated `status.md` ends with a provenance comment naming the script that wrote it.
If you migrated at `2.0.0-dirty`, that comment says `docs/scripts/migrate_board.py`.

**Leave it.** It is a true statement about a past act at the path that was correct then.
Rewriting it would make the record describe something that did not happen.

## If it goes wrong

Nothing here deletes or rewrites an existing file. `migrate_board.py` opens no path that
already exists, and never renames or moves anything.

So the recovery is ordinary version control: the files the migration added are new files.
Delete them and you are back where you started, with your board still in your README —
provided you have not yet done step 5.
