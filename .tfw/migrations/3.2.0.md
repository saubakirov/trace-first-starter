# Updating to TFW 3.2.0

Pin the published `v3.2.0` object, verify its commit and `.tfw/VERSION`, and read that exact
target's `.tfw/workflows/update.md` before applying files. This guide supplies version-specific
obligations, not another update procedure. An unpublished release candidate is not a published tag.

## What this release gives your project

Closing a task need not start another round of accepted product work just to correct its records.
The existing Coordinator owns the close, the independent Reviewer assesses changed final claims,
and affected checks still protect real changes. A returning Coordinator can continue an already
authorized close without asking the owner to select the same work again.

The maintainer test split is useful to this framework's contributors; receiving projects keep their
own checks. These instruction changes do not promise flawless agent behavior or quantified savings.

## 1. Select the starting-version route

If the project has not reached stable 2.0.0, first read [the 2.0.0 migration](2.0.0.md).
Acquire every applicable guide and changelog section from the same final `v3.2.0` object.
Historical version/ref examples describe their original releases; the final target remains 3.2.0.
Intermediate payload installation is unnecessary. Inspect actual migration evidence and perform
only still-needed actions, in the order below.

| Installed version | Ordered route to 3.2.0 |
|---|---|
| 3.1.0 | This guide; recheck any incomplete earlier migration |
| 3.0.0 | [3.1.0 guide](3.1.0.md), then this guide |
| 2.2.0 | [3.0.0 guide](3.0.0.md), 3.1.0, then this guide |
| 2.1.0 | [2.2.0 guide](2.2.0.md), 3.0.0, 3.1.0, then this guide |
| 2.0.0 | CHANGELOG 2.1.0 **Updating from 2.0.0**, including A/B/C and **Also in 2.1.0 — `/tfw-task` is retired**; then 2.2.0, 3.0.0, 3.1.0 and this guide |
| 2.0.0-dirty.5 | CHANGELOG 2.0.0 **Updating from a `2.0.0-dirty` tag**, then the stable 2.0.0 route |
| 2.0.0-dirty.2, .3 or .4 | CHANGELOG .5 **Updating from `2.0.0-dirty.2`, `.3` or `.4`**, including applicable .3 correction and .4 actions; then .5 and stable routes |

Where pre-2.0 corpus conversion is still needed, use the pinned target's self-contained
`tools/migrations/2.0.0/` bundle and its dependency preflight. Do not restore the retired payload
runtime, task board or shared portfolio. The 3.0.0 and 3.1.0 successor rules remain applicable.

## 2. Preserve state and synchronize the connected instructions

Establish a safe boundary for affected project writers and preserve recoverable framework/config/
adapter bytes before replacement. Keep project purpose, root README/RELEASE, configured task
containers and checks, scope budgets, knowledge/index/state, profiles/grants, private preferences,
external bindings, task artifacts and immutable journals. Do not copy upstream task history,
KNOWLEDGE.md, topics, tests or this repository's release procedure into a receiver.

Apply the pinned canonical conventions, handoff/review/docs/knowledge/resume workflows, and affected
status, journal, review and evidence templates as one connected group. Use the pinned manifest to
refresh installed or owner-selected adapters. Preserve foreign neighbors and project-owned text;
exact-copy receivers must match their canonical source, and Codex uses its declared thin skill
routers. The manifest topology and briefing template are unchanged by 3.2.0.

Merge only framework-owned version metadata: `.tfw/VERSION` and `tfw.version` agree at `3.2.0`;
`tfw.installed_from` names the configured upstream and verified `v3.2.0`, with its exact commit in
the update receipt. An explicitly authorized untagged experiment instead records its real full SHA.
No configuration keys are added, renamed or retired by this release. Preserve receiver values and
apply older migrations only where still required. Do not reset knowledge digests or processed markers.

## 3. Replace retired live obligations, not history

These verbatim search strings come from the 3.1.0 source. Their occurrence in historical task,
changelog or migration records is not a defect. Update managed live copies through the canonical
route; do not independently rewrite approved artifacts or redefine their original acceptance epoch.

| Retired wording and source | Successor in 3.2.0 |
|---|---|
| ``Run `/tfw-docs` — update KNOWLEDGE.md §1-§3`` in review Step 7 | After verdict, the Reviewer returns to the existing Coordinator. That Coordinator invokes applicable capture through its existing owners/gates; the Reviewer independently assesses materially changed final claims |
| `When both markers are set **and REVIEW §5 carries no undisposed item**` in review Step 7 | Markers describe actual effects, not sufficient proof. Required final outputs, affected checks, independent acceptance, dispositions and selected landing must be complete before terminal writes |
| `For trivial tasks: reviewer pre-marks both as N/A during review.` in review Step 7 | Coordinator records Applied/N/A with actual effects and reasons; pending capture or dispositions cannot masquerade as completion |
| `Ran at least 1 build/test command (or documented why not)?` in review/verify checkpoint | Independently establish evidence sufficiency and applicability. Run affected checks when needed; a fresh command solely to fill the checkpoint is not required |
| `Ask: **“Start planning Phase X?”** or **“Which phase should we work on?”** Then stop.` in resume | This gate still applies to unselected planning. An already selected, authorized closing/recovery request follows the conventions-owned closing route directly; no missing mandate is inferred |

The central **Closing and record recovery** contract in conventions owns the successor semantics.
It introduces no additional workflow, state, event kind, mandatory executable or evidence registry.

For an in-flight task, resolve its own authority and approval epoch before acting. Installation alone
does not reopen accepted work, transfer a reserved decision, or override an approved TS. A real
authority conflict returns to its existing ruler. Do not issue a fake transition for a missing old
event: preserve erroneous history, reconstruct the actual accepted result and append only a truthful
present act. Unknown acceptance, a changed oracle or authority, and material defects still stop close
and follow the existing return route. REJECTED remains terminal; only the accountable owner resolves
UNDECLARED. An unrelated pending knowledge batch does not become processed through a record repair.

## 4. Verify and explain the result

Verify exact target/version/provenance, applicable migration paths, connected source/adapter parity,
preservation and intended diff. Run the receiving project's own applicable checks. Where the update
changes an accepted output, identify the changed claim and obtain its required independent assessment;
source-string checks alone do not prove native behavior. Missing dependencies, pre-existing failures
and unavailable checks are not PASS. This guide adds no upstream pytest/MkDocs requirement or native
trial for every receiver. Assisted/Light and provider admission remain unchanged.

Follow the target update workflow's checks → cleanup disposition → immutable receipt → final outcome
order. Use its unchanged briefing template in `tfw.content_language`: explain the actual result,
useful change, preserved state, limitations and next action. Do not infer savings or successful use
from a version number, and do not claim a future message was already delivered or understood.

On failure, stop the affected group and retain pinned source and preservation references. Restore
only authorized exact pre-update paths; never erase intervening project work or rewrite history.
After new task writes, assess their form and authority before any downgrade. Updating TFW neither
releases the receiver's product nor authorizes another repository's merge, tag, push or deployment.
