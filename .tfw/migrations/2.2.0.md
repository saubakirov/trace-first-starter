# Updating to TFW 2.2.0

> **Superseded by** `.tfw/migrations/3.0.0.md` (2026-09-07) for targets at 3.0.0 or later. This
> guide remains the historical 2.2.0 route and must not replace the final target's migration.

Read the target's `.tfw/workflows/update.md`, not the installed one. Pin `v2.2.0`, verify
its `.tfw/VERSION`, and follow that pinned workflow; this guide supplies the release-specific
decisions, not a second update algorithm. Never copy a moving working tree.

## What this release gives you

- Workflow-owned selective context: read the rules needed at each checkpoint without losing gates.
- VALUE-only scope accounting: mandatory tests, evidence and lifecycle traces no longer spend the
  delivery budget, but remain mandatory.
- Rung-specific correction: a repair already covered by the TS does not require a new TS merely
  because a review round happened.
- State-backed session naming, isolated concurrent work, stable participant identities and bounded
  amendment authority. CRATM A–C are delivered foundations, not the complete autonomous team mode.

The owner selected 2.2.0 while reserving 3.0.0 for complete CRATM. This is an explicit numbering
exception: the configuration and prospective contract changes below still require migration.
Do not infer that a minor version can be copied without reviewing its updating instructions.

## 1. Select the starting-version route

**If the project has not reached stable 2.0.0, first read `migrations/2.0.0.md`.** This includes
0.x, 1.x and every `2.0.0-dirty` prerelease. Account for its board, phase-state, participant,
configuration and debt-retirement requirements in the update checklist. Execute only still-needed
steps after inspecting the actual state; do not repeat a completed migration or guess unknown state.
Reading that guide does not certify automatic migration of an unverified 0.x/custom project.

Use the updating sections in the pinned target's `CHANGELOG.md`. Intermediate versions do not need
to be installed separately; perform their applicable migration actions under the final target's
workflow. Historical target refs and `installed_from` examples are not the final target: record
`{upstream}@v2.2.0`, never an intermediate tag or machine-local path.

| Installed version | Required route before the 2.2.0 changes below |
|---|---|
| 2.1.0 | This guide; recheck inherited board-check configuration in section 5 |
| 2.0.0 | 2.1.0 **Updating from 2.0.0**, including A/B/C and **Also in 2.1.0 — `/tfw-task` is retired** |
| 2.0.0-dirty.5 | 2.0.0 **Updating from a `2.0.0-dirty` tag**, then the 2.1.0 route |
| 2.0.0-dirty.2, .3 or .4 | .5 **Updating from `2.0.0-dirty.2`, `.3` or `.4`**, including the .3 correction and .4 updating section where applicable; then 2.0.0 and 2.1.0 |
| 2.0.0-dirty | .2 **Migration from `2.0.0-dirty`**, then the applicable .3/.4/.5, 2.0.0 and 2.1.0 actions; do not reinstate retired `build.verify` |
| 1.x | 2.0.0 **Updating from 1.x** and `migrations/2.0.0.md`, then the 2.1.0 route |
| 0.x or unknown/custom provenance | No verified automatic route is claimed. Stop before writes, inventory the board/task/config forms and local customizations, and obtain a project-specific migration plan; do not treat a payload copy or full init as migration |

The older board-migration guide retains its historical step numbers. For a target of 2.2.0 its
instruction to follow update.md “up to and including its Step 7” means the current workflow's
approved payload/config application, not a nonexistent Step 7. Complete the corpus migration
before the current workflow's final verification and cleanup. Preserve the order **account for
the board → apply migration → derive the view → remove the board**; never migrate a moving board.

## 2. Preserve the receiving project

Pause task writers at a safe workflow boundary. Record the installed tag/provenance and preserve
a recoverable copy or commit of the pre-update framework and project configuration. Resolve the
acting human, task containers and project build commands through the target workflow's owner gate.

Do not replace `KNOWLEDGE.md`, `knowledge/`, task artifacts, team profiles, journal history,
`.tfw/knowledge_state.yaml`, or the project's North Star with this starter's copies. Preserve
existing root `README.md` and `.tfw/README.md` bytes. Preserve user preferences and external
per-machine bindings. Merge configuration key by key and approve the exact changed/removed file
list before applying it. Synchronize canonical workflows and selected adapters as one update.

## 3. Migrate scope budgets without changing the receiver's numbers

This change is prospective by release and TS approval epoch. Existing approved TS files and
historical results retain their recorded semantics; do not rewrite them or infer their meaning
from a newer installation. Record the introducing release as 2.2.0 for newly approved contracts.

For an old-only `tfw.scope_budgets` block, apply the following in one approved config merge:

| Retired key | New treatment |
|---|---|
| `max_files_per_phase` | Rename to `decomposition_trigger_files`; preserve its value |
| `max_loc` | Rename to `decomposition_trigger_loc`; preserve its value |
| `max_new_files` | Remove; do not reinterpret it as total files |
| `max_modified_files` | Remove; do not reinterpret it as total files |
| — | Add `owner_escalation_multiplier: 2` |

If the block already uses only the new keys, preserve its configured values. A mixed old/new block
is a hard stop for an owner ruling, not an automatic merge. Missing or customized semantics require
an explicit configuration decision, not the silent use of starter defaults.

For new approved TS files, classify each planned path as VALUE, ASSURANCE, TRACE or DERIVED.
Declare the selector, immutable Baseline/Candidate measurement, planned denominator and authority.
Only logical touched VALUE files and touched text LOC consume the delivery budget. Tests, evidence,
review and lifecycle closure are still owed. Prospective growth at the configured owner multiplier,
or from an applicable planned zero, requires the owner's decision; this is not a retrospective waiver.

## 4. Adopt the new context and identity contracts

- Sync the selected adapter through `adapters/manifest.yaml`: its managed root and every command,
  with exact copies where required and thin Codex routers where declared. Preserve adjacent project
  text and unrelated commands. Remove duplicate project-local preload instructions only where they
  conflict with the target workflow's ordered Read Contract. Use the changelog's retired quotations
  as search strings, rather than deleting every historical mention.
- Keep `.tfw/knowledge_state.yaml` intact during `/tfw-update`. Its old sequence/task cursor is not
  converted by copying the starter template. When `/tfw-knowledge` next reports
  `migration_required`, it reconciles every resolved task, obtains its own approvals, and writes
  `processed_task_digests` last. Only then are `last_consolidation_seq` and
  `last_consolidation_task` removed. The initial knowledge pass may therefore be larger.
- Existing human profiles and journal events remain valid. Never retrofit `writer`, rename event
  tokens, rewrite legacy `actor`, or create a profile per session. New optional `writer` names a
  stable declared principal. An agent principal needs direct human accountability and an immutable
  `may_rule_amendments` Boolean; neither its profile nor its title grants operational authority.
- Ordinary CL without delegated authority remains owner-ruled. Claimed delegation needs the
  governing human owner, separately recorded root authorization and a valid child-only chain;
  otherwise it stops. A new installation alone does not create that chain. Full Role Assignment,
  autonomy-start semantics and provider team profiles await CRATM D/E; do not advertise them as
  available in 2.2.0 or start mixed-provider autonomous role chains on that basis.
- Concurrent mutating runs use separate worktrees and exact-path commits. Cross-session landing
  follows review, attributes the producing task/phase, and preserves the exact reviewed Candidate.
  Session titles are navigation only; old titles and task history need no migration.

## 5. Verify and resume

1. Check VERSION/config agreement and final `installed_from`; run
   `python .tfw/scripts/gen_index.py --check project`, adapter parity, retired-vocabulary checks,
   customization-preservation checks and the receiving project's approved build commands.
2. Recheck `build.verify` and project-local gates. The framework's old
   `python .tfw/scripts/gen_index.py --check tasks` is report-only since 2.1.0; remove a still-inherited
   blocking invocation through the approved config merge. Keep unrelated project verification.
   The old reporter may say `unknown keys: writer` for a valid current event; this is a disclosed
   reporter limitation, not permission to change history or a reason to reject the current form.
   If the project deliberately depends on that reader as a gate, stop and agree its treatment before
   issuing the new form. Template-owned pre-write validation remains mandatory.
3. Deliver the user onboarding in section 6, then start with one ordinary task in one pilot project. Observe
   context selection, budget classification, session naming and correction routing before expanding
   adoption. This release does not itself update any receiving project.

Before any new post-update task writes, rollback can restore the saved framework/config/adapter
snapshot without touching task history. After new writes, do not blindly downgrade or delete them:
stop and assess their approval epoch and form compatibility first.

## 6. Finish with positive, useful user onboarding

After successful verification, deliver `.tfw/templates/briefing.md` in `tfw.content_language` as
the update's final user-facing message, and record delivery in the update checklist. This is required
even for an unattended update: a version number and a list of changed files are not the onboarding.
The target workflow's final **Provenance, Verify, Brief, Clean** stage owns it; the template's old
Step 8a label is not another step to locate or a reason to omit the briefing.

Keep the template's four blocks and derive every bullet from the intervening CHANGELOG's
Added/Changed/Fixed/Removed entries. Frame the facts as useful possibilities and simpler work, not
an administrative burden or unexplained terminology. For this release, explain these practical gains:

| CHANGELOG source | User-facing value to explain |
|---|---|
| Added: session identity | You can distinguish the task and phase of concurrent sessions by their titles |
| Added: stable principals | Responsibility can follow a named participant without inventing a new identity for every session |
| Changed: selective context | The agent reads the material needed for the current decision; required checks remain |
| Changed: VALUE accounting | Writing required tests, evidence and journal entries no longer consumes the budget for the actual deliverable |
| Changed: isolation | Parallel mutating work has separate Git indexes; reviewed results still have a traceable origin |
| Fixed: rung-specific correction | A correction covered by the existing specification can proceed without creating a replacement specification just because another review happened |
| Removed: separate new/modified file sublimits | There are fewer overlapping budget limits to reconcile; the approved VALUE budget and authority bounds remain |

State the receiving project's actual setting changes and preserved values under **What you now do
differently**, including that historical approved tasks were not rewritten. State the verified outcome,
not a plan to verify later. Be positive and concrete without unsupported savings figures, universal
reliability claims, or saying that full autonomous team mode has shipped. If a category is absent from
the applicable entries, use the template's honest empty-category line; never invent a benefit.
