# Updating to TFW 3.9.0

This minor release keeps every TFW project to its result and its selected trace. Working material
leaves the project for the system temporary directory, `evidence/` becomes a registry of what was
verified, how and what was observed, and a comment in a value file carries value for its reader or
is read by a program. It changes no task-state or numeric economics schema, formal role, routing
field or provider capability. Installation does not reopen frozen approvals, completed tasks or
historical records.

## 2. What changes for new work

Adopt the changed instructions at the next authorized activation or resumption of continued work.
Frozen HL/TS and existing routes stay as they are; a material scope change uses their ordinary
amendment authority.

| Retired wording / behavior | Successor in this release |
|---|---|
| `conventions.md` → `Evidence subfolder`: "Additional binary artifacts (screenshots, API responses, logs) go into the same `evidence/` folder and are indexed in the EV file's Attachments section." | `evidence/` holds only the EV registry. Raw output, logs, exports, screenshots, archives, copies and helper scripts are working material: the role that needs them keeps them in the system temporary directory under `tfw/<ID>/`, private to that role, and removes them when its work ends (`conventions.md` → `Working material`). |
| EV columns `What was verified · Environment · Result · Artifact` and the Attachments section | Registry columns `Verified · How · Observed · Result`. Each row carries the deciding values, not raw output; a claim that cannot be repeated is attested. The Attachments section is gone. |
| No rule about comments | `conventions.md` → `Comments`: in a value file a comment carries value for its reader or is read by a program; comments are not a channel between agents. |
| Daily: "Keep products at their ordinary project paths." | The record lists every product with its project path, and before each orderly turn return the record folder holds only record and economics files; working material stays under the system temporary `tfw/<folder ID>/`. |

The Executor writes each EV row when its observation is made and removes its working material
before returning (`handoff.md` steps 8, 10 and 11). The Reviewer repeats a check or opens the live
result instead of relying on another role's material, and lists the comments a Candidate adds
(`templates/review/verify.md`). Daily stays a separate opt-in group; refresh it under its
installation contract only when it is selected. The shipped economics helper and the configuration
and bindings templates lose their non-value comments; behavior and keys are unchanged.

## 3. Why comment correspondence harms

Comments had become a channel: agents left notes for one another in code and configuration
instead of in the trace. Such correspondence:

- goes stale and starts contradicting the code it sits in;
- grows into a wall and a slow conversation between agents;
- lets an agent leave a note instead of finishing the work;
- makes every later reader pay for it in tokens.

The reason for a decision already has a home in the trace: HL, TS, RF, REVIEW or the Daily record.
A comment that carries value for its file's reader stays, and a comment a program reads stays byte
for byte.

## 4. The cleanup offer

After the update applies, ask one material question, under the update workflow's rule to ask only
when evidence cannot settle a consequential choice:

> Open a separate TFW task to remove comment correspondence from existing code?

- **Now:** after the update completes, the owner starts `/tfw-plan` for the cleanup task. The update
  itself edits no code.
- **Later:** recorded; the owner may start the task at any time. Nothing else is tracked.
- **Not at all:** recorded.

Whatever the answer, new agent writes follow `Working material` and `Comments` from this update on.
Record it in the update receipt, §2, row `Material questions` (form
`<none, or question → answer/route>`), keeping only the answer actually given, the answering human
and the time:

```text
| Material questions | Open a separate TFW task to remove comment correspondence from existing code (migrations/3.9.0.md §4)? → now: owner starts /tfw-plan cleanup task after this update / later / not at all — <answering human>, <time>; new agent writes follow Working material and Comments regardless |
```

## 5. What update never does

Update rewrites no receiver code, comment or history, and it moves or deletes no existing
`evidence/` file, attachment, Daily record or leftover. A task in flight keeps what it has already
committed; its new rows follow the registry form.

## 6. Root instructions

Every adapter root now states both rules in one line that begins
`**Working material and comments.**`:

- Codex and Claude Code receive it inside their managed blocks; Cursor and Antigravity receive it
  with the copied rule files.
- A managed block with local edits is drift, and update refuses it (`update.md` Step 4). Once the
  receiver resolves the drift, the line arrives.
- A project's own rules outside the block, such as Claude's "Mandatory Rules", are never touched.

The Cursor and Antigravity rule files also list the eight Coordinator commands in one row instead
of two.
