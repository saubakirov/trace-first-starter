# Updating to TFW 3.3.0

New Full projects use `workspace` without a container interview. Existing projects retain their
chosen working paths; established historical storage remains readable without entering current-work
discovery. This guide is the bounded container/state exception within the existing update workflow,
not an archive manager, runtime, new lifecycle, or instruction to complete old tasks.

## 1. Resolve the same pinned target and applicable route

Use the final verified target's `.tfw/workflows/update.md`, changelog and guides. For a published
release verify `v3.3.0` and its full commit; an explicitly authorized untagged Candidate records its
actual full SHA and never impersonates that tag. Do not copy a live source tree.

- Installed 3.2.0: this guide directly; inspect any incomplete earlier migration.
- Earlier supported versions: follow the ordered starting-version routes in [3.2.0](3.2.0.md),
  including its predecessor guides/changelog sections, then this guide. Acquire them all from the
  same final target. Historical tag examples do not select intermediate payload installations.
- Installed 3.3.0: read this target-version migration entry and existing attempt/preservation before
  an already-current return, even with no intervening range. Re-observe actual completion.
- 0.x, unknown/custom versions or contradictory provenance: stop before application for a
  project-specific migration plan; never use full init to repair missing migration evidence.

Keep the existing update order: authority/preview, connected application, source and receiver checks,
cleanup disposition, immutable attempt receipt, then outcome. This guide adds no per-file approval.

## 2. Select the affected group by project evidence

`tfw.task_containers` remains the ordered active choice. Creation uses its first path; current
discovery and the Knowledge Gate use active paths only. Optional `tfw.historical_containers` is a
list of repository-relative directories for exact reading, initialized-project detection and
documentation. New projects receive no historical key/folder. Reference readers deduplicate resolved
paths in active-then-historical order; they refuse whole-ID collisions instead of choosing by order.
Validate malformed/duplicate YAML keys, historical path shape and conflicting reference membership
before application. Do not silently coerce historical input or normalize an existing active choice.

| Present receiver | Authorized effect |
|---|---|
| `[workspace]`, `[tasks]`, custom single/multiple paths or reversed `[tasks, workspace]` | Preserve exact active choice and creation behavior; retain any valid historical choice |
| Exact `[workspace, tasks]`, secondary absent or empty, determinate remembered state | Normalize active list to `[workspace]`; add no historical scaffold |
| Exact mixed list, established historical-only `tasks` | Active `[workspace]`; append `tasks` once to retained historical paths; reconcile only its exact remembered pairs |
| Mixed with live/unclear continuation and no settled disposition | Preserve operational reachability; present affected work together in one material question |
| Mixed with recorded keep-active decision | Preserve the list and that decision; do not repeat the unchanged question |
| Already migrated or partially applied | Re-observe against preservation and current input under §4; no repeated retirement |

Historical disposition follows actual task/phase state, continuation obligations and recorded
project authority. Old age, an ID prefix, list position, missing modern state or the mixed list alone
prove nothing. An explicit container-level historical disposition can govern stateless history without
inventing DONE/REJECTED. Keep that source reachable. Record a new keep-active answer in the existing
immutable attempt decision fields with its relevant membership/authority; a later unchanged case reuses
it. Changed material circumstances need fresh observation, not blanket retention or another interview.

Walk only the affected container and active/reference membership needed to identify the group. Use
the canonical direct-child plus four-digit-year traversal and whole-ID grammars. Account for each
path exactly once; report malformed/unreadable paths, duplicate IDs and unexplained remembered keys.
An absent directory cannot explain remembered IDs by prefix. Refuse indeterminate reconciliation;
never prune `HD-10` merely because the historical set contains `HD-1`.

## 3. Preserve, revalidate, and apply sequentially

Before the first affected state/config/provenance write, preserve one immutable attachment under
`.tfw/update_receipts/` containing: pinned source full SHA and guide identity; previous provenance;
disposition and its exact authority; old/intended active and historical fields (including absence);
exact container-path → whole-ID membership; old digest-map presence and exact pairs to remove;
original config/state bytes or content-addressed before-images. Include enough unaffected-state
identity to demonstrate preservation. No secret or private preference belongs in this attachment.
Content-address the attachment; reuse identical bytes, refuse a same-address mismatch. It is finite
historical evidence, not a mutable registry. Preserve it before publishing version/provenance too.

For a self-hosted implementation before Candidate exists, identify its approved immutable Baseline,
TS approval and actual proposed payload/guide hashes; never invent a future Candidate SHA. Subsequent
result evidence binds the tested Candidate. Receiver updates still require the pinned target SHA.

1. Establish a safe boundary for affected writers and retain exact preservation evidence. Install
   compatible canonical readers and selected adapter copies before narrowing the active scope.
2. Immediately re-read source identity, disposition, affected fields, whole-ID membership and digest
   values. Compare with preserved old/intended input. Refuse disagreement before either live write.
3. Remove only remembered pairs whose whole IDs belong to the established historical set and whose
   current values equal the preserved values. A map absent initially stays absent: no invented
   processing or empty replacement map. Preserve every unaffected key/value, knowledge, source
   marker, consolidation date/statistic and unrelated config; do not recompute fictional consolidation.
4. Publish the intended active/historical fields only after exact state reconciliation. Preserve
   valid unrelated historical paths. Never move, rename, copy, delete or relabel task artifacts.
5. Verify actual current discovery, removed-ID reconciliation, historical exact reads, unchanged
   task bytes and unaffected state. Complete the connected group before ordinary gate arithmetic,
   provenance completion or successful update reporting. Preserve configured hard/soft/off behavior.

These are recoverable sequential writes, not an atomic switch for arbitrary concurrent readers.
On a failed write, retain preservation and present state; never restore the whole old map or tree.
Ordinary knowledge consolidation still applies its unchanged source-effects-then-state-last rule.

## 4. Re-entry: finish expected cuts or refuse conflicting input

Resolve the same pinned target and preservation before deciding. Current affected fields must equal
their recorded old or intended values; each removed pair may be old-and-equal or already absent.
The exact membership/disposition must still agree. A digest map absent initially must remain absent;
unexpected map disappearance is not successful pruning. Unaffected later active edits are retained.

| Observed cut/repeat state | Action after input validation |
|---|---|
| Before preservation; no affected write | Observe and prepare §3 preservation, then proceed |
| Preservation only | Reuse the verified attachment and continue |
| Compatible readers only | Revalidate; reconcile state then config |
| State reconciled, old config | Preserve later active values; publish only intended affected config |
| Legacy config-first cut, old digests | With valid before-image/authority, reconcile exact pairs before gate arithmetic; missing evidence refuses |
| Final config/state, incomplete provenance or receipt | Verify actual group, finish remaining ordinary update effects; do not migrate again |
| Completed repeat, including equal version | Verify identity, current applicability and receipt/cleanup state; report unchanged without repeating retirement or question |

Refuse the affected group for: missing/colliding required preservation; target/source mismatch;
conflicting disposition; changed membership or whole-ID collision; changed affected digest; divergent
affected config. Preserve the conflicting input and subsequent work; name the exact conflict and
next authoritative action. Never fabricate a before-image from the narrowed state, treat an old
receipt as current authority, apply a whole-map rollback, or silently reset knowledge to pass a gate.

## 6. Verify the actual receiver and explain the result

Verify target/version/provenance, applicable routes, exact copies, selected effects and preservation;
then run the receiver's applicable checks. Source/model checks are not native init/update/resume
evidence. Keep pre-existing gate issues separate from introduced removed IDs. No Python helper or
upstream pytest/MkDocs suite becomes a receiving project's prerequisite. Final `.tfw/VERSION` and
`tfw.version` agree at 3.3.0; installed provenance names the verified tag or authorized full SHA.

Use the existing immutable receipt and briefing: actual outcome, useful default/historical access,
preserved choices, unresolved limitations and next action. Complete cleanup disposition before the
receipt and render the outcome last. Do not claim the recipient read it, full init completed merely
because a task was created, or a release was published merely because its version was installed.
