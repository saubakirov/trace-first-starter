# Updating to TFW 3.9.1

This patch makes the selected inter-role messages reference-only and distinguishes local checks,
missing decisions and role completion. The substance remains in the owned records. It preserves
mandatory Saint-Exupéry judgment, independent review, Research's existing stage dialogue and
human authority. It adds no runtime validator, task-state field, registry or provider capability.

## 1. Pin the complete target

Resolve the published `v3.9.1` tag to its full commit and verify VERSION. Before publication, use
only an explicitly authorized full untagged commit and label it untagged; an implementation
Candidate with older version metadata is not a complete prepared 3.9.1 release. Read that source's
update workflow, changelog and applicable guides before changing a receiver.

| Installed version | Ordered remaining obligations |
|---|---|
| 3.9.0 | This guide |
| Every earlier supported version, including supported 1.x and 2.0.0 dirty tags | Follow the exact route in [3.9.0](3.9.0.md), including its linked earlier obligations, then this guide |
| 3.9.1 | Verify exact source, selected bytes, receipt and any unfinished attempt before an already-current return |
| 0.x, unknown/custom or contradictory provenance | Stop for a bounded migration decision; full init is not migration |

Read obligations in order and install the selected final payload once through
[Update](../workflows/update.md). Preserve project settings, purpose, personal preferences,
task/phase state, journals, frozen approvals, qualified knowledge, original economics returns,
dated reports and unrelated work. Historical guides retain their original meaning; the explicit
successors below govern the selected target.

nor a human pause. Research retains its command-first activation, required stages, questions,
presentation and WAIT behavior with the existing routing restrictions. Owner–task Coordinator
discussion stays substantive; iterative dialogue still requires its exact separate grant.

## 3. Install and adopt at a safe boundary

Install the connected canonical rules, selected Plan/Handoff/Review workflows, ONB/REVIEW templates,
glossary and selected adapter roots/copies from the same pinned source. Use the existing manifest:
Codex/Claude managed blocks preserve project-owned neighbours; Cursor/Antigravity rule files and
Claude/Cursor command copies follow their copy strategy; thin skills continue routing to canonical
workflows. Preserve customized or ambiguous receivers for the update workflow's existing decision.
The manifest and outcome briefing need no new field or catalogue copy.

For work already in flight, finish or pause the current act at an authorized safe checkpoint.
Before the next activation/resumption, the responsible Coordinator and affected role validate the
installed source, current routing/selection, still-effective authority and reachable result refs.
Record a material adoption condition in the existing task-owned authority/handover record. An
unresolved mixed instruction set blocks the dependent send or act; installation alone neither
grants authority nor changes task topology. Reuse the same Executor and independent Reviewer.

Do not rewrite old messages, frozen HL/TS, earlier role results or immutable journal events to
make them appear produced under this catalogue. Read prior returns under their actual epoch.
If adoption conflicts with a frozen claim or requires a new reserved decision, use that existing
authority route before the dependent act. No migration creates a same-state lifecycle event.

## 4. Verify the selected receiver

Check exact target/version/config/changelog/guide agreement, managed-block preservation, copied
byte parity and selected skill/workflow routes. Follow glossary/catalogue links in the generated
documentation and inspect the rendered action tables. Exercise a no-blocker continuation, a
blocked decision, a completed role return, duplicate/stale delivery and missing-reference behavior
against the installed clauses; these observations establish contract consistency, not provider
reliability. Run the receiving project's configured checks, and record actual scope and limits in
its update receipt. No update alone authorizes publication, deployment or another project's work.
