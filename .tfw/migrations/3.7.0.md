# Updating to TFW 3.7.0

This release gives new work one task Coordinator for strategy and owner contact, with a separate
Coordinator only for each bounded phase of long work. It also adds an optional Daily route for small,
one-person tasks. Existing task records and their actual authority remain readable; this guide does
not turn an old route into a new mandate.

## 1. Pin the source and follow the complete route

For a published installation, resolve `v3.7.0` to its exact commit and verify that its
`.tfw/VERSION` is `3.7.0`. Before a tag is published, an explicitly authorized untagged source
uses its full commit SHA and is labelled untagged. Read the pinned target's update workflow,
changelog and every applicable version-addressed guide before changing a receiver.

| Installed version | Ordered remaining obligations |
|---|---|
| 3.6.1 | This guide |
| 3.6.0 | [3.6.1](3.6.1.md), then this guide |
| 3.5.2, 3.5.1, 3.5.0, 3.4.1, 3.4.0, 3.3.0, 3.2.0, 3.1.0, 3.0.0, 2.2.0 or 2.1.0 | Follow that version's exact row in [3.6.0](3.6.0.md), then 3.6.1 and this guide |
| 2.0.0, `2.0.0-dirty`, `2.0.0-dirty.2`, `2.0.0-dirty.3`, `2.0.0-dirty.4` or `2.0.0-dirty.5` | Follow that exact 2.x row in [3.6.0](3.6.0.md), including its named CHANGELOG obligations, then 3.6.1 and this guide |
| 1.0.0, 1.1.0, 1.2.0 or 1.3.0 | Follow the 1.x row in [3.6.0](3.6.0.md), including [2.0.0](2.0.0.md) and its CHANGELOG route, then 3.6.1 and this guide |
| 3.7.0 | Verify source identity, selected bytes and any unfinished prior update before an already-current return |
| 0.x, unknown/custom or contradictory provenance | Stop for a bounded migration decision; full init is not migration |

Read obligations in order, but install the selected final payload once through the target update
workflow. Preserve project settings, personal preferences, custom instructions outside managed
blocks, task/phase status, journals, frozen authority, historical records and unrelated work.
Uncertain source ownership or a mixed connected group requires its bounded refusal, not a blind copy.

## 2. Install the connected Full instruction group

Refresh the selected canonical `.tfw/` workflow, convention, glossary, templates and three
Coordinator profiles from one immutable source. The changed group includes Plan, Review, Init,
Update and Config, the HL/REVIEW/status templates, persistent adapter sources and the selected
installed Codex, Claude Code and Antigravity copies. Use
`.tfw/adapters/manifest.yaml` only as the tooling copy/check map; runtime roles do not read it.
Cursor remains common-only and gets no provider profile. Do not install an absent adapter.

Synchronize only installed exact ten-command Full routes. Verify each `copy` target byte for byte
against its source and each `managed_block` against its one declared marker range, preserving
unrelated instructions. Keep `.tfw/templates/briefing.md` and the manifest's pinned unchanged
bytes in the final source tree; neither becomes a role launch briefing. The first message to a new
role remains only `/tfw-* <task[/phase]>`.

Set `.tfw/VERSION`, the framework's `tfw.version` in `.tfw/project_config.yaml`, and the
framework version in `.tfw/templates/project_config.yaml` to `3.7.0`. A receiving project's
config merge preserves project-owned settings and records exact source provenance. Include this
guide and the matching `.tfw/CHANGELOG.md`. Do not rewrite earlier migration guides.

## 3. Adopt the new-work topology without changing old authority

The following retired 3.6.1 instructions are quoted to identify the exact normative reversals;
their successor applies to **new work** and authorized safe handovers, not retroactively to
historical task files.

| Retired wording or shape at 3.6.1 | 3.7.0 successor |
|---|---|
| Codex profile: “Full-session delegation uses a separate owner GATEWAY and a Coordinator per ready phase; direct coordination needs an explicit owner choice.” | The task Coordinator itself owns strategy, phase advancement and owner contact. One-phase work needs no phase Coordinator; long work gives each ready phase its own bounded Coordinator. No separate GATEWAY is issued. |
| Codex profile: “for an approved multi-phase map create one separate Coordinator per ready phase, and one for a single phase.” | Create a phase Coordinator only for a bounded phase of long work. The original planning Coordinator remains the task Coordinator while capable. |
| Status template: `owner_gateway: owner:human-handle` as the new task's upward route | New task statuses use `upstream_route: owner:{human-handle}`; new phase statuses use `upstream_route: coordinator:{actual-task-Coordinator-address}`. The four shared fields plus exactly one upward route and the selection pair form the complete current spine. |
| Claude profile: “Conditional compact route” allowing separate role subagents for eligible small work | Full TFW Researcher, Executor and independent Reviewer roles require distinct, directly addressable units. A subagent does not substitute for a role. A small task can still use one task Coordinator without a second coordination layer. |

Keep a complete historical `owner_gateway` carrier, GATEWAY/LEAD record and immutable selection
under its actual epoch. Never infer a new parent, route or owner answer from a title, principal,
machine or old field. A live successor requires a safe checkpoint, exact address, acknowledged
reconstruction from current task files and an authorized route switch; until then the old route
remains effective. The `reporting`/`selection_ref` pair and independent two-peer dialogue grant
retain their separate authority checks.

With `native-gates` and `tfw-gates-only`, Researcher, Executor and Reviewer send material status,
questions and durable returns only to their own Coordinator. A phase Coordinator returns only
phase-level decisions, blockers and results to the task Coordinator. A real workflow checkpoint,
not a relabelled hint or copied reasoning, justifies each gate. The task Coordinator may discuss
strategy with the human owner and advance authorized phases without routine command transfer.
Provider creation and wake limits remain actual-surface observations, not promises made by this
guide.

## 4. Keep Daily optional and preserve local forms

The new `.tfw/extensions/daily-task/` source and
`.tfw/extensions/daily-task/installation.md` define a separate, bounded Daily route. It is not an
eleventh Full command and is not selected merely because canonical source files exist. The
framework repository opts in to the Codex and Claude discovery entries; receiving projects need
their own explicit selection or verified prior installation.

Before any generic update write, classify the entire Daily connected group by the pinned
installation contract. Preserve selected local form semantics, existing history and unrelated
field skills. A customized or ambiguous canonical skill, discovery entry or form ownership
refuses only that connected Daily group; independent Full groups may continue. Refresh only
selected entries from the same immutable source and verify exact source/target bytes separately
from the ten Full routes. No service, registry or bulk task conversion is introduced.

## 5. Verify the receiver and release composition

1. Verify target tag or full untagged SHA, VERSION, both framework version fields, changelog and
   this guide all agree. Check exact source/installed adapter parity, selected Daily entries and
   the fixed ten Full commands.
2. Exercise a new task route, a new phase upward route, a complete historical
   `owner_gateway` carrier and refusal of partial/double/wrong-parent routing. Preserve old
   status and journal bytes. If an optional upstream `tools/tfw_state.py` reader is installed,
   update it coherently; it is not a new receiver runtime dependency.
3. Check one-phase, sequential/parallel phase and safe-successor next actors; verify that role
   messages go to their own Coordinator and that owner-reserved decisions still stop dependent
   work. Inspect provider capability limits on the actual surface. A filesystem copy cannot prove
   live external activation, browser coverage or idle-parent wake.
4. For selected Daily, check opt-in, local-form preservation, repeat application and absence of
   an extra Full command. Run the receiver's configured checks and record exact source, paths,
   preserved inputs, limits and results.
5. Upstream additionally runs its configured pytest/MkDocs checks and staged/full-history
   Git-blob guards against the final checked release tree. A passing check is evidence for its
   named subject, not proof of owner comprehension or provider reliability.
