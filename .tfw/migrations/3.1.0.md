# Updating to TFW 3.1.0

Pin `v3.1.0` and verify the tag's commit and `.tfw/VERSION`. Read that exact target's
`.tfw/workflows/update.md` before applying files. This guide supplies version-specific obligations
and explicit successors to older wording; the target workflow remains the single update procedure.
Never copy a moving working tree or treat an unpublished commit as a published release.

## What this release gives your project

- You can request an ordinary update without answering a standard technical questionnaire: the agent
  first discovers facts already recorded in your project and asks only about consequential gaps.
- Your project keeps its purpose, settings and work history while receiving current TFW instructions
  and values. Updating the framework is not a fresh project setup or a decision to adopt autonomy.
- The result explains what you can use now, what was preserved, what remains unverified and what to
  do next. A retained record makes an interrupted or partial update easier to inspect and continue.
- Your release process remains your own. Projects with different outputs or no releases do not inherit
  this framework repository's Git, versioning or publication procedure.

These are changes to the delivered instructions, not a promise that every agent follows them perfectly.

## 1. Select the starting-version route

**If the project has not reached stable 2.0.0, first read [the 2.0.0 migration](2.0.0.md).** Account
for its still-needed corpus, participant and configuration work. Reading it does not certify an
automatic migration for an unknown/custom or 0.x project.

All guides and changelog sections below come from the same final `v3.1.0` object. Intermediate tags
need not be installed. Their version/ref examples describe their historical release, not the final
target; apply the remaining actions in order under the final target workflow. Observe actual state
and evidence before repeating any migration.

## 2. Preserve the project and apply only the needed configuration changes

Before replacement, retain a recoverable payload/config/adapter snapshot and establish a safe boundary
for affected project writers. Preserve root `README.md`, root `RELEASE.md`, `KNOWLEDGE.md`, `knowledge/`,
task containers and their history, profiles/grants, private preferences and external machine bindings.
Do not import this repository's project state or reset `.tfw/knowledge_state.yaml`.

The current `.tfw/README.md` is classified by purpose and authority under the target workflow. Current
framework values are part of an ordinary framework refresh, not a separate request to adopt this
repository's project purpose. Preserve customized, project-purpose-bearing or historically cited bytes
at the target workflow's content-addressed legacy attachment BEFORE replacing the current copy. Reuse
an identical attachment; refuse a different-byte collision. Preserve historical citations and resolve
their meaning through the attachment. An unresolved purpose conflict needs one material question,
not a guess. Do not replace the project's root README or fabricate a missing Project North Star.

| Configuration subject | 3.1.0 action |
|---|---|
| `.tfw/VERSION` and `tfw.version` | Agree at `3.1.0` after the approved application; equality alone is not completion |
| `tfw.installed_from` | Record configured upstream plus verified `v3.1.0`; receipt also records the exact full commit. An explicitly authorized untagged experiment instead uses its full SHA, never a fabricated tag |
| `tfw.upstream`, project identity, `task_containers`, `build.*`, scope budgets and chosen values | Preserve project ownership; merge framework-owned additions by key, not by replacing the config |
| Retired keys | No new retirement in 3.1.0. Apply 2.2.0 budget renames and 3.0.0 removals only if still needed; preserve numbers and stop on an unresolved mixed old/new block |
| Knowledge state, profiles, grants and autonomy | No automatic reset, profile creation, grant change, receiving LEAD selection or AT adoption |

Refresh only installed or owner-selected adapters through the pinned manifest. Antigravity's canonical
targets are `.agents/rules/tfw.md` and `.agents/workflows/tfw-{command}.md`; the older singular rule
location is compatibility guidance, not evidence that a provider discovers singular workflow copies.
Compare exact owned files before retiring duplicates; preserve foreign neighboring rules/commands.
Do not copy the starter's project-owned `RELEASE.md` over the receiving project's procedure.

## 4. Verify, record and explain the actual result

Use the target workflow's verification gates: exact source/version/provenance, applicable migration
paths, config and purpose preservation, selected adapter parity, intended diff and receiver checks.
Retired paths and keys from older routes must not survive as unexplained current requirements.
Check the receiving project's own commands; the maintainer suite and MkDocs environment are not
new receiver prerequisites. A placeholder, missing dependency or pre-existing failure is not PASS.

After checks, resolve or disclose cleanup while required source remains available. Then seal one
immutable `.tfw/update_receipts/UPDATE__YYYYMMDD-HHMMSS__<four-hex>.md` using the target template.
At that moment final-message delivery is `planned/not-yet-observed`. Render the final message next;
do not rewrite the receipt to claim that a person read or understood it. Re-entry observes current
files and authority instead of trusting a prior receipt or the version number alone.

Give the owner a positive, concrete explanation in their language: actual outcome first; useful new
possibilities supported by the release; what was preserved or materially changed; limitations and
the next ordinary project action. Link technical detail only when useful. For example, after verified
success explain that the project retained its settings and history, and future updates now ask the
agent to discover routine facts before involving the owner. Do not manufacture those preservation
facts when they were not checked. A partial result must clearly say what remains, without presenting
the framework's internal procedure as the user's benefit.

This release does not claim universal agent reliability, measured savings, confirmed owner comprehension
or broader native provider admission. Source tests and independent review are not a substitute for
observing a receiving project. No repeat field campaign is required by this migration.

## 5. Recovery and release boundary

On failure, stop the affected group and retain the source/preservation references needed for recovery.
Restore only the recorded pre-update payload/config/adapter paths when authorized and compatible with
current project work. Never erase intervening task work or rewrite immutable events to make rollback
appear clean. After new task writes, assess their form and approval epoch before downgrading.

The update request does not authorize changes to another repository, production deployment, tag,
push or publication. Preparing or installing TFW also does not release the receiving project's product.
